# 템플릿 설계 근거 (DESIGN_DECISIONS)

이 템플릿이 **왜 이렇게 생겼는지**를 남깁니다. 프로젝트의 결정은 `docs/adr/`에 쌓이고, 이 문서는
템플릿 자체의 결정을 다룹니다. 초기화 후에는 지워도 됩니다.

## 출처

실제 팀 프로젝트(6인, 2주 스프린트, 공개 저장소)에서 검증된 스캐폴딩을 일반화한 것입니다.
여기 적힌 함정은 대부분 **실제로 밟은 것**이며, 그래서 규칙 옆에 항상 "왜"가 붙어 있습니다.

## 1. 왜 모노레포인가 — 그리고 왜 AI만 독립 배포인가

레포 구조 조사의 실질은 "쪼개라"가 아니라 **"AI를 인라인 호출이 아니라 독립 배포 가능한
엔진으로 두고 배포·운영을 문서화하라"**였습니다. 형식(멀티레포)과 실질(독립 배포 모듈)을 구분하면,
소규모·단기 팀에서는 모노레포 + 앱별 배포 단위가 우세합니다. 상세: [adr/0001-monorepo.md](adr/0001-monorepo.md).

경계가 물리적으로 강제되지 않으므로 세 가지로 대신합니다: `CODEOWNERS`, 앱 간 파이썬 import 금지
규약, 그리고 앱 디렉토리를 빌드 컨텍스트로 삼는 `docker-build.yml`(이미지 빌드 + `/health` 확인).
마지막 것 덕분에 "독립 배포 가능"은 주장이 아니라 **회귀 검사 대상**이 됩니다.

## 2. 왜 워킹 스켈레톤을 넣었나

빈 스캐폴딩은 "구조는 있는데 아무것도 관통하지 않는 상태"에서 오래 머무릅니다. 관통 경로를 먼저
만들어 두면 팀원 각자가 **자기 이음매만 교체**하면 되고, 통합은 첫날부터 이미 끝나 있습니다.

대신 스텁이 실물로 오해될 위험이 생기므로, 세 곳에 경고를 박아 두었습니다: `AGENTS.md`의 현재 상태
절, 코퍼스 파일의 `[더미]` 표시와 fixtures/README, `StubGenerator`의 docstring.

## 3. 왜 가드레일이 두 겹인가

프롬프트만으로는 보장이 되지 않습니다 — 프롬프트는 요청이지 강제가 아닙니다. 그래서 생성 후
출력을 근거와 대조하는 `verify()`가 따로 있습니다. 이 출력 검증이 있어야 **환각 억제율이 측정
가능한 숫자**가 됩니다.

`verify()`를 어휘 기반(문자 bigram)으로 둔 것은 의도적입니다: 모델 채점이 더 정확하지만 요청마다
외부 호출이 붙고 CI가 비결정적이 됩니다. 모델 채점은 `eval/`의 교차 채점 단계에서 하고, 그때
**채점 모델은 생성 모델과 달라야** 자기채점 편향이 빠집니다.

`enabled=False`가 `passed=False`를 반환하는 것도 의도입니다. 대조군 실행이 "깨끗한 통과"로 보이면
on/off 비교 자체가 무의미해집니다.

## 4. 왜 `eval/`이 ai-engine **안**에 있나

채점 기준은 채점 대상과 같은 PR에서 움직여야 재현이 유지됩니다. 별도 최상위 디렉토리에 두면
엔진이 바뀌었는데 기준은 그대로인 상태가 조용히 발생합니다.

같은 이유로 `eval/`은 pytest 수집 대상(`testpaths = ["tests", "eval"]`)입니다 — 지표 함수는 보고
숫자의 근거이므로 회귀 검사가 필요합니다. 대신 **실제 채점 실행은 `run_*.py`로 이름 지어** CI가
외부 API를 부르지 않게 했습니다. 파일 이름이 CI 동작을 가르는 드문 경우라 README에 명시했습니다.

## 5. 왜 E2E가 `apps/*/tests/` 밖에 있나

`apps/*/tests/`는 **required** pytest 매트릭스가 수집합니다. E2E는 스택 기동과 외부 키를 요구하므로,
거기 두는 순간 모든 PR이 인프라 사정으로 막힙니다. 관통 검증은 "머지 차단"이 아니라 "신호"여야
합니다. 그래서 별도 최상위 + non-required 워크플로 조합입니다.

`E2E_BASE_URL` 미설정 시 전량 skip으로 두어, "연결은 돼 있고 대상만 아직 없는" 상태가 초록을
유지하도록 했습니다. 스택이 뜨면 자동으로 실제 검증에 들어갑니다.

## 6. 왜 required 워크플로에 paths 필터가 없나

GitHub의 유명한 함정입니다. required로 지정된 워크플로에 `paths:` 필터가 있으면, 그 경로를 건드리지
않은 PR에서는 체크가 **생성되지 않고** 머지가 영원히 `Expected`로 대기합니다. 그래서 `ci.yml`만
필터 없이 모든 PR에서 돌고, 나머지 4종(frontend·docker·contracts·e2e·notebook)은 non-required입니다.

non-required 워크플로는 **대상 파일이 없으면 전 단계를 건너뛰도록** 작성했습니다. 프론트엔드나
compose가 생기는 순간 별도 설정 없이 활성화됩니다.

## 7. 왜 시크릿 방어가 3중인가

각각 구멍이 있기 때문입니다. GitHub Push protection은 제휴 발급사 패턴만, pre-commit
`detect-private-key`는 PEM 개인키만 잡습니다. 그 사이의 일반 API 키 문자열이 사각지대라
**gitleaks**를 넣었습니다.

⚠️ gitleaks의 pre-commit 훅과 CI 스텝은 **한 쌍**입니다. 훅 entry가 `--staged` 고정이라
`pre-commit run --all-files`(CI)로는 아무것도 검사하지 않기 때문입니다. 둘 중 하나만 남기면
방어선이 사라집니다.

## 8. 왜 ruff `select`를 명시했나

비워 두면 ruff의 기본 규칙셋을 상속하는데, ruff는 0.x라 마이너 업그레이드에서 기본값이 넓어집니다
(실측: 0.15 통과 → 0.16에서 신규 검출 다수). 즉 버전을 올릴 때마다 린트 정책이 팀 의사와 무관하게
바뀝니다. 명시하면 규칙 변경이 코드 리뷰를 거치는 **명시적 diff**가 됩니다.

같은 이유로 ruff 버전은 세 곳(`.pre-commit-config.yaml` rev + 두 앱의 dev extra)에 **고정**돼 있고,
그 셋은 항상 함께 올려야 합니다.

## 9. 왜 문서 폴더만 한글인가

문서는 사람이 읽는 것이라 한글 이름이 검색·인지에 유리합니다. 반면 코드·설정·CI 경로는 빌드
도구와 셸이 소비하므로 비ASCII 세그먼트가 인코딩·이식성 사고를 냅니다. 그래서 **무엇을 담느냐**로
갈리며, 위치로 갈리지 않습니다.

## 10. 이 템플릿이 하지 않는 것

- **프론트엔드 스캐폴딩** — 프레임워크 선택은 프로젝트마다 다릅니다. 자리와 CI, 그리고
  `.gitignore` 함정 경고만 준비해 두었습니다.
- **벡터 DB·모델 클라이언트 선택** — 이음매(프로토콜)만 정의하고 구현은 비워 두었습니다.
  무거운 의존성을 core에 넣지 않는 것이 CI를 가볍게 유지하는 장치입니다.
- **배포 자동화** — `docker-compose`까지만. 클라우드·리전·인스턴스 선택은 ADR로 남길 프로젝트
  결정입니다.
