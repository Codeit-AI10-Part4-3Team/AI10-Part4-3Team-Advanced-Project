### 품질 티어는 요청이 실어 보냅니다 (2026-08-20)

배정 4건 중 "품질 티어의 출력 유형별 분리"를 닫았습니다. **설정을 쪼개는 대신 계약에 실었습니다.**

- 계약에 `ImageQuality`(`low` / `medium` / `high`)와 `ImageRenderRequest.quality`(**필수**)가
  생겼습니다. 값의 정본은 호출자인 backend 의 `COMIC_QUALITY` / `SINGLE_AD_QUALITY` 상수입니다.
- **엔진이 `outputType` 에서 유도하지 않는 이유는 `spec` 과 같습니다.** 같은 계약이 이미
  "호출자가 규격을 정해 보냅니다. 엔진이 유형을 보고 스스로 정하면 값이 두 곳에 생기고, 한쪽만
  고치는 순간 어긋납니다"라고 못박아 두었고, 티어도 유형별로 갈리는 값이라 사정이 같습니다.
- **벤더의 `auto` 는 열거에 넣지 않았습니다.** 모델에게 맡기면 같은 요청의 비용이 최대 9배까지
  흔들립니다 (2026-08-13, 08-15 실측). `high` 는 열거에 있지만 재지 않았습니다 -- 쓰기로 하면
  병렬 소요 시간과 타임아웃을 다시 재야 합니다 (N19-a).
- **`ADGEN_IMAGE_QUALITY` 는 `ADGEN_IMAGE_QUALITY_OVERRIDE` 로 이름이 바뀌었습니다.** 개발과
  검증 실험을 `low` 로 돌리기 위한 스위치입니다 -- 그러자고 backend 의 운영 상수를 고치면 그
  값이 그대로 배포됩니다. 발동하면 경고 로그가 남으며, **그 상태로 잰 숫자는 운영 경로의 숫자가
  아닙니다.**

**남은 것 하나**: `infra/.env.example` 의 항목 이름 갱신입니다 (소관 05, 미결정_대장 E-2).
`docker-compose.yml` 은 이번에 함께 고쳤습니다.

### 인수 항목: `draft:patch` 누락 (2026-08-15 해소)

재배정으로 03 을 인수하면서 **계약에는 있는데 엔진이 서빙하지 않는 경로**가 하나 넘어왔습니다.
`apps/ai-engine` 이 `/health` `/v1/generate` `/v1/brief:fill` `/v1/draft:generate`
`/v1/image:render` 다섯만 서빙하고 있었고 `/v1/draft:patch` 가 없었습니다.

**증상이 엉뚱한 곳을 가리킵니다.** backend 클라이언트는 그 경로를 부르므로 실제 엔진 상대로는
404 가 돌아오고, 404 는 다른 HTTP 실패와 같이 매핑되어 사용자에게 **`503 UPSTREAM_UNAVAILABLE`**
로 나갑니다. 즉 S5(부분 교체)가 죽어 있는데 화면에는 "모델 API 를 쓸 수 없습니다"라고 뜨고,
디버깅하는 사람은 멀쩡히 돌고 있는 서비스를 들여다보게 됩니다. **S5 는 테스트 fake 상대로만
동작하던 상태**였습니다.

스텁 분기로 닫았습니다. 실물 분기(`_patch_with_model`)는 `draft:generate` 실물화와 같은
시점입니다 -- 두 경로가 같은 모델 호출을 공유하므로 따로 잡지 않았습니다.

  다시 설계해야 합니다.
- **부수 실측 두 가지**: 생성 시간 54 ~ 122초(동기 HTTP 금지 결정의 근거), `quality` 미지정 시
  품질 티어가 회차마다 흔들려 비용이 2.3배까지 벌어짐(예산 상한은 높은 티어 기준으로).

> **"AI 담당"은 03(생성·서빙)만 가리킵니다** (2026-08-14 확정). 이 역할이 수행한 1, 3, 5순위의
> 판정자는 **정승호·임동규·송기하 3명이고 2명 이상 동의로 통과**합니다. 4순위는 수행자가 04라
> 판정자가 임동규·송기하 2명이며 두 사람 모두 동의해야 합니다
> ([미결정_대장.md](../기술문서/미결정_대장.md) B-15, B-16).

### `image:render` 실물화를 앞당긴 이유 (2026-08-15)

**일정표와 판정 기준이 어긋나 있었습니다.** 중간 점검(08-17)의 PM 확정 문구는 "워킹 스켈레톤이
관통하고, **외부 이미지 생성 API 호출이 그 경로를 지나 실제 이미지를 반환할 것**"인데
([00-overall.md](00-overall.md) 3-b절), 이 표의 `image:render` 실물화는 08-22 ~ 08-26 이었습니다.
판정일보다 뒤입니다. 순서를 바꿔 먼저 배선했습니다.

**앞당길 수 있었던 이유는 검증 1순위가 이미 그 호출을 통과시켰기 때문입니다.** 모델, 규격,
응답 형태, 소요 시간, 단가가 전부 실측돼 있어(RESULTS.md) 남은 일은 하네스의 호출 모양을
이음매로 옮기는 것이었습니다. 프롬프트 문장도 실험이 쓴 것과 같은 뼈대를 씁니다 -- 다르면
20회를 들여 잰 결과가 지금 서비스가 쓰지 않는 문장의 결과가 됩니다.

**여전히 기본값은 스텁입니다.** `ADGEN_GENERATION_MODE=stub` 이 기본이고, 켜는 쪽이 위험하기
때문입니다 -- 켜면 요청마다 요금이 나갑니다. 실물로 돌릴 때는 키를 함께 채우고, 키 없이 켜면
렌더가 503 으로 명시적으로 실패합니다 (스텁으로 되돌아가지 않습니다).

**남은 실물화는 `brief:fill` 과 `draft:generate` 둘입니다.** 08-20 ~ 08-22 그대로입니다.

## 검증 2순위 결과와 A-1, A-2 확정 (2026-08-18)

실측 근거는 [API생성_시험_보고서.md](../보고서/API생성_시험_보고서.md) E절,
[로컬모델_탐색_보고서.md](../보고서/로컬모델_탐색_보고서.md),
[생성_경로_비교표.md](../보고서/생성_경로_비교표.md)입니다. 확정 근거는
[회의록](../회의록/2026-08-18_이미지_생성_경로_결정.md)입니다 -- 보고서는 수치를 제공할 뿐
결정이 아닙니다 ([AGENTS.md](../../AGENTS.md) 근거 자료 규칙).

- **A-2 확정. 컷별 생성 후 3x2 합성이 기본 경로입니다.** 08-14 시점에 "조건부 후처리"였던 것이
  기본 경로로 올라갔습니다. 전제 두 개가 실측으로 뒤집혔기 때문입니다 -- 호출 수가 6배인데도
  `low` 기준 **17% 저렴**하고(0.0974 대 0.1171 USD), 병렬 호출로 **55.9초**라 한 장 생성
  (54 ~ 122초)과 같은 구간입니다.
- **08-14에 적어 둔 "여백 편차로 실패 기준을 다시 설계한다"는 과제는 소멸했습니다.** 재려던
  대상이 컷별 생성에서는 존재하지 않습니다. 여백을 합성 단계가 결정하므로 편차가 0입니다.
- **A-1 확정. 본안 유지이고 예비안은 미채택입니다.** 정확도로는 갈리지 않았지만(둘 다 100%),
  예비안에는 **말풍선 위치를 사후 검출하는 단계**가 붙는데 그것이 된다는 증거가 없습니다.
  직선인 격자 경계조차 14 ~ 36px 어긋난 마당에 곡선은 더 어렵습니다.
- **품질 티어를 유형별로 고정했습니다.** 만화형 `medium`, 단일 광고형 `low`. `low` 만화형에서
  손과 사물의 물리가 무너지는 결함이 관측되었습니다.

**여기서 세 항목이 새로 열렸습니다** (미결정_대장 N18, N19, N20). 위 표의 "배정 대기" 네 줄이
그 항목들이며, **회의가 담당자를 정하지 않았습니다.** 컷별 생성 구현과 같은 사람이 맡아야 합니다.

**`medium` 병렬도 실측으로 채웠습니다** (08-18 추가 검증). 회의 시점에는 `low` 만 재고 `medium`
은 같은 비율을 가정한 판단이었는데, 세 티어를 다 재면서 그 가정이 확인되었습니다.

| 티어 | 순차 | 병렬 | 단축 | 개별 호출 팽창 |
|---|---|---|---|---|
| `low` | 132.4초 | 55.9초 | 57.8% | 44% |
| `auto` | 203.6초 | 83.6초 | 58.9% | 18% |
| `medium` | 310.8초 | **139.2초** | 55.2% | 64% |

**이것으로 타임아웃 위험이 좁아졌습니다.** `medium` 병렬 139.2초는 `render_timeout_s`(300초) 안에
2배 이상 여유가 있습니다. 남은 위험은 **순차 구현이 먼저 나가는 경우**(310.8초) 하나이며, 그
순서로 간다면 타임아웃을 함께 올려야 합니다 (N19-a).

**주의 둘.** 표본이 티어당 1세트입니다. 그리고 동시에 보내면 개별 호출이 느려지는데 **무거운
티어일수록 팽창이 큽니다**(`medium` 64%). `high` 는 재지 않았고, 팽창이 커질수록 병렬의 이득이
줄어들므로 티어를 더 올리는 결정이 나오면 다시 재야 합니다.
