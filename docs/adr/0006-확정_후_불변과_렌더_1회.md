# ADR-0006: 확정한 세션은 바꿀 수 없고 이미지는 한 번만 만든다

- **상태**: Proposed
- **날짜**: 2026-08-08
- **결정자**: 신호정 (TL) 제안. 팀 합의 대기
- **관련**: [도메인_모델.md](../기술문서/도메인_모델.md) 7절 (INV-2, INV-3), 기획서 5.1, 11.1, 11.2

두 규칙을 **세션 상태 기계의 전이 가드**로 강제합니다. 이 결정이 지키는 것은 둘입니다:
세션당 비용의 상한과, 확정이라는 단계의 의미.

## 배경

이 서비스에서 비용은 한 곳에 몰려 있습니다. 텍스트 호출은 저렴하고 반복해도 부담이 적지만,
**최종 이미지 생성 한 번이 세션 비용의 대부분**입니다 (기획서 11.1).

기획서 11.2는 사용량 상한(세션당 요청 상한, 하루 총량, 공개 주소 접근 제한)을 **지금 정하지
않기로** 했습니다. 개발과 검증 단계에서는 팀 내부만 사용하므로 남용 위험이 낮고, 실측 없이
숫자를 정하면 근거 없는 값이 되기 때문입니다. 그 대신 "그림 생성이 구조적으로 1회로 묶여
있다는 점이 사실상의 비용 방어선"이라고 적어 두었습니다.

즉 **유일한 비용 방어선이 구조**인데, 그 구조를 무엇이 보장하는지는 정해지지 않았습니다.
같은 문제가 기획서 5.1의 "확정 후 재생성 없음"에도 걸립니다 -- 확정 이후 시안을 고치고 다시
렌더할 수 있다면 확정이라는 단계 자체가 의미를 잃습니다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. **상태 기계로 강제** | 방어선이 코드에 있음. 우회하려면 상태 전이를 고쳐야 하므로 리뷰에 반드시 걸림 | 렌더 실패 후 재시도까지 같은 가드에 막힘. 예외 경로를 명시적으로 설계해야 함 |
| B. 요청 상한 / 쿼터 | 사용자 단위 총량을 막을 수 있음 | 기획서 11.2가 지금 정하지 않기로 한 사안. 실측 전에는 숫자가 근거 없음. 세션 하나 안에서의 중복 렌더는 못 막음 |
| C. 규약과 리뷰로만 | 구현 비용 없음 | 강제가 아님. "문서에 적혀 있었다"는 사고 후에 확인됩니다 |
| D. 과금으로 흡수 | 비용이 사용자에게 전가됨 | 결제는 범위 밖 (기획서 7.4, 구현_범위 3절) |

## 결정

**A를 택합니다.** 두 규칙을 세션 상태 기계의 전이 가드로 구현합니다.

| 규칙 | 구현 | 위반 시 |
|---|---|---|
| INV-2 `finalized` 이후 `draft` 변경 불가 | patch 처리 전 상태 확인 | 409 `STATE_CONFLICT` |
| INV-3 `render`는 세션당 1회 | `finalize` 시 `jobId` 존재 여부 확인 | 409 `STATE_CONFLICT` |

브리프는 이 ADR의 대상이 아닙니다. `finalized`보다 이른 `draft_generating` 시점에 잠기며
(INV-7), 그것은 확정의 의미가 아니라 **시안의 근거를 고정하는** 별개의 결정입니다.

B를 택하지 않은 이유는 **막는 지점이 다르기** 때문입니다. 쿼터는 "이 사용자가 오늘 몇 번"을
막고, 이 결정은 "이 세션에서 두 번"을 막습니다. 앞의 것은 기획서가 미룬 사안이고, 뒤의 것은
기획서가 이미 방어선이라고 부른 것입니다. 배포 단계에서 쿼터를 도입하더라도 이 가드는 남습니다 --
두 층은 대체 관계가 아닙니다.

C를 택하지 않은 이유는 이 규칙이 **깨져도 즉시 드러나지 않기** 때문입니다. 중복 렌더는 오류가
아니라 정상 응답으로 보이고, 청구서가 도착할 때까지 아무도 모릅니다.

## 결과

**생기는 제약**

- 세션 상태는 서버가 보관해야 합니다. 상태가 없으면 "이미 확정했는가"를 판정할 수 없습니다
  ([세션_보관_정책.md](../기술문서/세션_보관_정책.md) 3절).
- 409 `STATE_CONFLICT`가 계약에 명시되어야 합니다. 클라이언트가 이 응답을 모르면 사용자에게
  "실패했다"고만 보여 주게 됩니다 ([API_계약.md](../기술문서/API_계약.md) 5절).
- INV-2와 INV-3에는 각각 테스트가 있어야 하며, 테스트 이름에 `INV-2` / `INV-3`을 답니다.
- 재생성 기능(기획서 7.4)은 이 가드를 고치지 않으면 구현할 수 없습니다. **그것이 목적입니다** --
  2차 고도화로 넘긴 기능이 조용히 되살아나는 것을 막습니다.

**어려워지는 것**

- **렌더 실패 후 재시도가 같은 가드에 걸립니다.** 결과가 마음에 들지 않아 다시 만드는 것과,
  결과가 아예 없어서 다시 시도하는 것은 다른 일입니다. 후자까지 막으면 API 장애 한 번에 세션이
  버려집니다. 잠정안은 **실패 시 1회 재시도 허용**이며, 확정은 기획서 18.2 #13입니다.
- 사용자가 오타를 발견해도 고칠 수 없습니다. 이것은 이 결정의 부작용이 아니라 기획서 10.3이
  이미 받아들인 제약입니다.

**쉬워지는 것**

- 세션당 최대 비용이 상한을 가집니다. 비용 예측이 사용량 통계가 아니라 산술이 됩니다.
- 사용량 상한 로직 없이도 개발 단계를 버틸 수 있습니다 (기획서 11.2의 판단이 성립합니다).

**재검토 신호**

- 기획서 18.2 #13(확정 후 재생성 지원)이 "지원함"으로 결정될 때. 이 ADR을 고치지 말고 새 ADR을
  쓰고 `Superseded by`로 연결하세요.
- 렌더 실패율이 높아 재시도 요구가 반복될 때. 예외 경로의 범위를 다시 정해야 합니다.
- 배포 단계에서 사용량 상한을 도입할 때 (기획서 17.2). 그때 두 층의 책임 경계를 명확히 하세요 --
  쿼터가 생겼다고 이 가드를 지우면 세션 내 중복이 다시 열립니다.
