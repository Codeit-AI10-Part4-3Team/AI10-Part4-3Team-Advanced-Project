# ADR-0015: 렌더 워커는 같은 프로세스의 배경 작업으로 돌리고, 직렬은 저장소가 강제합니다

- **상태**: Proposed
- **날짜**: 2026-08-14
- **결정자**: 임동규 (05 백엔드/인프라). 합의 대기: 신호정 (02 TL), 정승호 (01 PM)
- **관련**: [ADR-0010](0010-상태_저장소와_파일_보관_위치.md),
  [ADR-0011](0011-배포_환경_스펙과_권한_경계.md),
  [ADR-0014](0014-상태_파일은_이름_있는_볼륨에_둔다.md),
  [도메인_모델.md](../기술문서/도메인_모델.md) 7절 INV-3,
  [API_계약.md](../기술문서/API_계약.md) 2.1절과 2.2절,
  [세션_보관_정책.md](../기술문서/세션_보관_정책.md) 2절

## 배경

S6 에서 `POST /v1/sessions/{sessionId}/finalize` 가 잡을 접수하고 `GET /v1/jobs/{jobId}` 가
상태를 돌려주는 데까지 왔습니다. **그런데 잡을 실제로 실행하는 것이 없습니다.** 접수된 잡은
`queued` 에 머물고, 세션은 `rendering` 에서 더 가지 않습니다. `rendering -> completed` 전이는
아직 한 번도 실행된 적이 없습니다.

이미 정해져 있어 우리가 고를 수 없는 것이 넷입니다.

- **GPU 는 한 대입니다** ([AGENTS.md](../../AGENTS.md) 설계 제약). 렌더 둘이 동시에 VRAM 을
  요구하면 둘 다 OOM 입니다. 동시 실행은 성능 선택이 아니라 고장입니다.
- **워커는 한 개입니다** ([API_계약.md](../기술문서/API_계약.md) 2.2절). 프로세스를 늘리는
  선택지 자체가 없습니다.
- **배포는 `git pull` + `docker compose up` 이고 별도 기동 단계가 없습니다**
  ([ADR-0011](0011-배포_환경_스펙과_권한_경계.md)).
- **상태는 SQLite 파일 하나** ([ADR-0010](0010-상태_저장소와_파일_보관_위치.md)), 이미지는 같은
  볼륨 ([ADR-0014](0014-상태_파일은_이름_있는_볼륨에_둔다.md)).

INV-3(렌더는 세션당 1회)은 비용 방어선이고, 그것을 지키는 것이 이 결정의 목적입니다.

## 선택지

| 안 | 무엇 | 장점 | 단점 |
|---|---|---|---|
| **A. 같은 프로세스의 배경 작업** | FastAPI 기동 시 배경 태스크 하나를 띄우고 큐를 폴링 | 새 배포 단위가 없음. compose 파일이 그대로. 상태를 공유하므로 붙는 곳이 없음 | 렌더가 앱과 생사를 같이함. 앱을 재시작하면 실행 중이던 잡이 끊김 |
| B. 별도 컨테이너 | 워커를 두 번째 서비스로 | 앱 재시작과 무관. 자원 격리 | compose 에 서비스가 하나 늘고, 같은 SQLite 파일을 두 프로세스가 엽니다 - ADR-0010 이 한 워커를 전제로 수락된 결정이라 그것부터 다시 열어야 함 |
| C. 잡 큐 미들웨어 (Redis 등) | 큐를 외부에 | 표준적인 형태 | 컨테이너와 운영 대상이 하나 늘고, 큐잉 대상이 하루 수십 건입니다. 얻는 것이 없음 |
| D. 접수 즉시 동기 렌더 | 잡 없이 finalize 에서 바로 | 가장 단순 | **계약 위반입니다.** 이미지 한 장에 수 분이라 요청을 붙들면 타임아웃이 먼저 옵니다 (API_계약 2.1절). 잡과 폴링 경로가 존재하는 이유가 이것입니다 |

## 결정

**A 를 택합니다.** 렌더 워커는 backend 프로세스 안의 배경 작업 하나이며, `lifespan` 에서
시작해 `lifespan` 에서 멈춥니다.

**직렬 실행은 워커가 아니라 저장소가 강제합니다.** `jobs.next_queued` 가 `running` 인 잡이
하나라도 있으면 `None` 을 돌려줍니다. 규칙을 워커 안의 루프에 두면 워커가 둘이 되는 순간
조용히 사라지지만, 조회 자체가 거부하면 워커가 몇 개든 동시에 두 건이 돌지 않습니다.

**잡은 접수와 실행이 분리됩니다.** `finalize` 는 행을 넣고 즉시 202 를 돌려주며, 워커가
그것을 나중에 집습니다. 접수와 실행이 같은 요청 안에 있으면 D 와 같아집니다.

## 결과

### 생기는 제약

- **앱을 재시작하면 실행 중이던 잡이 끊깁니다.** `running` 인 채로 남고 아무도 그것을 잇지
  않습니다. 기동 시 `running` 을 `queued` 로 되돌리는 처리가 필요하며, 그것은 **잡이
  멱등해야 한다는 뜻**입니다 - 같은 잡을 두 번 렌더해도 결과가 하나여야 합니다. 이미지
  파일명이 `jobId` 기준이면 두 번째가 첫 번째를 덮어쓰므로 성립합니다.
- **INV-3 이 두 층에서 지켜집니다.** 세션 쪽은 상태 기계와 조건부 UPDATE 가, 잡 쪽은
  `next_queued` 의 직렬 규칙이 막습니다. 둘 중 하나만 있으면 부족합니다 - 상태 기계만으로는
  동시 요청 둘이 함께 통과하고(2026-08-14 실측), 직렬 규칙만으로는 한 세션이 잡을 두 개
  만드는 것을 못 막습니다.
- **렌더 실패는 잡의 실패이지 조회의 실패가 아닙니다.** `GET /v1/jobs/{jobId}` 는 200 을
  유지하고 사유는 `error.code` 에 담습니다 (API_계약 2.1절).
- **결과 이미지의 보존은 7일입니다** ([세션_보관_정책.md](../기술문서/세션_보관_정책.md) 2절).
  `JobResult.expiresAt` 이 그 값을 담으며, 실제로 지우는 것은 08-25 의 정리 배치입니다.

### 쉬워지는 것

- compose 파일이 그대로입니다. 배포 절차가 늘지 않습니다.
- 워커가 상태를 앱과 공유하므로 둘 사이에 붙일 것이 없습니다.
- 로컬에서 스택 전체가 `uvicorn` 한 번으로 뜹니다.

### 어려워지는 것

- 렌더가 앱의 CPU 와 메모리를 함께 씁니다. 지금은 렌더가 외부 API 호출이라 대기가 대부분이고,
  **이번 범위에서는 그대로 갑니다** - 이 항목을 다시 열 신호였던 로컬 모델 채택이 2026-08-20 에
  미채택으로 닫혔습니다 (아래 재검토 신호).
- 워커 로그와 요청 로그가 한 스트림에 섞입니다.

### 재검토 신호

- ~~**로컬 모델을 채택하는 경우**~~ (미결정 대장 A-5). **2026-08-20 에 미채택으로 닫혀 이
  신호는 이번 범위에서 발생하지 않습니다**
  ([회의록](../회의록/2026-08-20_검증4순위_로컬모델_미채택.md)). 되살아나려면 A-5 확정을 뒤집는
  새 회의록이 먼저입니다. 그때의 판단은 전과 같습니다 - 렌더가 같은 프로세스에서 VRAM 을 잡으면
  앱의 응답성이 함께 떨어지므로 B 로 옮기되 ADR-0010 을 함께 엽니다.
  - **남은 신호 둘이 이 결정의 실질적인 재검토 조건입니다.** 아래 둘은 외부 API 를 쓰는 지금
    구성에서도 그대로 발생할 수 있습니다.
- 렌더 대기열이 실제로 밀리는 것이 관측되는 경우. 지금은 하루 수십 건 규모의 가정입니다.
- 앱 재시작이 잦아 끊긴 잡이 문제가 되는 경우.
