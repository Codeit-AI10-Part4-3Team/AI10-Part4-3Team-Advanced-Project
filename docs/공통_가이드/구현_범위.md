# 구현 범위

**무엇을 만들지**보다 **무엇을 만들지 않을지**가 더 중요한 문서입니다. 짧은 프로젝트에서
범위가 조용히 늘어나는 것이 가장 흔한 실패 원인입니다.

> ⚠️ **세부 범위는 2026-08-04 착수 회의에서 확정합니다.** 아래는 과제 요구사항
> ("모델 서빙 → 클라우드 배포까지 전 과정")에서 직접 도출되는 최소 골격이며, 확정 전까지
> 각 행의 DoD와 소관은 `TBD`입니다. **이 문서가 확정되기 전에 기능 코드를 쓰지 마세요** —
> 되돌리는 비용이 22일짜리 일정에서 가장 비쌉니다.

## 이번 범위에 **넣지 않는 것** (의도적 제외)

명시적으로 적어 두지 않으면 "당연히 해야 하는 것"으로 되살아납니다.

| 항목 | 왜 제외했나 | 다시 검토할 시점 |
|---|---|---|
| 다중 브랜드 동시 지원 | 어댑터 스위칭·격리가 새 문제 영역. 한 브랜드로 파이프라인을 먼저 증명 | 1브랜드 배포가 안정된 뒤 |
| 사용자 계정·결제 | 과제 목표(서빙~배포)와 무관한 순수 CRUD. 시간만 소모 | 범위 밖 |
| 스케일아웃 (다중 GPU/노드) | VM 1대가 전제. 큐·워커 추상화만 남기고 실제 확장은 하지 않음 | 범위 밖 |
| 동영상·GIF 광고 | 이미지가 안정되기 전에 손대면 둘 다 미완성 | 이미지 지표 실측 후 |
| 실시간 협업 편집 | 프론트 복잡도가 프로젝트 전체를 삼킴 | 범위 밖 |
| A/B 성과 측정(실제 광고 집행) | 외부 광고 플랫폼 연동이 필요. 검증 불가 | 범위 밖 |
| 모델 자체 사전학습 | 파인튜닝이 과제 요구사항. 사전학습은 자원상 불가능 | 범위 밖 |

## 범위를 바꿀 때

- 범위 추가는 **무언가를 빼는 것과 함께** 제안하세요. 일정은 고정되어 있습니다
  (2026-08-04 ~ 2026-08-31, 실작업 22일).
- 아키텍처에 영향을 주는 범위 변경은 [docs/adr/](../adr/)에 ADR로 남깁니다.
- **일정이 밀리면 품질 게이트가 아니라 범위를 줄입니다.** CI·가드레일·테스트를 끄는 것은
  일정 대응이 아니라 측정 포기입니다.
