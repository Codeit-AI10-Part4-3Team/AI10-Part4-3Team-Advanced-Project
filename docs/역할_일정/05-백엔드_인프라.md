## 진행 기록

### 08-12 루프백 바인딩 — 부분 충족, 나머지는 배포 시점으로 보류 (임동규)

확인된 것 둘입니다.

- `infra/docker-compose.yml`이 이미 `"127.0.0.1:8100:8100"`으로 바인딩하고 있습니다. 새로 짤
  것은 없고, 선언대로 동작하는지 확인하는 것이 이 작업의 내용입니다.
- **8100을 여는 방화벽 규칙이 0건**입니다 (`--filter="allowed[].ports~8100"`).
  기록: [infra/README.md](../../infra/README.md) 권한 경계 표.

**DoD의 "외부에서 8100 접근 불가 확인"은 보류합니다.** 밖에서 8000과 8100을 함께 재면 지금은
둘 다 닫혀 있고, 그 상태로는 **"막혀서 실패"와 "안 떠 있어서 실패"가 구분되지 않습니다**
(SSH 22번은 열려 있어 VM 도달 자체는 확인됨). 대조군인 8000이 살아 있어야 판정이 서므로,
스택을 VM에 올리는 시점에 8000 열림 + 8100 닫힘을 함께 확인해 닫습니다.

⚠️ **그 배포 날짜에 문서가 어긋나 있습니다.** [착수_체크리스트.md](../공통_가이드/착수_체크리스트.md) 5-a와
`infra/README.md`는 "W2 중"(08-12 ~ 08-14), 이 문서와 [00-overall.md](00-overall.md)는 **08-20**
입니다. 즉 **08-12 항목의 DoD가 08-20 작업을 전제**하고 있습니다. 어느 쪽이 맞는지는 회의록으로
정합니다 (기획서 14.3).

**2026-08-13 회의록으로 절반이 정해졌습니다**
([회의록](../회의록/2026-08-13_워킹스켈레톤_일정_조정.md) 정정 절).

### 08-13 S0 로그인 — 인증 경로는 닫힘, INV-9 의 404 는 S2 로 넘어감 (임동규)

닫힌 것: 고정 계정 둘 시드, 아이디 조회 + 비밀번호 대조, 세션 쿠키 발급과 폐기,
미인증 401, 계약의 auth 경로 6개(구현 3 + 501 3). 계약과 실제 서빙 경로를 대조해
양쪽 차집합이 0 인 것을 확인했습니다.

**DoD 의 "남의 세션 404 (INV-9)" 는 S0 만으로 닫을 수 없습니다.** 404 를 낼 대상인 세션
리소스가 S2 소관이기 때문입니다. S0 에서 닫은 것은 그 앞 절반 - 요청이 소유자로 해석되고,
소유자 없는 요청은 401 이 되는 것 - 이며, 두 계정이 서로 다른 `userId` 를 받는지(404 경로의
전제)까지 테스트로 걸어 두었습니다. **이 항목은 S2 에서 함께 닫습니다.**

> **해소 (2026-08-14, 표기는 08-19).** S2 와 함께 들어왔습니다.
> `test_inv_9_someone_elses_session_is_404_not_403` 이 남의 세션과 없는 id 의 **응답 본문이
> 같은지**까지 봅니다 - 404 만 맞고 본문이 다르면 id 존재 여부가 그대로 새기 때문입니다.
> 단언은 `assert mine.json() == invented.json()` 이라 파싱된 객체 비교이며, 키 순서나 공백은
> 보지 않습니다.
> `test_inv_9_the_list_only_shows_your_own` 이 목록 쪽을 함께 막습니다.

새로 생긴 결정 둘을 ADR 로 남겼습니다:
[ADR-0013](../adr/0013-로그인_토큰_형식과_폐기_정책.md) 토큰 형식과 폐기 정책,
[ADR-0014](../adr/0014-상태_파일은_이름_있는_볼륨에_둔다.md) 상태 파일의 볼륨.

⚠️ **로그인을 브라우저로 쓰려면 HTTPS 가 먼저 필요합니다.** 세션 쿠키가 계약대로 `Secure` 를
달기 때문에, 평문 HTTP 로 배포하면 브라우저가 쿠키를 버려 로그인이 성립하지 않습니다. 상세는
[API_계약.md](../기술문서/API_계약.md) 8.3절입니다.
**08-14 의 "VM에 스택 1회 배포"는 이것에 막히지 않습니다** — 그 항목의 DoD 는 "빈 스택이어도
충족"이라 로그인 동작을 요구하지 않습니다. 막히는 것은 그 위에서 화면이 붙는 시점이고,
HTTPS 는 그 전까지 닫으면 됩니다.

### 08-14 S2 ~ S8 — 관통 경로가 끝까지 이어짐 (임동규)

계약의 21개 경로 중 서빙되지 않는 것이 0개입니다. 세션이 `created` → `brief_ready` →
`draft_ready` → `rendering` → `completed` 까지 **계약만 밟고** 갑니다 (도메인을 직접 건드리는
지름길 없이 라우트만으로 밟는 테스트가 있습니다).

**렌더 워커까지 넣어 S2 와 S6 을 닫았습니다.** 그 전까지 `rendering` → `completed` 전이는
한 번도 실행된 적이 없었습니다. 결정은 [ADR-0015](../adr/0015-렌더_워커는_같은_프로세스의_배경_작업으로_돌린다.md)
로 남겼고 요지는 셋입니다.

- **워커는 backend 프로세스 안의 배경 작업**입니다. 별도 컨테이너를 두면 같은 SQLite 파일을
  두 프로세스가 열게 되는데, [ADR-0010](../adr/0010-상태_저장소와_파일_보관_위치.md)이 한
  워커를 전제로 수락된 결정이라 그것부터 다시 열어야 합니다.
- **직렬 실행은 워커가 아니라 저장소가 강제합니다.** `jobs.next_queued` 가 `running` 인 잡이
  있으면 아무것도 돌려주지 않습니다. GPU 가 한 대라 동시 실행은 성능 선택이 아니라 둘 다
  OOM 이고, 규칙을 워커 루프에 두면 워커가 둘이 되는 순간 조용히 사라집니다.
- **기동 시 `running` 인 잡을 `queued` 로 되돌립니다.** 그러지 않으면 배포 한 번에 세션이
  `rendering` 에 영원히 갇힙니다 — `rendering` 에는 되돌아오는 간선이 없습니다. 재시도가
  안전한 이유는 결과 파일이 **잡 id** 로 이름 지어져 두 번째 시도가 첫 번째를 덮어쓰기
  때문입니다.

**자체 검토에서 결함 4건이 나와 같이 고쳤습니다.** 넷 다 테스트가 초록인 채로 숨어 있었습니다:

1. **INV-7 이 뚫려 있었습니다.** 브리프 patch 가 목표 상태를 "지금 자리"로 골랐는데
   `draft_ready → draft_ready` 가 정상 간선이라(시안 patch 반복) 가드가 아무것도 막지
   못했습니다. 브리프를 **미완성으로 만드는** patch 를 시안이 있는 세션에 보내면 200 이
   나오고 시안의 근거가 덮어써졌습니다. 기존 테스트는 완성된 patch 만 보내 이 구멍을
   지나쳤습니다.
2. **빈 patch(`{}`)가 통과했습니다.** 계약의 `minProperties: 1` 이 스키마에 없었습니다.
   아무것도 안 바꾸면서 `revision` 만 올려, 다른 화면들의 낙관적 잠금을 이유 없이 깹니다.
3. **컨테이너에서 사진 업로드가 죽습니다.** `ADGEN_IMAGE_DIR` 기본값이 상대 경로라
   root 소유인 `/app` 아래로 풀립니다. 아침에 `ADGEN_DB_PATH` 로 겪은 것과 같은 함정인데
   **증상이 기동이 아니라 첫 업로드**라 `/health` 도 CI 스모크도 초록입니다.
4. **짧은 변 512px 검사가 없었습니다.** [미결정_대장](../기술문서/미결정_대장.md) N3 의
   확정 사항인데 구현이 빠져 있었습니다.

3번은 CI 가 구조적으로 못 잡는 종류라 "쓰기 경로는 전부 Dockerfile 과 compose 양쪽에서
`/data` 를 가리켜야 한다"를 테스트로 만들어 두었습니다
(`tests/test_container_state_paths.py`). 다음에 쓰기 경로가 하나 더 생길 때 걸립니다.

> 들어갔습니다 ([API_계약.md](../기술문서/API_계약.md) 8.4절). 값은 앱 상대 경로입니다.

### 08-19 HTTPS 종단 — 프록시를 앞에 한 겹 얹었습니다 (임동규)

08-18 배포에서 **로그인은 되는데 새로고침하면 로그인 화면으로 돌아오는** 증상이 나왔습니다.
코드 결함이 아니라 앞단 문제입니다 — 세션 쿠키가 계약대로 `Secure` 를 달고 있어 브라우저가
평문 HTTP 응답에서 그것을 저장하지 않습니다. 화면이 잠깐 로그인 상태로 보이는 것은
`AuthProvider.signIn` 이 쿠키가 아니라 응답 본문으로 상태를 정하기 때문이고, 마운트 시점의
`GET /v1/me` 가 401 을 받아 진짜 상태가 드러납니다. **위 08-13 기록이 예고한 그대로입니다.**

방식은 [ADR-0016](../adr/0016-HTTPS_종단_지점과_인증서_발급_경로.md) 으로 정했습니다. Caddy 를
프론트엔드 nginx **앞에** 한 겹 얹어 거기서 TLS 를 종단하고, 인증서는 빌려온 이름으로 Let's
Encrypt 에서 자동 발급받습니다. 06 의 `nginx.conf` 는 건드리지 않았습니다.

| 확인한 것 (2026-08-19, 로컬 스택) | 결과 |
|---|---|
| `ADGEN_PUBLIC_HOST` 세 상태(미설정 / `:80` / 호스트명)의 설정 유효성 | 전부 통과. 호스트명일 때 자동 HTTPS 와 HTTP -> HTTPS 리다이렉트가 켜짐 |
| 컨테이너 4개 기동과 헬스체크 | 전부 healthy |
| 프록시 경유 `/`, `/login`(SPA 폴백), `/health`, `/v1/me` | 200 / 200 / 200 / 401 (미인증이므로 정상) |
| 로그인 -> `/v1/me` 왕복 | 200. `Set-Cookie` 의 `Secure` + `SameSite=lax` 가 프록시를 지나며 그대로 보존됨 |
| 호스트에서 backend `8000` | 루프백에만 발행 - 로컬에서는 닿고 밖에서는 닿지 않습니다 |
| `e2e/` 하네스 | 3 passed |

**VM 반영까지 끝났습니다 (2026-08-19).** 머지 전에 브랜치를 `--ref` 로 올려 확인했습니다.

| 확인한 것 | 결과 |
|---|---|
| Let's Encrypt 발급 | 성공. production 엔드포인트, 공유 한도에 걸리지 않았습니다 |
| **브라우저 새로고침 후 로그인 유지** | **유지됩니다.** 08-18 에 발견한 증상이 사라졌습니다 |
| 갱신 시점 | 2026-10-17. 제출일보다 47일 뒤이므로 프로젝트 안에서 갱신이 일어나지 않습니다 |

**예상 하나가 틀렸습니다.** 문서 네 곳이 "80 을 닫으면 안 되는 이유는 인증서 발급 검증이 그
포트로 들어오기 때문" 이라고 적고 있었는데, 실제 첫 발급은 `tls-alpn-01` 챌린지로 끝나 443 만
쓰였습니다. 결론(80 을 열어 둔다)은 그대로지만 근거가 달라 함께 고쳤습니다 - 틀린 이유를
남겨 두면 다음 사람이 "80 을 닫아도 발급이 되네" 를 근거로 리다이렉트까지 지웁니다.

방화벽은 손댈 것이 없었습니다. 443 은 08-19 실측에서 이미 열려 있는 것으로 확인됐습니다.

### 08-19 미결로 남아 있던 넷을 실측으로 닫습니다 (임동규)

넷 다 **실제로는 충족돼 있었는데 표에만 대기로 남아 있던** 것입니다. 판정에 필요한 조건이
그동안 갖춰졌기 때문이며(대부분 VM 배포), 근거를 남기지 않고 상태만 바꾸면 다음 사람이 다시
재게 되므로 잰 값을 함께 적습니다.

#### 1. 루프백 바인딩 - 보류했던 판정을 냈습니다

08-12 기록이 보류한 이유는 "막혀서 실패"와 "안 떠 있어서 실패"가 구분되지 않는다는 것이었고,
대조군인 8000이 살아나기를 기다리고 있었습니다. 배포가 끝나 조건이 갖춰졌습니다.

**관측 지점은 VM 밖(개발자 노트북)이고, 시각은 HTTPS 종단이 배포되기 전입니다.** 아래
"08-19 HTTPS 종단" 기록의 8000 서술과 값이 다른 이유가 그것이라 먼저 적어 둡니다.

| 포트 | 결과 (VM 밖에서, HTTPS 배포 전) | 읽는 법 |
|---|---|---|
| 80 | 연결됨 (0.2초) | 스택이 떠 있습니다 |
| 8000 | 연결됨 (0.2초) | **대조군.** VM 까지 도달하는 경로가 살아 있습니다 |
| 8100 | 타임아웃 (8.0초) | 거부가 아니라 타임아웃 - 방화벽이 패킷을 조용히 버립니다 |

재현한 명령입니다. 파이썬 소켓을 쓴 것은 `curl` 이 타임아웃과 거부를 같은 종료 코드로
돌려주어 **둘을 구분할 수 없기** 때문이고, 이 판정은 그 구분이 전부입니다.

```python
s = socket.socket(); s.settimeout(8)
try: s.connect((IP, port))          # 연결됨
except socket.timeout: ...          # 방화벽이 버림
except OSError: ...                 # 거부 - 방화벽은 통과, 듣는 쪽이 없음
```

`8.0초` 는 관측치가 아니라 위 `settimeout(8)` 에 걸린 값입니다. 그보다 오래 기다리면 더
길어졌을 뿐이고, 판정에 쓰는 것은 시간이 아니라 **어느 예외로 끝났는가**입니다.

**거부와 타임아웃의 구분이 판정의 전부입니다.** 8000 이 즉시 붙는데 8100 만 8초를 기다리다
끊긴다면, 원인은 "안 떠 있음"이 아니라 "닿지 못함"입니다.

**이 측정은 다시 할 수 없습니다.** 같은 날 늦게
[ADR-0016](../adr/0016-HTTPS_종단_지점과_인증서_발급_경로.md) 이 배포되면서 8000 이 루프백
바인딩으로 바뀌어(`infra/docker-compose.yml` 의 `127.0.0.1:8000:8000`) 대조군이 사라졌습니다.
위 표의 판정은 8000 이 "연결됨" 이어야 성립하므로, **재현 불가입니다.**

배포 뒤에 같은 자리에서 다시 쟀습니다.

| 포트 | 결과 (VM 밖에서, HTTPS 배포 후) | 읽는 법 |
|---|---|---|
| 80 | 연결됨 | HTTPS 리다이렉트 |
| 443 | 연결됨 | **HTTPS 가 살아 있습니다** |
| 8000 | 거부 | 방화벽은 통과했는데 듣는 쪽이 없습니다 - 루프백 바인딩이 동작합니다 |
| 8100 | 타임아웃 | 방화벽이 패킷을 버립니다 (변동 없음) |

**8000 의 "거부" 가 루프백 바인딩의 직접 증거입니다.** 이 VM 의 8000 은 우리가 만들지 않은
태그 없는 규칙으로 방화벽이 열려 있는데도 연결이 거부되었으므로, 컨테이너가 외부 인터페이스에
붙어 있지 않다는 뜻입니다. 8100 은 방화벽이 먼저 막아 같은 방식으로는 구분되지 않습니다 -
아래 "바인딩 자체" 를 따로 적어 두는 이유입니다.

아래 "08-19 HTTPS 종단" 기록의 8000 서술은 **이 시점 이후의 값**입니다.

##### 바인딩 자체 - DoD 의 나머지 절반

위까지는 "밖에서 닿지 않는가" 만 잰 것이고, DoD 는 조건이 둘입니다. **`127.0.0.1:8100:8100`**
과 **외부에서 8100 접근 불가**. 밖에서 재는 것으로는 앞쪽이 확인되지 않습니다 - 컨테이너가
`0.0.0.0:8100` 에 붙어 있어도 방화벽이 막으면 똑같이 타임아웃이기 때문입니다. 두 상태가
구분되지 않는 것이고, 그 차이는 우리가 만들지 않은 방화벽 규칙이 하나 바뀌는 날 드러납니다.

그래서 VM 안에서 **실제로 도는 컨테이너의 바인딩**을 따로 확인했습니다.

```
$ docker compose -f infra/docker-compose.yml ps --format 'table {{.Service}}\t{{.Ports}}'
SERVICE     PORTS
ai-engine   127.0.0.1:8100->8100/tcp
backend     127.0.0.1:8000->8000/tcp
caddy       0.0.0.0:80->80/tcp, [::]:80->80/tcp, 0.0.0.0:443->443/tcp, [::]:443->443/tcp, 443/udp, 2019/tcp
frontend    80/tcp
```

**선언이 아니라 런타임 값입니다.** compose 파일에 `127.0.0.1:` 이 적혀 있는 것과 그렇게 떠
있는 것은 다른 주장이고, 이 출력이 뒤쪽입니다. 이로써 DoD 두 조건이 모두 확인됐습니다.

함께 읽히는 것 셋입니다.

- `frontend` 와 `caddy` 의 `443/udp` `2019/tcp` 에는 호스트 바인딩이 없습니다. 프론트엔드는
  프록시 뒤로 들어갔고, HTTP/3 용 UDP 와 Caddy 관리 엔드포인트는 발행하지 않았습니다
  ([ADR-0016](../adr/0016-HTTPS_종단_지점과_인증서_발급_경로.md)).
- `caddy` 만 `0.0.0.0` 입니다. 밖에서 보이는 문이 하나라는 뜻입니다.
- 이 확인은 **앞으로도 재현 가능합니다.** 밖에서 재는 쪽과 달리 대조군이 필요 없습니다.

#### 2. `brief:fill` 열화 - 실물을 끄고 확인했습니다

구현은 S2 에 이미 들어와 있었고 단위 테스트도 있었습니다. 다만 그 테스트는 **가짜 엔진**이라
DoD 의 "ai-engine 을 끈 상태에서"를 만족한다고 볼 수 없어, 컨테이너를 실제로 정지시키고
대조군과 함께 다시 쟀습니다.

| | 엔진 살아 있음 | **엔진 정지** | DoD |
|---|---|---|---|
| HTTP | 201 | **201** | 201 |
| `state` | `brief_ready` | **`brief_filling`** | `brief_filling` |
| `messageMode` | `normal` | **`degraded`** | `degraded` |
| `needsInput` | 없음 | 없음 | 열화와 정보 부족을 가르는 키 (없어야 정상) |

`category` 와 `target` 은 빈 문자열로 왔습니다 - 계약의 "`null` 금지"와 일치합니다.

소요는 4.06초였고, 여기서 말할 수 있는 것은 **상한 15초를 기다리지 않았다**는 것뿐입니다
(`brief_fill_timeout_s`). 잰 값은 `POST /v1/sessions` **요청 전체의 왕복**이라 600x600 PNG
업로드와 저장, 세션 생성이 모두 들어 있습니다. 이음매 호출만 따로 잰 것이 아니므로 "연결
거부가 즉시 돌아온다" 의 근거로는 쓸 수 없습니다 - 연결 거부 자체는 밀리초 단위입니다.

재현한 절차입니다. 대조군을 먼저 찍고 엔진을 내린 뒤 같은 요청을 반복합니다.

```bash
docker compose -f infra/docker-compose.yml stop ai-engine
# 로그인으로 받은 쿠키를 헤더로 실어 POST /v1/sessions (multipart)
#   outputType=single_ad, productName, sellingPoint, productImage=600x600 PNG
```

⚠️ 사진은 **짧은 변이 512px 이상**이어야 합니다. 계약이 그렇게 규정하고 있어 작은 이미지는
422 로 먼저 걸립니다. 그리고 쿠키는 헤더로 직접 실어야 합니다 - 아래 "덤" 참고.

**왜 코드를 읽는 것으로 충분하지 않은가.** `fill_brief` 는 `httpx.HTTPError` 를 통째로 잡아
열화로 보냅니다. 실제 연결 거부가 그 안에 드는지는 예외 계층을 믿는 것이지 잰 것이 아니고,
[AGENTS.md](../../AGENTS.md) 가 경계하는 "스텁을 실물로 착각" 이 정확히 이 자리입니다.

덤으로 확인된 것 하나: **httpx 가 `Secure` 쿠키를 평문 `http://localhost` 에 싣지 않습니다.**
첫 시도가 401 로 튕겨 쿠키를 헤더로 직접 실어야 했습니다. 브라우저와 같은 규칙이며,
**위 "08-19 HTTPS 종단" 기록이 브라우저에서 겪은 증상과 같은 원인입니다** - 그쪽은 사람이
새로고침해서 발견했고 이쪽은 테스트 클라이언트가 401 로 알려 준 것뿐입니다.

### 08-19 보존 기간 정리 배치 - 기간이 문서 밖으로 나왔습니다 (임동규)

08-25 항목을 당겨왔습니다. `brief:fill` 열화가 이미 충족돼 08-20 ~ 21 이 비었고, 08-26 에 세
항목이 몰려 있어 덜어낼 필요가 있었습니다.

**들어오기 전까지 이 정책은 글이었습니다.** 세션_보관_정책 2절이 "만료된 데이터는 삭제하는
코드가 있어야 합니다. 기간을 문서에만 적어 두면 아무것도 지워지지 않습니다" 라고 적어 두었는데,
그 코드가 없었습니다. 계약이 "만료된 사진은 빈 문자열" 이라고 약속하고
([API_계약.md](../기술문서/API_계약.md) 8.4절) 만료 자체가 일어나지 않던 상태입니다.

| 무엇 | 어디 |
|---|---|
| 무엇을 지우나 (순수 함수, 서버 없이 시험 가능) | `backend_core/retention.py` |
| 언제 도나 (같은 프로세스의 배경 작업, ADR-0015 와 같은 갈래) | `api/sweeper.py` |
| 기간과 주기 (정책이 "설정값" 이라고 못박은 것) | `ADGEN_RETENTION_*`, `ADGEN_SWEEP_*` |

#### 설계에서 걸린 것 하나

**세션 기한과 계약 약속이 어긋납니다.** 세션은 생성 후 7일, 결과 이미지는 `expiresAt` 까지인데,
6일째에 렌더한 세션은 7일째에 지워지면서 아직 6일이 남은 결과를 함께 가져갑니다. 잡이 사라지면
결과는 모두에게 404 이므로(INV-9), 우리가 공표한 시각보다 먼저 링크가 죽습니다.

**늦은 쪽을 따르기로 했습니다.** 세션은 자기 기한과 결과 약속 중 나중까지 남습니다. 기간표를
지키려다 계약을 어기는 것보다 낫다고 봤습니다 - 기간표는 우리끼리의 약속이고 `expiresAt` 은
이미 클라이언트에게 나간 값입니다.

#### 확인한 것

테스트 7개이고, **통과만으로는 아무것도 증명하지 않으므로** 위 규칙을 지우고 돌려 봤습니다.
`_deadline` 에서 결과 약속을 빼니 해당 테스트가 `assert 1 == 0` 으로 실패합니다.

- 사진: 23시간에는 남고 25시간에는 파일과 참조가 함께 사라집니다.
- **빈 문자열로 바꿔도 `revision` 과 `updated_at` 은 그대로입니다.** 배치는 사용자 편집이 아닙니다 -
  `revision` 이 움직이면 열려 있던 화면의 다음 patch 가 설명할 수 없는 충돌로 실패하고,
  `updated_at` 이 움직이면 새벽에 배치가 돌았다는 이유로 남의 세션 목록 순서가 바뀝니다.
- 세션: 8일째에 잡과 파일까지 함께 지워집니다.
- 두 번 돌려도 두 번째 패스는 아무것도 하지 않습니다(시작할 때 한 번 + 주기마다이므로 정상 상황).

**로그 30일은 이 배치의 대상이 아닙니다.** 표준 출력으로 나가 컨테이너 런타임이 들고 있고,
SQLite 안에 지울 로그 저장소가 없습니다. 회전은 배포 쪽 소관으로 남깁니다.

#### 리뷰가 잡아 준 것 (PR #132, 신호정)

재현까지 붙은 결함 둘이 나왔습니다. 둘 다 **이 배치가 막으려던 실패와 같은 종류**입니다.

- **렌더 중인 세션을 지우면 결과 파일이 영구 고아가 됩니다.** 아직 결과가 없는
  `queued` / `running` 잡은 기한 계산에 들어가지 않아, 배치가 세션과 잡 행을 지우고 워커가
  그 뒤에 파일을 씁니다. 그 파일을 가리키는 행이 없으니 **이후 어떤 패스도 수거하지
  못합니다** - 기간 없이 생성물을 쌓지 말라는 것이 이 배치의 존재 이유인데 배치 자신이 그
  경로가 됩니다. 미종료 잡이 있는 세션은 통째로 건너뛰도록 고쳤습니다. 다음 패스가 가져갑니다.
- **사진 비우기가 동시 편집을 덮어씁니다.** 배치는 패스 시작 시점에 전 세션을 읽고 한참 뒤에
  쓰는데, 그 사이 사용자가 저장하면 **200 을 받은 편집이 조용히 사라집니다.** `save` 가
  `Precondition` 을 필수로 둔 바로 그 창입니다. UPDATE 에 읽을 때의 `revision` 조건을 붙이고,
  0행이면 이번 패스를 건너뛰도록 했습니다.

**사진의 실제 보존이 최대 48시간이었습니다.** 만료 판정 24시간에 배치 주기 24시간이 더해지는데,
표는 24시간을 약속합니다. 기본 주기를 1시간으로 줄여 상한을 25시간으로 낮췄고, "이때부터 지워도
된다이지 이때 지워진다가 아니다" 를 정책 2절에 적었습니다. 한 패스가 수십 행을 훑는 일이라
주기를 줄이는 비용이 개인정보를 두 배로 오래 들고 있는 비용보다 훨씬 쌉니다.

**`RESULT_RETENTION` 만 설정값이 아니었던 것도 함께 고쳤습니다.** 후속으로 미뤄도 된다고
하셨지만 `run_one` 에 인자 하나를 더하는 일이라 지금 했습니다. 그대로 두면
`ADGEN_RETENTION_SESSION_D` 를 줄여도 렌더된 세션에는 효과가 없어(늦은 쪽을 따르므로) VM
실측에서 배치가 고장 난 것처럼 보였을 항목입니다.

회귀 테스트 4개를 더했고, 두 가드를 지워 보니 정확히 그 4개가 깨집니다.

**남은 것은 VM 실측입니다.** 주기가 1시간이라 배포된 스택에서 한 시간 안에 도는 것을 볼 수
있지만, 사진 만료를 보려면 기간을 줄여 한 번 확인하는 편이 빠릅니다.
