# packages/contracts

모듈 간 **계약의 단일 원천**입니다. `openapi.yaml` 하나가 backend의 공개 경로와 ai-engine의
내부 경로를 모두 기술합니다.

## 규칙

- **구현보다 계약이 먼저.** 모듈 사이 인터페이스는 여기에 먼저 존재하고, 그다음 코드에 생깁니다.
  구두 합의는 계약이 아닙니다 — 합의한 사람이 자리를 비우면 사라지기 때문입니다.
- **필드는 camelCase.** 파이썬 코드는 snake_case를 쓰고 pydantic alias로 매핑합니다.
  라우터에서 손으로 dict를 조립하기 시작하면 그 순간부터 스펙과 어긋납니다.
- **알 수 없는 필드는 거부**(`additionalProperties: false`). 오타 난 필드가 조용히 무시되면
  보낸 쪽은 보냈다고 믿고, 받는 쪽은 못 본 채로 동작합니다.
- **`null`은 계약 전체에서 금지.** "비어 있음"은 빈 문자열 `""`, "없음"은 키 생략입니다.
  요청에 `null`이 나타나면 422입니다. 이 도메인에는 "필드를 지운다"는 동작이 없고, 그 의미를
  열어 두면 자유 메모를 비우려던 요청이 필드 자체를 없애는 사고가 납니다. 근거와 네 뜻(값 있음 /
  비어 있음 / 해당 없음 / 아직 없음)을 두 표현으로 나눈 규칙:
  [API_계약.md](../../docs/기술문서/API_계약.md) 3절.

## 검증은 두 겹

| 무엇을 | 어디서 |
|---|---|
| 스펙 문법이 유효한가 | CI [`contracts-check.yml`](../../.github/workflows/contracts-check.yml) — `packages/contracts/*.yaml` 전량 |
| 구현이 스펙대로 응답하는가 | 각 앱의 계약 준수 테스트 (`apps/*/tests/test_service.py` 등) |

두 번째가 없으면 "문법은 맞지만 아무도 안 지키는 스펙"이 됩니다. 스펙을 고치는 PR에는 그
계약을 검사하는 테스트도 같이 들어가야 합니다.

예외는 **아직 구현이 없는 경로**입니다. 지금 이 스펙의 광고 생성 경로가 그렇습니다 -- 교체 순서가
계약 -> 스키마 -> 구현 -> 테스트라 계약만 앞서 있는 구간이며, 이 상태는 의도된 것입니다
([API_계약.md](../../docs/기술문서/API_계약.md) 7절의 구간 2). **CI가 이 드리프트를 잡아주지
않으므로** 진행 상황은 [구현_범위.md](../../docs/공통_가이드/구현_범위.md)의 항목으로 추적합니다.

## 스펙을 나눌 때

파일이 늘어나도 CI는 자동으로 따라옵니다(파일명을 하드코딩하지 않았습니다). 다만 이 디렉토리
밖으로 옮기면 검증 대상에서 조용히 빠지므로, 계약은 여기 두세요.
