## 진행 기록

### 08-12 루프백 바인딩 — 부분 충족, 나머지는 배포 시점으로 보류 (임동규)

확인된 것 둘입니다.

- `infra/docker-compose.yml`이 이미 `"127.0.0.1:8100:8100"`으로 바인딩하고 있습니다. 새로 짤
  것은 없고, 선언대로 동작하는지 확인하는 것이 이 작업의 내용입니다.
- **8100을 여는 방화벽 규칙이 0건**입니다 (`--filter="allowed[].ports~8100"`).
  기록: [infra/README.md](../../infra/README.md) 권한 경계 표.

**DoD의 "외부에서 8100 접근 불가 확인"은 보류합니다.** 밖에서 8000과 8100을 함께 재면 지금은
둘 다 닫혀 있고, 그 상태로는 **"막혀서 실패"와 "안 떠 있어서 실패"가 구분되지 않습니다**
(SSH 22번은 열려 있어 VM 도달 자체는 확인됨). 대조군인 8000이 살아 있어야 판정이 서므로,
스택을 VM에 올리는 시점에 8000 열림 + 8100 닫힘을 함께 확인해 닫습니다.

⚠️ **그 배포 날짜에 문서가 어긋나 있습니다.** [착수_체크리스트.md](../공통_가이드/착수_체크리스트.md) 5-a와
`infra/README.md`는 "W2 중"(08-12 ~ 08-14), 이 문서와 [00-overall.md](00-overall.md)는 **08-20**
입니다. 즉 **08-12 항목의 DoD가 08-20 작업을 전제**하고 있습니다. 어느 쪽이 맞는지는 회의록으로
정합니다 (기획서 14.3).

**2026-08-13 회의록으로 절반이 정해졌습니다**
([회의록](../회의록/2026-08-13_워킹스켈레톤_일정_조정.md) 정정 절).

- 정해진 것: 08-12에 끝난 것은 **VM 환경 설정**이고 **스택 배포는 미완료**입니다. 따라서 위
  보류 판단은 유효합니다 - 대조군인 8000이 아직 살아 있지 않습니다. 세 항목의 구분:
  [00-overall.md](00-overall.md) 5-a절.
- 남은 것이었던 **"W2 중"인지 08-20인지**는 **08-14로 맞췄습니다** (2026-08-13, TL 신호정).
  착수_체크리스트와 `infra/README.md`의 "W2 중"과 같은 값이 되어 세 문서가 어긋나지 않습니다.
  다만 이것은 **TL 초안**이고 확정 근거는 여전히 회의록입니다 ([00-overall.md](00-overall.md) 머리말).

### 08-13 S0 로그인 — 인증 경로는 닫힘, INV-9 의 404 는 S2 로 넘어감 (임동규)

닫힌 것: 고정 계정 둘 시드, 아이디 조회 + 비밀번호 대조, 세션 쿠키 발급과 폐기,
미인증 401, 계약의 auth 경로 6개(구현 3 + 501 3). 계약과 실제 서빙 경로를 대조해
양쪽 차집합이 0 인 것을 확인했습니다.

**DoD 의 "남의 세션 404 (INV-9)" 는 S0 만으로 닫을 수 없습니다.** 404 를 낼 대상인 세션
리소스가 S2 소관이기 때문입니다. S0 에서 닫은 것은 그 앞 절반 - 요청이 소유자로 해석되고,
소유자 없는 요청은 401 이 되는 것 - 이며, 두 계정이 서로 다른 `userId` 를 받는지(404 경로의
전제)까지 테스트로 걸어 두었습니다. **이 항목은 S2 에서 함께 닫습니다.**

새로 생긴 결정 둘을 ADR 로 남겼습니다:
[ADR-0013](../adr/0013-로그인_토큰_형식과_폐기_정책.md) 토큰 형식과 폐기 정책,
[ADR-0014](../adr/0014-상태_파일은_이름_있는_볼륨에_둔다.md) 상태 파일의 볼륨.

⚠️ **로그인을 브라우저로 쓰려면 HTTPS 가 먼저 필요합니다.** 세션 쿠키가 계약대로 `Secure` 를
달기 때문에, 평문 HTTP 로 배포하면 브라우저가 쿠키를 버려 로그인이 성립하지 않습니다. 상세는
[API_계약.md](../기술문서/API_계약.md) 8.3절입니다.
**08-14 의 "VM에 스택 1회 배포"는 이것에 막히지 않습니다** — 그 항목의 DoD 는 "빈 스택이어도
충족"이라 로그인 동작을 요구하지 않습니다. 막히는 것은 그 위에서 화면이 붙는 시점이고,
HTTPS 는 그 전까지 닫으면 됩니다.

### 08-14 S2 ~ S8 — 관통 경로가 끝까지 이어짐 (임동규)

계약의 21개 경로 중 서빙되지 않는 것이 0개입니다. 세션이 `created` → `brief_ready` →
`draft_ready` → `rendering` → `completed` 까지 **계약만 밟고** 갑니다 (도메인을 직접 건드리는
지름길 없이 라우트만으로 밟는 테스트가 있습니다).

**렌더 워커까지 넣어 S2 와 S6 을 닫았습니다.** 그 전까지 `rendering` → `completed` 전이는
한 번도 실행된 적이 없었습니다. 결정은 [ADR-0015](../adr/0015-렌더_워커는_같은_프로세스의_배경_작업으로_돌린다.md)
로 남겼고 요지는 셋입니다.

- **워커는 backend 프로세스 안의 배경 작업**입니다. 별도 컨테이너를 두면 같은 SQLite 파일을
  두 프로세스가 열게 되는데, [ADR-0010](../adr/0010-상태_저장소와_파일_보관_위치.md)이 한
  워커를 전제로 수락된 결정이라 그것부터 다시 열어야 합니다.
- **직렬 실행은 워커가 아니라 저장소가 강제합니다.** `jobs.next_queued` 가 `running` 인 잡이
  있으면 아무것도 돌려주지 않습니다. GPU 가 한 대라 동시 실행은 성능 선택이 아니라 둘 다
  OOM 이고, 규칙을 워커 루프에 두면 워커가 둘이 되는 순간 조용히 사라집니다.
- **기동 시 `running` 인 잡을 `queued` 로 되돌립니다.** 그러지 않으면 배포 한 번에 세션이
  `rendering` 에 영원히 갇힙니다 — `rendering` 에는 되돌아오는 간선이 없습니다. 재시도가
  안전한 이유는 결과 파일이 **잡 id** 로 이름 지어져 두 번째 시도가 첫 번째를 덮어쓰기
  때문입니다.

**자체 검토에서 결함 4건이 나와 같이 고쳤습니다.** 넷 다 테스트가 초록인 채로 숨어 있었습니다:

1. **INV-7 이 뚫려 있었습니다.** 브리프 patch 가 목표 상태를 "지금 자리"로 골랐는데
   `draft_ready → draft_ready` 가 정상 간선이라(시안 patch 반복) 가드가 아무것도 막지
   못했습니다. 브리프를 **미완성으로 만드는** patch 를 시안이 있는 세션에 보내면 200 이
   나오고 시안의 근거가 덮어써졌습니다. 기존 테스트는 완성된 patch 만 보내 이 구멍을
   지나쳤습니다.
2. **빈 patch(`{}`)가 통과했습니다.** 계약의 `minProperties: 1` 이 스키마에 없었습니다.
   아무것도 안 바꾸면서 `revision` 만 올려, 다른 화면들의 낙관적 잠금을 이유 없이 깹니다.
3. **컨테이너에서 사진 업로드가 죽습니다.** `ADGEN_IMAGE_DIR` 기본값이 상대 경로라
   root 소유인 `/app` 아래로 풀립니다. 아침에 `ADGEN_DB_PATH` 로 겪은 것과 같은 함정인데
   **증상이 기동이 아니라 첫 업로드**라 `/health` 도 CI 스모크도 초록입니다.
4. **짧은 변 512px 검사가 없었습니다.** [미결정_대장](../기술문서/미결정_대장.md) N3 의
   확정 사항인데 구현이 빠져 있었습니다.

3번은 CI 가 구조적으로 못 잡는 종류라 "쓰기 경로는 전부 Dockerfile 과 compose 양쪽에서
`/data` 를 가리켜야 한다"를 테스트로 만들어 두었습니다
(`tests/test_container_state_paths.py`). 다음에 쓰기 경로가 하나 더 생길 때 걸립니다.

⚠️ **계약에 빈 곳이 하나 있습니다 (소관 02).** `Brief.productImageUrl` 이 URL 을 약속하는데

### 08-19 HTTPS 종단 — 프록시를 앞에 한 겹 얹었습니다 (임동규)

08-18 배포에서 **로그인은 되는데 새로고침하면 로그인 화면으로 돌아오는** 증상이 나왔습니다.
코드 결함이 아니라 앞단 문제입니다 — 세션 쿠키가 계약대로 `Secure` 를 달고 있어 브라우저가
평문 HTTP 응답에서 그것을 저장하지 않습니다. 화면이 잠깐 로그인 상태로 보이는 것은
`AuthProvider.signIn` 이 쿠키가 아니라 응답 본문으로 상태를 정하기 때문이고, 마운트 시점의
`GET /v1/me` 가 401 을 받아 진짜 상태가 드러납니다. **위 08-13 기록이 예고한 그대로입니다.**

방식은 [ADR-0016](../adr/0016-HTTPS_종단_지점과_인증서_발급_경로.md) 으로 정했습니다. Caddy 를
프론트엔드 nginx **앞에** 한 겹 얹어 거기서 TLS 를 종단하고, 인증서는 빌려온 이름으로 Let's
Encrypt 에서 자동 발급받습니다. 06 의 `nginx.conf` 는 건드리지 않았습니다.

| 확인한 것 (2026-08-19, 로컬 스택) | 결과 |
|---|---|
| `ADGEN_PUBLIC_HOST` 세 상태(미설정 / `:80` / 호스트명)의 설정 유효성 | 전부 통과. 호스트명일 때 자동 HTTPS 와 HTTP -> HTTPS 리다이렉트가 켜짐 |
| 컨테이너 4개 기동과 헬스체크 | 전부 healthy |
| 프록시 경유 `/`, `/login`(SPA 폴백), `/health`, `/v1/me` | 200 / 200 / 200 / 401 (미인증이므로 정상) |
| 로그인 -> `/v1/me` 왕복 | 200. `Set-Cookie` 의 `Secure` + `SameSite=lax` 가 프록시를 지나며 그대로 보존됨 |
| 호스트에서 backend `8000` | 연결 실패 (발행 중단) |
| `e2e/` 하네스 | 3 passed |

**아직 남은 것은 VM 반영입니다.** 방화벽 443 규칙 확인과 `ADGEN_PUBLIC_HOST` 설정이 필요하며,
절차는 [infra/README.md](../../infra/README.md) "HTTPS" 절에 있습니다. 인증서 실발급은 그때
처음 일어나므로, 발급 한도로 막히는지는 아직 확인되지 않았습니다 (ADR-0016 "어려워지는 것").
