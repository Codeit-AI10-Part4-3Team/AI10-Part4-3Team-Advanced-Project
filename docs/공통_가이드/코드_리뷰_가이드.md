# 코드 리뷰 가이드

리뷰 **코멘트를 어떻게 쓰는가**에 대한 규약입니다. 리뷰어로 지정된 사람 전원이 대상이며,
AI 리뷰(`.github/workflows/ai-review.yml`)도 같은 서식을 따릅니다.

| 목적 | 문서 |
|---|---|
| 브랜치 → PR → 머지 **절차** | [pr-checklist.md](../pr-checklist.md) |
| 아키텍처 규칙·경계 (지적의 **근거**) | [AGENTS.md](../../AGENTS.md) |
| **리뷰 코멘트 작성법** | 이 문서 |

> 이 문서는 무엇을 지적할지(§1)와 어떻게 쓸지(§2~§4)만 다룹니다. 규약 자체의 정본은 `AGENTS.md`이며,
> 여기에 복제하지 않습니다.

## 1. 무엇을 보는가 (체크리스트)

리뷰어가 볼 것과 **기계가 이미 보는 것**을 분리합니다. 기계가 판정하는 항목을 사람이 다시
지적하면 조언이 충돌하고, 그 순간 팀은 리뷰 코멘트 전체를 신뢰하지 않기 시작합니다.

### 1-a. 반드시 볼 것

| # | 항목 | 왜 |
|---|---|---|
| 1 | **앱 간 경계 위반** — `apps/ai-engine` 이 `apps/backend` 를 import(역도 동일), `training/` 과 `apps/` 의 양방향 import, `backend_core` 가 `api` 를 import | import 한 줄이 "독립 배포 가능한 AI 모듈"이라는 성질을 조용히 없앱니다 |
| 2 | **계약 누락** — 요청/응답 스키마를 바꾸면서 `packages/contracts/openapi.yaml` 을 함께 고치지 않음 | 구두 합의는 계약이 아닙니다. 계약 없이 짜인 구현은 리뷰 대상이 아닙니다 |
| 3 | **하드코딩된 키·토큰·자격증명** (테스트 픽스처 포함) | public 레포입니다. 푸시되는 순간 공개이며 해결은 revert가 아니라 폐기·재발급입니다 |
| 4 | **예외 처리 없는 외부 호출** (HTTP, 모델 API, 파일 IO) | 의도적 생략이면 주석에 이유가 있어야 합니다 |
| 5 | **열화 폴백 소실** — 외부 의존이 죽었을 때 조용히 실패하거나 `messageMode` 에 드러나지 않음 | 폴백은 기능이지 예외 처리가 아닙니다 |
| 6 | **가드레일 우회** — 테스트를 통과시키려고 가드레일을 목으로 대체 | 테스트를 고치는 게 아니라 on/off 델타 지표를 무효로 만듭니다 |
| 7 | **논리 오류·경계 조건 누락·되돌릴 수 없는 부작용** | |
| 8 | **GPU 예산** — 학습과 추론이 동시에 VRAM을 요구하는 변경, 이미지 생성을 동기 HTTP로 붙드는 변경 | GPU는 한 대뿐이고, 동기 생성은 프록시 타임아웃에 먼저 걸립니다 |
| 9 | **테스트 가능성** — 도메인 로직이 FastAPI 없이 실행되는가, 지표 함수가 순수 함수로 남는가 | |
| 10 | **CI 계약 드리프트** — required check 이름(`.github/workflows/ci.yml` 의 잡 `name`)을 바꾸면서 `scripts/setup-github.sh` 의 `contexts` 를 함께 고치지 않음 | 모든 PR이 영원히 생성되지 않는 체크를 기다립니다 |

### 1-b. 지적하지 않을 것

- **스타일·포맷·import 정렬·타입** — ruff / mypy / reviewdog 소관입니다. 결정론적으로 이미 판정됩니다.
- **문서의 표현이나 오타** — 의미가 바뀌는 경우가 아니면 넘어갑니다.
- **취향에 속하는 설계 선택** — 규약 위반이 아니라면 지적이 아니라 질문으로 남기세요.

## 2. 대원칙: 결론부터 씁니다

리뷰는 두 종류의 독자를 동시에 상대합니다. **코드를 열지 않는 PM/QA**와, **정확히 무엇을 고칠지
알아야 하는 작성자**입니다. 아래 세 원칙은 그 둘을 층으로 분리해 양쪽이 다 살아남게 합니다.

### 2-a. 모든 제목이 판정을 담아야 합니다

질문형 제목은 정보를 담지 못합니다.

- 나쁨: `### 그래서 실제로 무슨 일이 벌어지나`
- 좋음: `### 기존에 받아둔 저장소에서는 고쳐지지 않습니다`

### 2-b. 제목 옆에 처리 등급을 붙입니다

아래 네 라벨을 **글자 그대로** 씁니다.

| 라벨 | 뜻 |
|---|---|
| `머지 전 필수` | 이 PR을 머지하기 전에 고쳐야 합니다 |
| `이 PR에서 권장` | 지금 고치는 편이 낫지만 머지를 막지는 않습니다 |
| `후속 과제` | 별도 이슈로 넘깁니다. 이 PR에서 처리하지 않습니다 |
| `참고, 조치 불필요` | 맥락 공유입니다. 작성자가 할 일은 없습니다 |

등급을 맨 아래 요약에 몰아 두지 마세요. 위에서 아래로 읽는 사람은 각 항목이 자기를 막는지를
**그 자리에서** 알아야 합니다. (Conventional Comments와 같은 발상입니다.)

## 3. 첫 문단은 코드를 한 줄도 열지 않고 읽혀야 합니다

- **첫 문단만으로 누가, 언제, 어떻게 피해를 보는지**가 답해져야 합니다. "비전공자도 이해할 수 있게"는
  자기 판단에 따라 흔들리지만, "코드를 열지 않고 읽히는가"는 실제로 검사할 수 있습니다.
- 기술적으로 무엇이 틀렸는지가 아니라 **실무에서 무엇이 잘못되는지**로 시작합니다.
- **언제 깨지는지**와 **왜 지금은 멀쩡해 보이는지**를 함께 적습니다. 후자는 오늘 무증상인 결함일수록
  중요합니다.
- **근거와 수정 문단은 정확성을 우선합니다.** 파일과 줄 번호를 정확히 인용하되, 처음 나오는 용어는
  그 자리에서 한 문장으로 풀어 씁니다. 읽기 쉽게 하려고 위치를 흐리면 리뷰가 수필이 되고 작성자에게는
  조치할 것이 남지 않습니다.
- 코드 인용은 근거로 유지하되 앞뒤를 평문으로 감쌉니다.

## 4. 수정이 작을 때만 고친 코드를 줍니다

- 완성된 수정본은 **한 파일, 몇 줄, 판단이 개입하지 않을 때만** 제시합니다.
- **판단이 개입하면(설계나 규약 선택) 코드가 아니라 선택지를 제시합니다.** 남의 설계 결정을 패치로
  건네는 것은 리뷰가 아니라 인수입니다.
- **검증 여부를 몇 마디로 표기합니다.** 아래 라벨을 글자 그대로 씁니다.
  - `로컬에서 확인함`
  - `미검증, 눈으로만 확인`
  코드로 제시된 수정은 검증된 것처럼 읽히므로, 확인한 주장과 확인하지 않은 주장에 같은 확신을
  주어서는 안 됩니다.
- 추측이 섞인 지적에는 **`추정`** 이라고 밝힙니다.

## 5. 작성 예시

> ### 어댑터 로드 실패 시 서비스가 500으로 죽습니다 - `머지 전 필수`
>
> 파인튜닝 어댑터 파일이 없거나 손상된 VM에서는 첫 생성 요청이 500으로 떨어집니다. 사용자에게는
> "일시적 오류"로 보이지만 재시도해도 같습니다. 지금 스테이징에서 멀쩡한 이유는 어댑터가 이미
> 디스크에 있기 때문이고, 새 VM을 띄우는 배포일에 처음 드러납니다.
>
> `apps/ai-engine/src/ai_engine/generator.py:48` 에서 어댑터를 로드하는데 예외 처리가 없습니다.
> 이 프로젝트의 규약상 여기는 base 모델로 열화 폴백하고 그 사실을 `messageMode` 에 표기해야 하는
> 자리입니다(`AGENTS.md` 설계 제약 2번).
>
> 수정은 한 곳입니다. `미검증, 눈으로만 확인`:
>
> ```python
> try:
>     pipe.load_lora_weights(adapter_path)
> except (OSError, ValueError) as exc:  # 어댑터 없음/손상 -> base 모델로 열화
>     logger.warning("adapter load failed, falling back to base: %s", exc)
>     message_mode = "official_fallback"
> ```

## 6. AI 리뷰와의 관계

`.github/workflows/ai-review.yml` 이 PR마다 같은 체크리스트(§1)와 같은 서식(§2~§4)으로 1차 리뷰를
남깁니다. **보조 리뷰어이지 승인 주체가 아닙니다** - 머지 게이트는 `ci.yml`(ruff / mypy / pytest)과
사람의 Approve입니다.

- AI 코멘트에 동의하지 않으면 그렇게 답글을 달고 `Resolve conversation` 하세요. 근거 없이 따를
  대상이 아닙니다.
- AI가 놓친 것을 사람이 봅니다. §1의 5, 8, 9번(폴백 설계, GPU 예산, 테스트 가능성)은 레포 전체 맥락과
  실측이 필요해 LLM이 특히 약한 영역입니다.
- 워크플로 프롬프트를 고칠 때는 이 문서를 **같은 PR에서** 함께 고치세요. 둘이 어긋나면 사람과 봇이
  다른 서식으로 리뷰하게 됩니다.
