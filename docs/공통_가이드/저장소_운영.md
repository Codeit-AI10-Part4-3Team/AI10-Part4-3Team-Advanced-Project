# 저장소 운영 가이드

GitHub 저장소 **설정**을 적용·유지하는 방법입니다. 주 대상은 admin이지만, §4(CI 계약)는 워크플로나
`scripts/setup-github.sh`를 건드리는 모든 사람이 읽어야 합니다.

| 목적 | 문서 |
|---|---|
| 내 PC에 개발 환경 맞추기 | [환경_세팅_가이드.md](환경_세팅_가이드.md) |
| 브랜치 → PR → 머지 절차 | [pr-checklist.md](../pr-checklist.md) |
| 아키텍처 규칙·코드 컨벤션 | [AGENTS.md](../../AGENTS.md) |
| **저장소 설정·CI 계약** | 이 문서 |

## 1. 대원칙: 설정은 파일로 따라오지 않는다

저장소를 구성하는 것은 두 트랙이고, **git이 추적하는 것은 한쪽뿐**입니다.

| 트랙 | 예 | 어떻게 유지되나 |
|---|---|---|
| **파일** | 워크플로, 이슈/PR/Discussion 템플릿, `labels.yml`, pre-commit 설정, 코드, 문서 | git이 추적 — PR diff에 보이고 자동으로 따라옴 |
| **설정** | 브랜치 보호 규칙, 라벨 실체, 머지 전략, Secrets/Variables, Discussions 활성화·카테고리, Code security, 협업자 권한 | GitHub 서버에만 존재 — **diff에 보이지 않고**, `scripts/setup-github.sh` + 수동 설정(§3)으로만 재현 |

이 비대칭이 이 문서가 존재하는 이유입니다. 템플릿에서 리포를 만들어도 **설정은 하나도 복사되지
않습니다.** 설정 쪽은 누가 콘솔에서 바꿔도 기록이 남지 않으므로, **바꿨으면 스크립트에도 반영**해야
다음 사람이 같은 상태를 재현할 수 있습니다.

## 2. 저장소 하드닝 (admin, 리포당 1회)

```bash
gh auth login                                                    # 대상 레포 admin 권한 필요
bash scripts/setup-github.sh Codeit-AI10-Part4-3Team/AI10-Part4-3Team-Advanced-Project    # 브랜치 보호 + 머지 전략 + 라벨
bash scripts/setup-github.sh Codeit-AI10-Part4-3Team/AI10-Part4-3Team-Advanced-Project --solo   # 1인 프로젝트: 승인 요구 제외
```

**재실행이 필요한 시점**

- CI 잡 이름을 바꾸거나 앱을 추가했을 때 → `setup-github.sh`의 `contexts`를 **같은 PR에서** 고친 뒤 재실행 (§4)
- 루트 `CODEOWNERS`에 경로를 추가/변경했을 때 → 새 경로에 오너가 **2명 이상**인지 확인 후 재실행
- 브랜치 보호가 403으로 실패했을 때 → 원인 해소 후 재실행. 스크립트는 보호 적용에 실패해도
  머지 전략·라벨은 계속 적용하고, 무엇이 빠졌는지 마지막에 출력합니다.

> ⚠️ 템플릿의 `CODEOWNERS`는 존재하지 않는 예시 계정을 담고 있습니다. 그대로 두면
> `setup-github.sh`가 이를 감지해 **코드오너 리뷰 요구만 끄고** 나머지 보호를 적용합니다
> (승인 가능한 오너가 0명이 되어 모든 PR이 영구 블록되는 사고를 막기 위한 안전장치).
> 실제 계정으로 채운 뒤 스크립트를 다시 실행하세요.

## 3. 수동 설정 체크리스트 (스크립트가 못 하는 것)

- [ ] **Settings → General → Features**: Discussions 활성화
- [ ] **Discussions → 카테고리 `CollaborationLog` 생성** — Discussion 카테고리는 API가 없어 수동 생성만
      가능합니다. 만들지 않으면 이슈 config의 협업 일지 링크와 `DISCUSSION_TEMPLATE`이 동작하지 않습니다.
- [ ] **Settings → Code security**: Secret scanning + Push protection 활성화 (public 저장소 전용 기능)
      — ⚠️ 이것만 믿으면 안 됩니다. GitHub의 탐지는 **제휴 발급사 패턴 위주**라 국내 서비스나
      자체 발급 키는 사각지대일 가능성이 높습니다(추정). 실질 방어선은 pre-commit의 **gitleaks** 훅과
      CI의 전체 트리 스캔입니다.
- [ ] (팀) Collaborators/Teams 권한 부여 → 루트 `CODEOWNERS`에 실제 계정 배정
      — 팀원이 바뀌면 collaborator 권한(write 이상)과 `CODEOWNERS`를 **함께** 갱신하세요.
      write 권한이 없는 계정은 오너로 인정되지 않아 조용히 무시됩니다.
- [ ] (필요 시) Actions Secrets/Variables 등록 — 워크플로가 참조하는 secret이 없으면 등록 전까지 CI가 실패합니다
- [ ] (선택) **SonarQube Cloud 연결** — 프로젝트 임포트 → Automatic Analysis **끄기** → `SONAR_TOKEN`
      시크릿 등록 → `sonar-project.properties`의 `organization`/`projectKey`를 실제 값으로. 상세: §8
- [ ] (선택) **Greptile GitHub App 설치** — 앱 설치 없이는 루트 `greptile.json`이 아무 효과가 없습니다. 상세: §8

## 4. CI 계약 유지 규칙

required status check는 **브랜치 보호 설정(서버)과 워크플로 파일(git)이 문자열로 맺은 계약**입니다.
한쪽만 바꾸면 모든 PR이 조용히 막히므로, 아래 세 가지는 규칙으로 취급하세요.

- **required check에 `paths:` 필터를 걸지 말 것.** 필터가 걸린 워크플로는 해당 경로를 건드리지 않은
  PR에서 **체크 자체가 생성되지 않고**, 머지는 영원히 `Expected` 상태로 대기합니다.
  그래서 `ci.yml`은 필터 없이 모든 PR에서 돌고, 경로 필터형 워크플로 4종은 required로 지정하지
  않습니다. CI 비용을 줄이려면 `dorny/paths-filter` 같은 **잡 내부** 필터를 쓰세요.
- **required check의 context 이름 = 잡의 `name:`.** `setup-github.sh`의 `contexts` 배열과 `ci.yml`의
  잡 이름은 문자열이 정확히 일치해야 합니다. 매트릭스 잡이라 이름이 전개되어 현재 5종입니다 —
  `Pre-commit hooks`, `Lint & Type Check (backend)` / `(ai-engine)`, `Unit tests (backend)` / `(ai-engine)`.
  **앱을 추가하면 `ci.yml`의 matrix와 `setup-github.sh`의 contexts를 같은 PR에서 함께 늘리세요.**
- **브랜치 보호는 첫 CI가 돈 뒤에 적용.** GitHub가 아직 본 적 없는 체크 이름을 required로 걸면
  PR에서 `Expected` 대기가 생길 수 있습니다. 가능하면 첫 push 이후에 실행하세요.

### 4-1. ruff 버전 드리프트 (`ruff-sync` 훅)

이 레포는 **같은 ruff를 서로 다른 경로로** 설치합니다 — pre-commit 훅은 `.pre-commit-config.yaml`의
`rev`로, CI lint 잡은 `apps/<app>/pyproject.toml`의 `ruff==`로, reviewdog 워크플로는
`RUFF_VERSION`으로. ruff는 0.x라 마이너 업그레이드에서 기본 규칙셋 자체가 넓어지므로
(실측: 0.15 통과 → 0.16에서 신규 23건), 한 곳만 올라가면 **"로컬 훅은 통과했는데 CI는 실패"** 가
재현됩니다. 그 상태가 반복되면 팀은 훅을 무시하기 시작하고, 품질 게이트의 전제가 무너집니다.

이 규약은 오랫동안 주석으로만 있었고, 실제로 Dependabot의 pip 업데이트가 `pyproject.toml`만
올리면서 드리프트가 발생했습니다(#2). 지금은 `scripts/check_ruff_sync.py`가 검사하고,
pre-commit의 `ruff-sync` 훅으로 등록되어 **커밋 시점과 CI 양쪽에서** 강제됩니다
(CI의 `Pre-commit hooks` 잡이 `--all-files`로 함께 돌립니다 — 새 required check가 필요 없습니다).

⚠️ **ruff 상향은 여전히 두 개의 Dependabot PR로 도착합니다** (pip 하나, pre-commit 하나).
Dependabot은 생태계를 가로지르는 그룹화를 지원하지 않기 때문입니다. 먼저 도착한 PR은
`ruff-sync`에서 실패하는데 이는 **설계된 동작**입니다 — 한쪽 PR 브랜치에서 나머지 파일까지
함께 고쳐 하나로 합쳐 머지하세요.

## 5. 라벨 동기화

`.github/labels.yml`이 **원천**입니다. 라벨을 바꾸려면 콘솔이 아니라 파일을 고치고 동기화하세요.

```bash
bash scripts/apply-labels.sh Codeit-AI10-Part4-3Team/AI10-Part4-3Team-Advanced-Project
```

PR 템플릿의 '변경 유형' 체크박스와 라벨 목록은 짝을 이루므로 **함께** 갱신합니다.

## 6. 무료 플랜 private 리포에서 쓰기

private 리포 생성 자체는 제약이 없습니다. 다만 무료 플랜에서는 아래가 동작하지 않습니다
(GitHub Pro/Team 또는 public 전환 시 전부 사용 가능).

| 항목 | 무료 private | 대응 |
|---|---|---|
| 파일 자산 전부 (워크플로·템플릿·pre-commit·코드) | ✅ | — |
| CI (GitHub Actions) | ✅ 월 2,000분 한도 | `concurrency`가 중복 실행을 취소. 부족하면 public 전환(무제한) |
| 머지 전략·라벨·Discussions | ✅ | — |
| **브랜치 보호 규칙** | ❌ (API 403) | `setup-github.sh`가 경고 후 나머지를 계속 적용 |
| **CODEOWNERS** (자동 배정·필수 리뷰) | ❌ | 파일은 무해하게 남음 — 전환 시 즉시 동작 |
| Secret scanning / Push protection | ❌ (public 전용) | pre-commit **gitleaks** + `.gitignore` 시크릿 패턴이 로컬 방어선 |
| README의 CI 배지 | ❌ (외부 임베드 불가) | 배지 줄 삭제, public 전환 시 복원 |

브랜치 보호가 없는 동안의 실질 방어선은 **pre-commit + pre-push pytest**입니다 — CI와 동일 기준이라
훅 설치만 지키면 품질 게이트는 유지됩니다. 다만 main 직접 push를 막는 **강제력**은 없습니다.

이 저장소는 [Yopkigom/ai-team-project-template](https://github.com/Yopkigom/ai-team-project-template)에서 파생됐습니다. 여기서 발견한 개선점(새 함정,
더 나은 CI 구성, 관례)은 템플릿 쪽에 되돌려 두세요 — 템플릿은 "가장 최근 프로젝트의 교훈이 쌓인

`git remote add template ...` 후 선별 cherry-pick으로 가져옵니다.

## 8. 보조 리뷰 도구 (reviewdog / SonarQube Cloud / AI 리뷰)

`ci.yml`이 **하드 게이트**(통과 못 하면 머지 불가)이고, 아래 셋은 **보조 리뷰어**입니다.
세 도구 모두 required status check가 **아닙니다** — 이유는 공통적으로 하나입니다.

> required로 걸면 "체크가 생성되지 않는 상황"이 곧 영구 머지 블록입니다. 세 도구 각각
> fork PR(reviewdog·AI 리뷰), 토큰 미설정·외부 서비스 장애(Sonar·AI 리뷰), 크레딧 소진(AI 리뷰)에서
> 그 상황이 실제로 발생합니다. 품질의 최종 판정은 사람과 `ci.yml`이 하고, 이들은 근거를 앞에 놓아줄 뿐입니다.

| 도구 | 설정 파일 | 필요한 사전 작업 | 성격 |
|---|---|---|---|
| reviewdog | `.github/workflows/reviewdog.yml` | 없음 (`GITHUB_TOKEN`만 사용) | 결정론적 린터 결과를 PR 변경 줄에 인라인 코멘트 |
| SonarQube Cloud | `sonar-project.properties` + `.github/workflows/sonarqube.yml` | 프로젝트 임포트 + `SONAR_TOKEN` 시크릿 | 정적 분석 + 커버리지 추세 |
| AI 리뷰 | `.github/workflows/ai-review.yml` | `ANTHROPIC_API_KEY` 시크릿 | LLM 기반 맥락 리뷰 (논리·경계·계약) |

**세 계층은 서로 겹치지 않게 나눠져 있습니다.** 스타일·포맷·타입은 reviewdog가, 커버리지·중복은
Sonar가, 논리 오류·경계 조건·계약 위반은 AI 리뷰가 봅니다. 이 분담이 무너져 두 봇이 같은 주제로
코멘트하기 시작하면 서로 충돌하는 조언이 되고, 그 순간 팀은 봇 코멘트 **전체**를 무시하기 시작합니다.

### reviewdog

`ci.yml`이 이미 돌리는 것과 **같은 도구·같은 버전**을 돌립니다. 차이는 출력 위치뿐입니다 —
CI 로그를 열어 실패 줄을 찾는 대신 PR diff에 코멘트가 붙습니다. 검사 대상은
ruff(진단 + 포맷 제안), mypy, actionlint, eslint(프론트엔드 스캐폴딩 후 자동 활성화)입니다.

- ⚠️ **ruff 버전은 3곳이 아니라 4곳**이 되었습니다: `.pre-commit-config.yaml`의 `rev`,
  `apps/backend`·`apps/ai-engine`의 `ruff==`, 그리고 `reviewdog.yml`의 `RUFF_VERSION`.
  한 곳만 올리면 같은 코드가 게이트와 보조 리뷰에서 다르게 판정됩니다 —
  이제 `ruff-sync` 훅이 이를 강제합니다(§4-1).
- ⚠️ **fork PR에서는 잡 전체가 스킵됩니다.** fork의 `GITHUB_TOKEN`은 read-only라 코멘트를
  쓸 수 없기 때문입니다. `pull_request_target`으로 우회할 수 있지만 fork 코드를 write 권한
  컨텍스트에서 실행하게 되므로(임의 코드 실행) public 저장소에서는 채택하지 않았습니다.
  외부 기여자의 PR은 `ci.yml` 결과로 판단하세요.

### SonarQube Cloud

1. [sonarcloud.io](https://sonarcloud.io)에 GitHub 계정으로 로그인 → 조직 임포트 → 이 저장소 추가
2. 프로젝트 설정 → Analysis Method → **Automatic Analysis 끄기**
   ⚠️ 켜두면 CI 기반 스캔이 "이미 자동 분석 중"이라며 실패합니다. 자동 분석은 커버리지 리포트를
   읽지 못하므로 CI 기반을 씁니다.
3. My Account → Security에서 토큰 발급 → 저장소 Settings → Secrets에 `SONAR_TOKEN` 등록
4. `sonar-project.properties`의 `sonar.organization`·`sonar.projectKey`를 Sonar 프로젝트 페이지에
   표시된 값과 정확히 일치시키기 (organization 키는 소문자만 허용)

- `SONAR_TOKEN`이 없으면 워크플로가 **실패 대신 스킵**합니다. 템플릿을 그대로 클론한 팀이
  Sonar를 붙이기 전까지 빨간 X를 보지 않게 하기 위한 처리입니다.
- ⚠️ **앱을 추가하면 3곳을 함께 고치세요**: `sonar.sources`/`sonar.tests`,
  `sonar.python.coverage.reportPaths`, 그리고 `sonarqube.yml`의 커버리지 스텝.
  커버리지 XML이 없으면 스캐너는 경고만 남기고 0%로 보고하며, Quality Gate가 조용히 실패합니다.
- `checkout`의 `fetch-depth: 0`은 필수입니다. Sonar가 blame으로 "새 코드"를 판정하므로
  얕은 클론이면 모든 줄이 새 코드로 잡혀 지표가 무의미해집니다.

### AI 리뷰 (Claude)

`.github/workflows/ai-review.yml`이 PR diff를 읽고 **논리 오류·경계 조건·계약 위반**을 인라인
코멘트로 답니다. 리포지토리 규약은 `AGENTS.md`가 원천이며, 워크플로의 `prompt`가 그중 무엇을
지적하고 무엇을 지적하지 말지 좁혀 둡니다.

**사전 작업은 시크릿 하나입니다**: [console.anthropic.com](https://console.anthropic.com)에서
API 키를 발급해 Settings → Secrets and variables → Actions에 `ANTHROPIC_API_KEY`로 등록하세요.
등록 전까지 워크플로는 **실패 대신 스킵**합니다(Sonar와 같은 처리).

#### 왜 개인 구독 토큰이 아니라 조직 API 키인가

`anthropics/claude-code-action`은 Pro/Max 구독자용 OAuth 토큰(`CLAUDE_CODE_OAUTH_TOKEN`,
`claude setup-token`으로 발급)도 지원합니다. 이 저장소는 **쓰지 않습니다** — 이유가 세 가지입니다.

- **시크릿은 write 권한자 전원이 꺼낼 수 있습니다.** 워크플로를 브랜치에서 고쳐 값을 인코딩해
  출력하면 GitHub의 로그 마스킹은 우회됩니다. 개인 계정 자격증명을 5명이 공유하는 구조가 됩니다.
- **구독 쿼터는 본인의 작업 쿼터와 같은 통입니다.** CI가 소진하면 그 사람의 Claude Code 작업이 멈춥니다.
- **폐기 단위가 다릅니다.** OAuth 토큰은 계정 전체 자격증명이라 유출 시 개인 계정을 재인증해야
  하지만, API 키는 그 키만 폐기하면 되고 조직 소유로 둘 수 있습니다.

⚠️ 그래도 **API 키 역시 write 권한자는 꺼낼 수 있습니다.** 콘솔에서 **지출 상한(spend limit)을
반드시 설정**하고, 프로젝트가 끝나면 키를 삭제하세요.

#### 비용

PR 1건당 diff + 주변 컨텍스트를 30k input / 3k output으로 가정한 `추정`입니다. 실제 값은
PR 크기에 비례하므로 콘솔의 사용량으로 재측정하세요.

| 모델 | PR 1건 | PR 100건 |
|---|---|---|
| `claude-opus-5` ($5 / $25 per MTok) | 약 $0.23 | 약 $23 |
| `claude-sonnet-5` ($3 / $15, 2026-08-31까지 인트로 $2 / $10) | 약 $0.09 | 약 $9 |

기본값은 `claude-opus-5`입니다. 비용을 줄이려면 `ai-review.yml`의 `--model`을
`claude-sonnet-5`로 바꾸세요 — 과제 기간(~2026-08-31)은 인트로 가격이 적용됩니다.

#### 주의

- ⚠️ **`pull_request_target`으로 바꾸지 마세요.** fork 코드를 write 권한 + 시크릿 접근 컨텍스트에서
  실행하게 되어 임의 코드 실행과 API 키 탈취가 동시에 가능해집니다. public 저장소라 실제 위험입니다.
  대신 fork PR에서는 잡을 스킵합니다(reviewdog와 같은 처리).
- ⚠️ **스타일·포맷·타입을 지적하게 두지 마세요.** 워크플로의 `prompt`가 이를 명시적으로 금지하고
  있습니다. 지우면 reviewdog와 충돌하는 조언이 나옵니다.
- ⚠️ **required로 만들지 마세요.** 크레딧 소진·API 장애·fork PR에서 체크가 생성되지 않으면
  그대로 영구 머지 블록입니다.
- `concurrency`가 같은 PR의 이전 실행을 취소합니다 — 연속 push 시 중복 과금을 막는 장치이므로
  지우지 마세요.
- 로컬에서 push 전에 `/code-review`를 돌리면 각자의 구독으로 미리 걸러집니다(공유 시크릿 불필요).
  CI의 AI 리뷰는 그것을 건너뛴 PR을 잡는 백스톱입니다.

#### Greptile을 쓰지 않는 이유

이전 구성은 [Greptile](https://app.greptile.com)(`greptile.json` + GitHub App)이었으나 **월 결제가
필요해 제외**했습니다. Anthropic의 관리형 Code Review도 후보였지만 Team/Enterprise 구독 전용이고
리뷰 1건당 $15~25이라 이 프로젝트 규모에 맞지 않습니다(`높은 신뢰`). 되돌릴 경우
`greptile.json`을 복원하고 이 절을 교체하세요 — 이력은 git에 남아 있습니다.
