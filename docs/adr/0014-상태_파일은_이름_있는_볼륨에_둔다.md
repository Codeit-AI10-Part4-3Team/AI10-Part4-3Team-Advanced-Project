# ADR-0014: 상태 파일은 이름 있는 볼륨에 두고, 바인드 마운트를 쓰지 않는다

- **상태**: Proposed
- **날짜**: 2026-08-12
- **결정자**: 임동규 (05 백엔드/인프라). 합의 대기: 신호정 (02 TL), 정승호 (01 PM)
- **관련**: [ADR-0010](0010-상태_저장소와_파일_보관_위치.md),
  [ADR-0011](0011-배포_환경_스펙과_권한_경계.md),
  [세션_보관_정책.md](../기술문서/세션_보관_정책.md) 2절과 3절,
  [리스크.md](../공통_가이드/리스크.md) 9번

## 배경

[ADR-0010](0010-상태_저장소와_파일_보관_위치.md)은 **무엇을 어디에 둘지**를 정했습니다. 상태는
SQLite 파일 하나, 이미지는 VM 로컬 디스크. 정하지 않은 것이 하나 남았습니다. **그 파일이
컨테이너에서 어떤 경로로 보이는가**입니다.

`docker compose up` 으로 도는 이상 이것은 취향이 아니라 기동 여부의 문제입니다. 2026-08-12 에
이미지를 빌드해 확인한 결과입니다.

```
db_path = ./data/adgen.sqlite
실패: PermissionError [Errno 13] Permission denied: 'data'
```

`apps/backend/Dockerfile` 은 `WORKDIR /app` 에 `USER appuser`(uid 10001) 로 돕니다. `/app` 은
빌드 중 root 로 만들어져 **비루트 사용자가 그 아래에 디렉토리를 만들 수 없습니다.** 저장소를
앱 기동에 연결하는 순간 컨테이너가 뜨자마자 죽습니다.

즉 결정이 필요한 것은 둘입니다. 상태 파일을 **볼륨 위로 옮기는 것**과, **어떤 종류의 볼륨을
쓸 것인가**입니다.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. **이름 있는 볼륨** (`adgen-state:/data`) | 도커가 이미지의 `/data` 소유권을 물려주므로 비루트 실행과 그대로 맞습니다. 호스트 경로를 몰라도 됩니다 | 백업이 호스트의 단순 파일 복사가 아니라 `docker compose exec` 를 한 번 거칩니다 |
| B. 바인드 마운트 (`../data:/data`) | 호스트에서 파일이 그대로 보여 백업과 내려받기가 직접적입니다 | 호스트 디렉토리는 도커가 root 로 만들고, 컨테이너의 uid 10001 과 맞지 않아 **같은 PermissionError 가 재발합니다.** 맞추려면 호스트에서 uid 를 고정해 미리 `chown` 해야 하고, 그 절차가 재현 문서에 얹힙니다 |
| C. Dockerfile 에서 `/app/data` 를 `appuser` 소유로 | 경로 기본값을 안 바꿔도 됩니다 | 볼륨이 아니라 **이미지 레이어**입니다. 컨테이너를 지우면 상태가 사라져 ADR-0010 이 인메모리를 배제한 이유가 그대로 재현됩니다 |

## 결정

**A를 택합니다.** 이름 있는 볼륨 `adgen-state` 를 `/data` 에 붙이고, `ADGEN_DB_PATH` 의
배포 기본값을 `/data/adgen.sqlite` 로 둡니다. 이미지에서는 `/data` 를 미리 만들어 `appuser`
소유로 넘깁니다 - 도커는 볼륨을 처음 붙일 때 그 경로의 소유권을 물려받으므로, 이 한 줄이
권한 문제를 없애는 지점입니다.

B를 택하지 않은 이유는 **그것이 풀려는 문제를 그대로 다시 만들기 때문**입니다. 바인드 마운트는
호스트 디렉토리의 소유권을 그대로 컨테이너에 노출하고, 우리는 비루트(uid 10001)로 돕니다.
비루트 실행을 포기하거나 호스트에서 uid 를 맞춰 `chown` 하는 절차를 재현 문서에 넣어야 하는데,
전자는 보안 후퇴이고 후자는 배포 절차가 사람 손에 의존하는 단계를 하나 늘립니다. 배포가
SSH + `git pull` + `docker compose up` 수동 경로라(ADR-0011) 손이 가는 단계는 그대로 빠뜨릴
수 있는 단계입니다.

C를 택하지 않은 이유는 **볼륨이 아니기 때문**입니다. 재시작은 견디지만 컨테이너 재생성은 견디지
못하고, 배포는 컨테이너를 다시 만드는 일입니다.

## 결과

### 생기는 제약

- **백업 경로가 한 단계 늘어납니다.** [ADR-0010](0010-상태_저장소와_파일_보관_위치.md)이
  "백업은 두 경로의 복사"라고 적은 것은 여전히 참이지만, 그 경로가 호스트 파일 시스템이 아니라
  볼륨 안입니다. 08-26 의 SQLite 백업 cron 은 `docker compose exec` 로 `VACUUM INTO` 를 돌린 뒤
  결과 파일을 꺼내는 형태가 됩니다. 리스크 9(시연 산출물을 미리 내려받기)의 대응도 같은 경로를
  씁니다.
- **`docker compose down -v` 는 상태를 지웁니다.** `-v` 없이 내리면 볼륨은 남습니다. 이 한 글자가
  계정과 세션 전체이므로 배포 절차서에 그대로 적습니다.
- **`ADGEN_DB_PATH` 의 기본값과 배포값이 다릅니다.** 코드 기본값은 로컬 실행용(`./data/...`),
  compose 는 `/data/...` 입니다. 경로가 설정값이어야 한다는
  [ADR-0010](0010-상태_저장소와_파일_보관_위치.md)의 요구가 여기서 실제로 쓰입니다.
- **이미지 파일도 이 볼륨에 둡니다.** 업로드 사진과 결과 이미지가 들어올 때 별도 볼륨을 새로
  만들지 마세요. 보존 기간 정리 배치가 한 곳만 보면 되도록 유지합니다
  ([세션_보관_정책.md](../기술문서/세션_보관_정책.md) 2절).

### 쉬워지는 것

- 비루트 실행을 유지한 채로 상태가 남습니다. 둘 중 하나를 포기하지 않아도 됩니다.
- 로컬과 VM 이 같은 compose 파일로 같은 결과를 냅니다. 호스트 경로가 등장하지 않습니다.

### 어려워지는 것

- 파일을 눈으로 열어 보려면 `docker compose exec` 가 필요합니다. 디버깅 시 한 단계 더 걸칩니다.

### 재검토 신호

- 백업 cron 이 실제로 만들어졌을 때 `docker compose exec` 경로가 불편하다고 판명되는 경우.
  그때는 B 로 옮기되 uid 고정 절차를 재현 문서에 함께 넣습니다.
- 이미지 파일 용량이 커져 볼륨과 별도 디스크를 갈라야 하는 경우.
- 워커를 늘려 여러 컨테이너가 같은 파일을 열어야 하는 경우. 그때는
  [ADR-0010](0010-상태_저장소와_파일_보관_위치.md)부터 다시 엽니다.
