### 08-12 루프백 바인딩 — 부분 충족, 나머지는 배포 시점으로 보류 (임동규)

확인된 것 둘입니다.

- `infra/docker-compose.yml`이 이미 `"127.0.0.1:8100:8100"`으로 바인딩하고 있습니다. 새로 짤
  것은 없고, 선언대로 동작하는지 확인하는 것이 이 작업의 내용입니다.
- **8100을 여는 방화벽 규칙이 0건**입니다 (`--filter="allowed[].ports~8100"`).
  기록: [infra/README.md](../../infra/README.md) 권한 경계 표.

**DoD의 "외부에서 8100 접근 불가 확인"은 보류합니다.** 밖에서 8000과 8100을 함께 재면 지금은
둘 다 닫혀 있고, 그 상태로는 **"막혀서 실패"와 "안 떠 있어서 실패"가 구분되지 않습니다**
(SSH 22번은 열려 있어 VM 도달 자체는 확인됨). 대조군인 8000이 살아 있어야 판정이 서므로,
스택을 VM에 올리는 시점에 8000 열림 + 8100 닫힘을 함께 확인해 닫습니다.

⚠️ **그 배포 날짜에 문서가 어긋나 있습니다.** [착수_체크리스트.md](../공통_가이드/착수_체크리스트.md) 5-a와
`infra/README.md`는 "W2 중"(08-12 ~ 08-14), 이 문서와 [00-overall.md](00-overall.md)는 **08-20**
입니다. 즉 **08-12 항목의 DoD가 08-20 작업을 전제**하고 있습니다. 어느 쪽이 맞는지는 회의록으로
정합니다 (기획서 14.3).

**2026-08-13 회의록으로 절반이 정해졌습니다**
([회의록](../회의록/2026-08-13_워킹스켈레톤_일정_조정.md) 정정 절).

- 정해진 것: 08-12에 끝난 것은 **VM 환경 설정**이고 **스택 배포는 미완료**입니다. 따라서 위

### 08-13 S0 로그인 — 인증 경로는 닫힘, INV-9 의 404 는 S2 로 넘어감 (임동규)

닫힌 것: 고정 계정 둘 시드, 아이디 조회 + 비밀번호 대조, 세션 쿠키 발급과 폐기,
미인증 401, 계약의 auth 경로 6개(구현 3 + 501 3). 계약과 실제 서빙 경로를 대조해
양쪽 차집합이 0 인 것을 확인했습니다.

**DoD 의 "남의 세션 404 (INV-9)" 는 S0 만으로 닫을 수 없습니다.** 404 를 낼 대상인 세션
리소스가 S2 소관이기 때문입니다. S0 에서 닫은 것은 그 앞 절반 - 요청이 소유자로 해석되고,
소유자 없는 요청은 401 이 되는 것 - 이며, 두 계정이 서로 다른 `userId` 를 받는지(404 경로의
전제)까지 테스트로 걸어 두었습니다. **이 항목은 S2 에서 함께 닫습니다.**

> **해소 (2026-08-14, 표기는 08-19).** S2 와 함께 들어왔습니다.
> `test_inv_9_someone_elses_session_is_404_not_403` 이 남의 세션과 없는 id 의 **응답 본문이
> 같은지**까지 봅니다 - 404 만 맞고 본문이 다르면 id 존재 여부가 그대로 새기 때문입니다.
> 단언은 `assert mine.json() == invented.json()` 이라 파싱된 객체 비교이며, 키 순서나 공백은
> 보지 않습니다.
> `test_inv_9_the_list_only_shows_your_own` 이 목록 쪽을 함께 막습니다.

새로 생긴 결정 둘을 ADR 로 남겼습니다:
[ADR-0013](../adr/0013-로그인_토큰_형식과_폐기_정책.md) 토큰 형식과 폐기 정책,
[ADR-0014](../adr/0014-상태_파일은_이름_있는_볼륨에_둔다.md) 상태 파일의 볼륨.

⚠️ **로그인을 브라우저로 쓰려면 HTTPS 가 먼저 필요합니다.** 세션 쿠키가 계약대로 `Secure` 를
달기 때문에, 평문 HTTP 로 배포하면 브라우저가 쿠키를 버려 로그인이 성립하지 않습니다. 상세는
[API_계약.md](../기술문서/API_계약.md) 8.3절입니다.
**08-14 의 "VM에 스택 1회 배포"는 이것에 막히지 않습니다** — 그 항목의 DoD 는 "빈 스택이어도
충족"이라 로그인 동작을 요구하지 않습니다. 막히는 것은 그 위에서 화면이 붙는 시점이고,
HTTPS 는 그 전까지 닫으면 됩니다.

### 08-19 미결로 남아 있던 넷을 실측으로 닫습니다 (임동규)

넷 다 **실제로는 충족돼 있었는데 표에만 대기로 남아 있던** 것입니다. 판정에 필요한 조건이
그동안 갖춰졌기 때문이며(대부분 VM 배포), 근거를 남기지 않고 상태만 바꾸면 다음 사람이 다시
재게 되므로 잰 값을 함께 적습니다.

#### 1. 루프백 바인딩 - 보류했던 판정을 냈습니다

08-12 기록이 보류한 이유는 "막혀서 실패"와 "안 떠 있어서 실패"가 구분되지 않는다는 것이었고,
대조군인 8000이 살아나기를 기다리고 있었습니다. 배포가 끝나 조건이 갖춰졌습니다.

**관측 지점은 VM 밖(개발자 노트북)이고, 시각은 HTTPS 종단이 배포되기 전입니다.** 아래
"08-19 HTTPS 종단" 기록의 8000 서술과 값이 다른 이유가 그것이라 먼저 적어 둡니다.

| 포트 | 결과 (VM 밖에서, HTTPS 배포 전) | 읽는 법 |
|---|---|---|
| 80 | 연결됨 (0.2초) | 스택이 떠 있습니다 |
| 8000 | 연결됨 (0.2초) | **대조군.** VM 까지 도달하는 경로가 살아 있습니다 |
| 8100 | 타임아웃 (8.0초) | 거부가 아니라 타임아웃 - 방화벽이 패킷을 조용히 버립니다 |

재현한 명령입니다. 파이썬 소켓을 쓴 것은 `curl` 이 타임아웃과 거부를 같은 종료 코드로
돌려주어 **둘을 구분할 수 없기** 때문이고, 이 판정은 그 구분이 전부입니다.

```python
s = socket.socket(); s.settimeout(8)
try: s.connect((IP, port))          # 연결됨
except socket.timeout: ...          # 방화벽이 버림
except OSError: ...                 # 거부 - 방화벽은 통과, 듣는 쪽이 없음
```

`8.0초` 는 관측치가 아니라 위 `settimeout(8)` 에 걸린 값입니다. 그보다 오래 기다리면 더
길어졌을 뿐이고, 판정에 쓰는 것은 시간이 아니라 **어느 예외로 끝났는가**입니다.

**거부와 타임아웃의 구분이 판정의 전부입니다.** 8000 이 즉시 붙는데 8100 만 8초를 기다리다
끊긴다면, 원인은 "안 떠 있음"이 아니라 "닿지 못함"입니다.

**이 측정은 다시 할 수 없습니다.** 같은 날 늦게
[ADR-0016](../adr/0016-HTTPS_종단_지점과_인증서_발급_경로.md) 이 배포되면서 8000 이 루프백
바인딩으로 바뀌어(`infra/docker-compose.yml` 의 `127.0.0.1:8000:8000`) 대조군이 사라졌습니다.
위 표의 판정은 8000 이 "연결됨" 이어야 성립하므로, **재현 불가입니다.**

배포 뒤에 같은 자리에서 다시 쟀습니다.

| 포트 | 결과 (VM 밖에서, HTTPS 배포 후) | 읽는 법 |
|---|---|---|
| 80 | 연결됨 | HTTPS 리다이렉트 |
| 443 | 연결됨 | **HTTPS 가 살아 있습니다** |
| 8000 | 거부 | 방화벽은 통과했는데 듣는 쪽이 없습니다 - 루프백 바인딩이 동작합니다 |
| 8100 | 타임아웃 | 방화벽이 패킷을 버립니다 (변동 없음) |

**8000 의 "거부" 가 루프백 바인딩의 직접 증거입니다.** 이 VM 의 8000 은 우리가 만들지 않은
태그 없는 규칙으로 방화벽이 열려 있는데도 연결이 거부되었으므로, 컨테이너가 외부 인터페이스에
붙어 있지 않다는 뜻입니다. 8100 은 방화벽이 먼저 막아 같은 방식으로는 구분되지 않습니다 -
아래 "바인딩 자체" 를 따로 적어 두는 이유입니다.

아래 "08-19 HTTPS 종단" 기록의 8000 서술은 **이 시점 이후의 값**입니다.

##### 바인딩 자체 - DoD 의 나머지 절반

위까지는 "밖에서 닿지 않는가" 만 잰 것이고, DoD 는 조건이 둘입니다. **`127.0.0.1:8100:8100`**
과 **외부에서 8100 접근 불가**. 밖에서 재는 것으로는 앞쪽이 확인되지 않습니다 - 컨테이너가
`0.0.0.0:8100` 에 붙어 있어도 방화벽이 막으면 똑같이 타임아웃이기 때문입니다. 두 상태가
구분되지 않는 것이고, 그 차이는 우리가 만들지 않은 방화벽 규칙이 하나 바뀌는 날 드러납니다.

그래서 VM 안에서 **실제로 도는 컨테이너의 바인딩**을 따로 확인했습니다.

```
$ docker compose -f infra/docker-compose.yml ps --format 'table {{.Service}}\t{{.Ports}}'
SERVICE     PORTS
ai-engine   127.0.0.1:8100->8100/tcp
backend     127.0.0.1:8000->8000/tcp
caddy       0.0.0.0:80->80/tcp, [::]:80->80/tcp, 0.0.0.0:443->443/tcp, [::]:443->443/tcp, 443/udp, 2019/tcp
frontend    80/tcp
```

**선언이 아니라 런타임 값입니다.** compose 파일에 `127.0.0.1:` 이 적혀 있는 것과 그렇게 떠
있는 것은 다른 주장이고, 이 출력이 뒤쪽입니다. 이로써 DoD 두 조건이 모두 확인됐습니다.

함께 읽히는 것 셋입니다.

- `frontend` 와 `caddy` 의 `443/udp` `2019/tcp` 에는 호스트 바인딩이 없습니다. 프론트엔드는
  프록시 뒤로 들어갔고, HTTP/3 용 UDP 와 Caddy 관리 엔드포인트는 발행하지 않았습니다
  ([ADR-0016](../adr/0016-HTTPS_종단_지점과_인증서_발급_경로.md)).
- `caddy` 만 `0.0.0.0` 입니다. 밖에서 보이는 문이 하나라는 뜻입니다.
- 이 확인은 **앞으로도 재현 가능합니다.** 밖에서 재는 쪽과 달리 대조군이 필요 없습니다.

#### 2. `brief:fill` 열화 - 실물을 끄고 확인했습니다

구현은 S2 에 이미 들어와 있었고 단위 테스트도 있었습니다. 다만 그 테스트는 **가짜 엔진**이라
DoD 의 "ai-engine 을 끈 상태에서"를 만족한다고 볼 수 없어, 컨테이너를 실제로 정지시키고
대조군과 함께 다시 쟀습니다.

| | 엔진 살아 있음 | **엔진 정지** | DoD |
|---|---|---|---|
| HTTP | 201 | **201** | 201 |
| `state` | `brief_ready` | **`brief_filling`** | `brief_filling` |
| `messageMode` | `normal` | **`degraded`** | `degraded` |
| `needsInput` | 없음 | 없음 | 열화와 정보 부족을 가르는 키 (없어야 정상) |

`category` 와 `target` 은 빈 문자열로 왔습니다 - 계약의 "`null` 금지"와 일치합니다.

소요는 4.06초였고, 여기서 말할 수 있는 것은 **상한 15초를 기다리지 않았다**는 것뿐입니다
(`brief_fill_timeout_s`). 잰 값은 `POST /v1/sessions` **요청 전체의 왕복**이라 600x600 PNG
업로드와 저장, 세션 생성이 모두 들어 있습니다. 이음매 호출만 따로 잰 것이 아니므로 "연결
거부가 즉시 돌아온다" 의 근거로는 쓸 수 없습니다 - 연결 거부 자체는 밀리초 단위입니다.

재현한 절차입니다. 대조군을 먼저 찍고 엔진을 내린 뒤 같은 요청을 반복합니다.


### 08-19 보존 기간 정리 배치 - 기간이 문서 밖으로 나왔습니다 (임동규)

08-25 항목을 당겨왔습니다. `brief:fill` 열화가 이미 충족돼 08-20 ~ 21 이 비었고, 08-26 에 세
항목이 몰려 있어 덜어낼 필요가 있었습니다.

**들어오기 전까지 이 정책은 글이었습니다.** 세션_보관_정책 2절이 "만료된 데이터는 삭제하는
코드가 있어야 합니다. 기간을 문서에만 적어 두면 아무것도 지워지지 않습니다" 라고 적어 두었는데,
그 코드가 없었습니다. 계약이 "만료된 사진은 빈 문자열" 이라고 약속하고
([API_계약.md](../기술문서/API_계약.md) 8.4절) 만료 자체가 일어나지 않던 상태입니다.

| 무엇 | 어디 |
|---|---|
| 무엇을 지우나 (순수 함수, 서버 없이 시험 가능) | `backend_core/retention.py` |
| 언제 도나 (같은 프로세스의 배경 작업, ADR-0015 와 같은 갈래) | `api/sweeper.py` |
| 기간과 주기 (정책이 "설정값" 이라고 못박은 것) | `ADGEN_RETENTION_*`, `ADGEN_SWEEP_*` |

#### 설계에서 걸린 것 하나

**세션 기한과 계약 약속이 어긋납니다.** 세션은 생성 후 7일, 결과 이미지는 `expiresAt` 까지인데,
6일째에 렌더한 세션은 7일째에 지워지면서 아직 6일이 남은 결과를 함께 가져갑니다. 잡이 사라지면
결과는 모두에게 404 이므로(INV-9), 우리가 공표한 시각보다 먼저 링크가 죽습니다.

**늦은 쪽을 따르기로 했습니다.** 세션은 자기 기한과 결과 약속 중 나중까지 남습니다. 기간표를
지키려다 계약을 어기는 것보다 낫다고 봤습니다 - 기간표는 우리끼리의 약속이고 `expiresAt` 은
이미 클라이언트에게 나간 값입니다.

#### 확인한 것

테스트 7개이고, **통과만으로는 아무것도 증명하지 않으므로** 위 규칙을 지우고 돌려 봤습니다.
`_deadline` 에서 결과 약속을 빼니 해당 테스트가 `assert 1 == 0` 으로 실패합니다.

- 사진: 23시간에는 남고 25시간에는 파일과 참조가 함께 사라집니다.
- **빈 문자열로 바꿔도 `revision` 과 `updated_at` 은 그대로입니다.** 배치는 사용자 편집이 아닙니다 -
  `revision` 이 움직이면 열려 있던 화면의 다음 patch 가 설명할 수 없는 충돌로 실패하고,
  `updated_at` 이 움직이면 새벽에 배치가 돌았다는 이유로 남의 세션 목록 순서가 바뀝니다.
- 세션: 8일째에 잡과 파일까지 함께 지워집니다.
- 두 번 돌려도 두 번째 패스는 아무것도 하지 않습니다(시작할 때 한 번 + 주기마다이므로 정상 상황).

**로그 30일은 이 배치의 대상이 아닙니다.** 표준 출력으로 나가 컨테이너 런타임이 들고 있고,
SQLite 안에 지울 로그 저장소가 없습니다. 회전은 배포 쪽 소관으로 남깁니다.

#### 리뷰가 잡아 준 것 (PR #132, 신호정)

재현까지 붙은 결함 둘이 나왔습니다. 둘 다 **이 배치가 막으려던 실패와 같은 종류**입니다.

- **렌더 중인 세션을 지우면 결과 파일이 영구 고아가 됩니다.** 아직 결과가 없는
  `queued` / `running` 잡은 기한 계산에 들어가지 않아, 배치가 세션과 잡 행을 지우고 워커가
  그 뒤에 파일을 씁니다. 그 파일을 가리키는 행이 없으니 **이후 어떤 패스도 수거하지
  못합니다** - 기간 없이 생성물을 쌓지 말라는 것이 이 배치의 존재 이유인데 배치 자신이 그
  경로가 됩니다. 미종료 잡이 있는 세션은 통째로 건너뛰도록 고쳤습니다. 다음 패스가 가져갑니다.
- **사진 비우기가 동시 편집을 덮어씁니다.** 배치는 패스 시작 시점에 전 세션을 읽고 한참 뒤에
  쓰는데, 그 사이 사용자가 저장하면 **200 을 받은 편집이 조용히 사라집니다.** `save` 가
  `Precondition` 을 필수로 둔 바로 그 창입니다. UPDATE 에 읽을 때의 `revision` 조건을 붙이고,
  0행이면 이번 패스를 건너뛰도록 했습니다.

**사진의 실제 보존이 최대 48시간이었습니다.** 만료 판정 24시간에 배치 주기 24시간이 더해지는데,
표는 24시간을 약속합니다. 기본 주기를 1시간으로 줄여 상한을 25시간으로 낮췄고, "이때부터 지워도
된다이지 이때 지워진다가 아니다" 를 정책 2절에 적었습니다. 한 패스가 수십 행을 훑는 일이라
주기를 줄이는 비용이 개인정보를 두 배로 오래 들고 있는 비용보다 훨씬 쌉니다.

**`RESULT_RETENTION` 만 설정값이 아니었던 것도 함께 고쳤습니다.** 후속으로 미뤄도 된다고
하셨지만 `run_one` 에 인자 하나를 더하는 일이라 지금 했습니다. 그대로 두면
`ADGEN_RETENTION_SESSION_D` 를 줄여도 렌더된 세션에는 효과가 없어(늦은 쪽을 따르므로) VM
실측에서 배치가 고장 난 것처럼 보였을 항목입니다.

회귀 테스트 4개를 더했고, 두 가드를 지워 보니 정확히 그 4개가 깨집니다.

**남은 것은 VM 실측입니다.** 주기가 1시간이라 배포된 스택에서 한 시간 안에 도는 것을 볼 수
있지만, 사진 만료를 보려면 기간을 줄여 한 번 확인하는 편이 빠릅니다.

### 08-19 SQLite 백업 - 뜨는 것과 되돌리는 것을 모두 확인했습니다 (임동규)

08-26 항목을 당겨왔습니다. 실물 엔진과 무관하고 다른 것에 걸리지 않아 지금 할 수 있는
작업이었습니다. `scripts/backup-db.sh` 이고 절차는 [infra/README.md](../../infra/README.md)
"상태 파일 백업" 절에 있습니다.

**확인하지 않은 백업은 없는 백업과 값이 같습니다.** 그래서 스크립트가 뜬 직후 파일을 열어
`integrity_check` 와 계정 건수를 찍고, 저도 복원까지 실제로 돌려 봤습니다.

| 확인한 것 (2026-08-19, 로컬 스택) | 결과 |
|---|---|
| `VACUUM INTO` 로 살아 있는 스택에서 사본을 뜨는가 | 뜹니다. `integrity_check ok`, 계정 2건 |
| 복원이 실제로 시점을 되돌리는가 | 백업 이후에 만든 세션이 사라지고 이전 세션만 남습니다 |
| 복원 뒤 스택이 정상인가 | healthy, 로그인 200 (= 상태 파일에 쓰기가 됩니다) |

#### 실측으로 잡은 함정 하나

**첫 복원은 성공한 것처럼 보이고 스택만 안 떴습니다.** busybox 의 `cp` 가 대상 파일을 지우고
새로 만들어 결과가 root 소유가 되는데, 앱은 비루트(`appuser`, uid 10001)라 다음 기동이
`attempt to write a readonly database` 로 죽었습니다. 복원 로그는 전부 초록이고 데이터도
제대로 돌아가 있어서, **증상만 보면 복원과 무관해 보입니다.**

`cat >` 로 기존 파일에 그대로 쓰도록 고쳤습니다. inode 와 소유권이 유지됩니다. uid 를 스크립트에
적지 않고 `/data` 의 소유자를 따라가게 한 것은, 적어 두면 Dockerfile 과 두 곳이 되고 갈라지는
날 같은 증상이 돌아오기 때문입니다.

#### 리뷰가 잡아 준 것 (PR #133, 신호정)

**복원 직전의 사전 백업이 복원 원본을 지울 수 있었습니다.** 백업이 상한만큼 쌓인 뒤 가장
오래된 것으로 되돌리려 하면, 사전 백업이 하나 늘어난 상태에서 정리가 돌아 그 파일이 사라집니다.
삭제는 스택을 내리기 전이고 파일을 읽는 것은 내린 뒤라 **원본이 없는 채로 서비스가 죽습니다.**
지금 무증상인 이유는 백업이 아직 상한에 안 찼기 때문이고, cron 이 도는 2주 뒤부터 성립합니다.
복원 중에는 아무것도 지우지 않도록 고쳤고, 상한을 3으로 낮춰 재현과 해소를 모두 확인했습니다.

**볼륨 이름을 손으로 적던 것도 없앴습니다.** 도커는 없는 이름의 볼륨을 조용히 새로 만들기
때문에, 오타가 나면 엉뚱한 빈 볼륨에 복원해 놓고 "완료" 를 찍습니다. `compose run` 으로 서비스
정의의 볼륨을 그대로 쓰도록 바꾸면서 `docker run` 과 `alpine` 의존이 함께 사라졌고, 덤으로
**스택이 죽어 있어도 백업과 복원이 됩니다** - 목록을 보고 싶은 때와 복원하고 싶은 때가 대개
그런 때입니다.

넣는 방식도 stdin 으로 바꿨습니다. 호스트가 읽고 컨테이너가 쓰므로 위의 소유권 함정과
좁혀 둔 백업을 컨테이너가 못 읽는 문제가 **둘 다** 사라집니다 (컨테이너 사용자는 그 파일의
소유자도 그룹 구성원도 아닙니다).

복원 구간에 `ERR` 트랩도 걸었습니다. 그 사이에 실패하면 서비스가 내려간 채로 끝나기 때문입니다.

#### 남긴 제약

- **이미지 파일은 백업에 없습니다.** 상태 파일만입니다. 사진은 24시간, 결과는 7일이면 어차피
  사라지므로(세션_보관_정책 2절) 백업이 그 기간을 우회하게 됩니다. ADR-0010 이 "두 경로의
  복사" 라고 적어 둔 부분과 어긋나므로 근거를 ADR 로 남겼습니다
  ([ADR-0018](../adr/0018-백업_대상은_상태_파일뿐입니다.md)).
- **사본은 볼륨 밖으로 곧장 씁니다.** 백업 디렉토리를 컨테이너에 `/backup` 으로 붙이고
  `VACUUM INTO` 가 거기에 씁니다. `/data` 에 만들면 그것이 곧 백업 대상 볼륨이라 다음 백업이
  지난 백업을 품습니다.
- **백업 파일은 0640 입니다.** `umask 077` 은 컨테이너가 만드는 파일에 적용되지 않으므로
  뜬 직후 `chmod` 로 좁힙니다. 0600 이 아닌 이유는 cron 이 한 사람의 crontab 에 걸리기
  때문입니다 -- 0600 이면 그 사람만 복원할 수 있고, `/srv/adcraft` 를 공용 경로로 세운
  전제와 부딪힙니다 (PR #133 리뷰, 신호정).
- **cron 등록은 VM 에서 손으로 해야 합니다.** `crontab -e` 한 줄이며 명령은 README 에 있습니다.

### 08-20 needsInput 재추론을 배선했습니다 (임동규)

**계약이 약속한 것을 서버가 지키지 않고 있었습니다.** `openapi.yaml` 의 `PATCH .../brief` 가
"`needsInput`이 걸린 세션에서 `note`를 채우면 서버가 추론을 다시 시도합니다" 라고 적었는데,
그 라우트는 엔진을 부르지 않고 값만 병합했습니다.

증상이 조용합니다. `category` 와 `target` 은 추론이 채우는 자리이고 그 경로에 다른 필자가
없으므로 사용자가 아무리 써도 빈 채로 남습니다. `brief_filling -> brief_filling` 은 합법
간선이라 응답은 200 이고, **화면은 같은 질문을 무한히 반복**합니다.

**스텁이 `needsInput` 을 내지 않는 동안에는 도달할 수 없었습니다.** #145 로 `brief:fill` 이
실물이 된 날(08-20) 도달 가능해졌습니다.

| 무엇 | 어디 |
|---|---|
| 재추론 조건 판정 | `session_flow.wants_refill` |
| 병합과 재추론 결과 반영 | `session_flow.merge_brief_patch`, `apply_brief_patch(refill=...)` |
| 엔진 호출과 사진 되읽기 | `api/routes/sessions.py` 의 `_refill_brief` |

동작 표는 [API_계약.md](../기술문서/API_계약.md) 2.1절에 넣었습니다. 판단이 갈린 자리 셋만
여기 적습니다.

- **`needsInput` 세션에서만, 그리고 추론이 읽는 필드를 건드릴 때만 부릅니다.** 매 patch 마다
  부르면 화면이 편집할 때마다 유료 호출이 나갑니다. `artStyle` 은 `brief:fill` 의 입력이
  아니므로 같은 답을 다시 사는 셈입니다.
- **사진을 디스크에서 되읽습니다.** 브리프 patch 는 사진을 싣지 않는데 `brief:fill` 은 글과
  사진을 함께 봅니다. 사진이 만료됐으면 글만 보내지 않고 "돌지 못함" 으로 처리합니다 - 다른
  질문의 답을 모델의 판단으로 기록하게 되기 때문입니다.
- **돌지 못했으면 `degraded` 로 내리고 `needsInput` 을 지웁니다.** 계약이 두 경우를 그 키
  하나로 가르고 있고(`needsInput` = 돌았는데 판단 못 함, `degraded` = 돌지 못함), 지우지
  않으면 화면이 이제 아무 데도 닿지 않는 메모를 계속 요구합니다. `degraded` 는 출구가 문서에
  있는 상태입니다 - 사용자가 두 값을 직접 채웁니다.

**닫히지 않은 것을 분명히 적습니다.** 재추론도 실패했을 때 계약은 422 `INSUFFICIENT_INPUT` 과
`failed` 를 약속하는데 그렇게 하지 않았습니다. **몇 번 만에 포기하는가**가 미결정_대장 B-11 이고
확정 근거가 회의록이라 코드가 숫자를 먼저 정할 수 없습니다. 회귀 시험 하나가 이 자리를 지금
모습 그대로 고정해 두었으니, 숫자가 정해지는 날 그 시험이 깨지면서 알려 줍니다.

회귀 시험을 더했고, 가드를 하나씩 지워 보니 매번 의도한 시험이 깨졌습니다.

**리뷰가 출구 두 개를 더 찾았습니다** (PR #148, 신호정). 둘 다 "이 PR 이 만든 출구가 특정
조건에서 닫힌다" 는 같은 모양이었습니다.

- **사진이 재추론 도중에 사라지면 500.** 파일을 찾는 것과 여는 것이 다른 호출인데 여는 쪽이
  `try` 밖이었습니다. 정리 배치가 같은 프로세스의 타이머로 도므로 그 사이에 끼어들 수 있고,
  창이 가장 넓은 때가 정확히 24시간 - 어제의 `needsInput` 에 답하는 사람이 가장 많은 때입니다.
- **장애를 한 번 겪은 세션이 재추론 자격을 영구히 잃음.** 돌지 못한 재추론이 `needsInput` 을
  지우는데 재추론 조건이 `needsInput` 만 보고 있었습니다. 엔진이 1초 뒤 살아나도 그 사용자는
  자동 채움을 다시 받지 못하고 화면에는 표시가 없습니다. 제가 그 자리에 적어 둔 근거("stampede
  방지")는 결과를 설명하지 못했습니다 - 정상 세션은 어차피 매번 재추론이 걸리므로, 실제로
  막힌 것은 이미 한 번 다친 세션뿐이었습니다.

값이 바뀌지 않은 patch 도 유료 호출을 내던 것(같은 메모 3회 저장에 호출 3건)도 함께 고쳤습니다.

### 08-21 잡 동시 실행 상한 — 이미 있었고, 없던 것은 그 근거였습니다 (임동규)

**결론: 새 설정값을 만들지 않습니다.** N9(렌더 직렬 1건)가 이미 상한 역할을 합니다.

규칙이 워커 루프가 아니라 **저장소**에 있습니다.

```python
# backend_core/jobs.py
def next_queued(connection):
    running = connection.execute("SELECT 1 FROM jobs WHERE status = 'running' LIMIT 1").fetchone()
    if running is not None:
        return None
```

`api/worker.py` 주석이 이유를 적어 두었습니다 — "a rule kept in a loop stops being a rule the
moment a second loop exists". 그리고 backend 는 `CMD ["uvicorn", ...]`, 즉 `--workers` 없는
**단일 프로세스**입니다. 따라서 외부 호출 동시성의 천장은 **잡 1건 x 칸 5건 = 5** 로 고정이고,
사용자가 몰리면 곱해지는 대신 큐가 자랍니다.

⚠️ **확인 도중에 나온 것: 그 보장의 전제가 어디에도 적혀 있지 않았습니다.**

`next_queued` 의 확인과 `run_one` 의 `mark_running` 은 **두 문장이지 하나가 아닙니다.**
프로세스가 하나라 지금은 그 사이가 겹칠 수 없지만, 누군가 `--workers 2` 를 넣으면 — 성능
개선으로 보이는 한 줄입니다 — 두 프로세스가 같은 확인을 통과해 **같은 잡을 함께 렌더합니다.**
요금이 곱으로 나가고, INV-3(세션당 렌더 1회)이 깨지고, 결과 파일을 서로 덮어씁니다.
**에러는 나지 않습니다.** `storage.py` 에 "one worker, one serial render" 라는 말이 있지만
그것은 커넥션 전략의 근거이지 배포 제약으로 적힌 것이 아니었습니다.

**그래서 claim 을 원자적으로 바꾸는 대신 전제를 고정했습니다.** 배포가 한 프로세스 한 GPU 인
동안은 없는 문제이고, 위험은 "코드가 틀렸다"가 아니라 "전제를 모른 채 한 줄 고친다"이기
때문입니다. 두 곳에 적었습니다.

- `apps/backend/Dockerfile` — `CMD` 바로 위에 `--workers` 금지와 그 이유
- `backend_core/jobs.py` `next_queued` docstring — 단일 프로세스 전제와, 원자적 claim 을
  일부러 넣지 않았다는 것

**다시 열어야 하는 조건**은 셋입니다. 프로세스를 늘릴 때, 큐가 자라는 거동이 문제가 될 때,
그리고 품질 티어를 `medium` 위로 올릴 때(개별 호출 팽창이 커져 병렬의 이득이 줄어듭니다 —
미결정_대장 N19-a).

⚠️ **벤더의 요청 수 제한은 여전히 모릅니다.** 실측에서 429 는 0건이었지만 표본이 티어당
1세트입니다. 확인하지 못한 채로 간다면 그 사실이 문서에 남아야 한다는 N19-a 의 조건은
아직 충족되지 않았습니다.

발동했을 때만 경고 한 줄이 나오므로 **로그가 조용한 것과 설정이 안 읽힌 것을 구별할 수 없습니다.**

문서에는 옛 이름 표와 대조 명령을 함께 넣었습니다. `.env.example` 에 없는 이름만 출력되므로
오타에도 걸립니다.

⚠️ **실측 범위**: 파싱 쪽만 확인했습니다(`.env.example` 28개 키). 이 PC 에 `infra/.env` 가 없어
두 파일 비교 자체는 고정 파일로만 돌려 봤습니다 — 옛 이름과 오타를 둘 다 잡는 것은 확인했습니다.

**먼저 재배포했습니다.** VM 이 `e68d947`(#153) 에 머물러 있어 17 커밋 뒤처져 있었고,

#### 재부팅 복구 - 통과

```
uptime                    00:59:47 up 0 min
docker ps                 4개 전부 Up 14 seconds (healthy)
deploy-vm.sh --check      8줄 전부 OK
crontab -l                남아 있음
```

**손을 대지 않았습니다.** `restart: unless-stopped` 와 도커 데몬 자동 기동이 알아서 올렸고,
볼륨도 그대로였습니다(계정 2건, 세션 5건, 잡 4건, 이미지 8개 - 재부팅 전 값과 동일).

⚠️ **다만 헬스체크가 하는 일과 안 하는 일이 갈립니다.** `restart: unless-stopped` 는
**프로세스가 죽었을 때만** 재시작합니다. 컨테이너가 `unhealthy` 로 떨어져도 도커는 아무것도
하지 않고 알림도 없습니다 - 살아는 있는데 응답을 못 하는 상태면 사람이 `docker ps` 를 볼
때까지 방치됩니다. 이번 검증이 덮지 못한 자리이고, 붙일지는 정해진 것이 없습니다.

#### 백업 cron - 등록하고 **실제로 도는 것까지** 봤습니다

`/srv/adcraft/backups` 를 만들고(setgid 와 ACL 이 상속되어 `drwxrws---+ :adcraft`),
README 의 한 줄을 `crontab -` 로 등록했습니다. `crontab -e` 는 인터랙티브라 못 씁니다.

**등록만 하고 끝내지 않았습니다.** 03:17 을 기다리는 대신 같은 명령을 3분 뒤로 임시
등록해 **진짜 cron 이 실행하는 것을 확인**하고 지웠습니다:

```
00:49  cron-probe.log
       ==> 정합 사본 뜨는 중 (/data/adgen.sqlite)
       ==> 확인: integrity_check ok, 계정 2건, 44K
```

그 전에 `env -i ... PATH=/usr/bin:/bin` 로 cron 의 빈약한 환경도 흉내 내 봤습니다.
`docker compose` 가 그 PATH 에서 찾아지는지가 이 한 줄의 유일한 위험이었습니다.

백업 파일 권한도 설계대로였습니다 - `-rw-r----- spai1029:adcraft`. 그룹 읽기가 남아
있으므로 장애 때 VM 에 붙은 사람이 제가 아니어도 복원할 수 있습니다.

#### N3 - 지적이 맞았고, 고치는 법까지 확인했습니다

PR #133 리뷰에서 02 가 낸 물음입니다: 백업이 `--user "$(id -u)"` 로 도는데 그 사용자는
uid 10001 소유 DB 를 읽기로만 열 수 있고, **저널 복구에는 쓰기가 필요하다**.

VM `/tmp` 에서 재현했습니다(프로덕션 볼륨은 건드리지 않았습니다):

```
저널 헤더 매직   d9d505f920a163d7   (유효한 hot journal, 9.1MB)
소유자 10001, 파일 644, 디렉토리 755
백업 사용자(1022) 로 VACUUM INTO   ->  attempt to write a readonly database
소유자(10001) 로 한 번 열기        ->  행 20000, 저널 파일 사라짐
다시 백업 사용자로                 ->  성공, 9134080 바이트
```

행 수 20000 이 회수가 제대로 됐다는 증거입니다 - 죽기 전 트랜잭션이 되돌려진 상태입니다.

⚠️ **재현 조건이 좁습니다.** 한 행짜리 트랜잭션 도중에 죽인 1차 시도는 저널이 남아도 백업이
**성공했습니다.** 캐시를 좁혀 페이지가 실제로 DB 파일로 흘러넘친 뒤 죽여야 실패합니다.
경계가 어디인지는 재지 않았으므로 "저널만 있으면 항상 실패한다" 로 옮기면 안 됩니다.

**왜 나쁜가**는 메시지입니다. `verify` 가 이미 "권한 문제와 손상을 구별하지 못하는
`unable to open database file`" 을 막아 두었는데, 이건 **그 앞 단계**에서 같은 종류의
혼동을 만듭니다. 크래시 루프 중 사전 백업을 뜨려는 사람이 `readonly database` 를 보면 백업
대상이 깨진 것으로 오진합니다.

수정은 `do_backup` 앞에 저널 회수 한 단계입니다. `--user` 를 주지 않으면 이미지 기본
사용자로 돌아 쓰기로 열리고, 여는 것만으로 회수가 끝납니다. 저널이 없으면 컨테이너만 한 번
뜨고 빠집니다.

#### 보존 배치 - 시계가 지나가는 것을 지켜봤습니다

VM 에 만료 직전 데이터가 걸쳐 있어 그대로 기다렸습니다. **기준은 파일 mtime 이 아니라
세션의 `createdAt`** 이고, 스위퍼는 기동 직후 한 번 그다음 1시간마다 돕니다.

첫 기회는 빗나갔습니다. 스윕이 `01:59:37`, 가장 오래된 세션이 `01:59:55.888` -
**18초 차이로 아무것도 안 지웠습니다.** 이것 자체가 나이 기준으로 판정한다는 증거입니다.

다음 틱에서 전부 지워졌습니다:

```
2026-08-22 02:59:40  INFO backend_core.retention
  retention sweep removed photos=4 results=0 sessions=1
```

이미지 8개 -> 3개. 남은 셋은 08-21 결과라 08-28 만료입니다.

⚠️ `results=0` 을 미리 1 로 예상했는데 틀렸습니다. 세 루프가 **서로 다른 것을 셉니다** -
08-15 결과 파일은 세션이 통째로 지워지면서 `_drop_session` 이 데려갔고, `results` 는
"세션은 살아 있는데 `expiresAt` 이 지난 결과" 를 세는 자리라 0 이 맞습니다.

**이 한 줄이 네 가지를 동시에 증명합니다**: 배치가 사람 없이 스스로 돈다, 나이 기준으로
판정한다, 파일과 행을 함께 지운다, 그리고 **#181 의 파일 로그가 배포와 재부팅을 넘어
볼륨에 남는다**. 마지막 것이 30일 보존 약속의 첫 실증입니다.

⚠️ 반대로 **`obs` 줄은 아직 0건입니다.** 배포 이후 아무도 서비스를 쓰지 않아 이음매가 돈
적이 없습니다. 즉 `scripts/observe.py` 는 여전히 실제 로그에 대고 돌려 본 적이 없습니다.

로그가 디스크를 채울까 싶어 재 봤는데 **위협이 아니었습니다.** 기동 후 1시간 32분 동안
