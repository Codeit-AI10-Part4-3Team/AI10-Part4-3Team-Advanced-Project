# ADR-0001: 모노레포 채택 — 단, AI는 독립 배포 가능한 모듈로 유지

- **상태**: Accepted
- **날짜**: 2026-08-01 (리포 준비 시점 채택 / 2026-08-04 착수 회의에서 팀 재확인)
- **결정자**: AI10-Part4-3Team

> 템플릿이 내려 둔 결정을 이 프로젝트가 **그대로 채택**했습니다. 다른 구조를 택하게 되면
> 이 문서를 고치지 말고 새 ADR로 대체(`Superseded by`)하세요 — 왜 바꿨는지가 남아야 합니다.
> 학습 파이프라인을 `apps/` 밖에 둔 후속 결정은 [ADR-0002](0002-학습_파이프라인_배치.md)입니다.

## 배경

AI 프로젝트의 레포 구조는 보통 두 갈래로 갈립니다.

- **멀티레포**: 서비스별로 레포를 나누고 org로 묶는 구성. "AI가 독립 모듈"이라는 인상이 강함.
- **모노레포**: 하나의 레포에 앱을 폴더로 두는 구성.

수상작·오픈소스 레포 조사에서 반복 확인되는 **본질**은 "레포를 여러 개로 쪼갠다"(형식)가 아니라
**"AI를 인라인 API 호출이 아니라 독립적으로 배포 가능한 엔진/모듈로 두고, 배포·운영을 README에
문서화한다"**(실질)였습니다. 형식과 실질을 구분하는 것이 이 결정의 출발점입니다.

한편 소규모 팀·단기 일정에서는 멀티레포의 비용이 큽니다: 문서·인프라 설정 중복, cross-repo PR
조율, 신규 참여자 온보딩 부하, 그리고 계층을 가로지르는 변경이 원자적으로 머지되지 않는 문제.

## 검토한 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 멀티레포 + org | 배포 단위 분리가 물리적으로 강제됨 | 조율 비용·중복·통합 부채. 소규모 단기 팀에서 이득보다 큼 |
| 모노레포 (단일 앱) | 가장 단순 | AI가 인라인 모듈로 섞여 "독립 배포" 실질을 잃음 |
| **모노레포 + 앱별 배포 단위** | 원자적 변경 + 독립 배포 실질 동시 확보 | 경계를 **규약과 CI로** 지켜야 함(물리적 강제 없음) |

## 결정

**단일 모노레포**를 쓰되, `apps/ai-engine/`을 자체 `pyproject.toml`·`Dockerfile`·README를 가진
독립 배포 단위로 유지합니다.

경계는 물리적으로 강제되지 않으므로 다음으로 대신합니다:

- `CODEOWNERS` + 브랜치 보호로 폴더별 소유권 분리
- **앱 간 파이썬 import 금지** 규약 (허용된 결합은 `packages/contracts`의 HTTP 계약뿐)
- `docker-build.yml`이 앱 디렉토리를 빌드 컨텍스트로 이미지를 만들고 `/health`까지 확인 —
  "독립 배포 가능"이 주장이 아니라 회귀 검사 대상이 됨

## 결과

**생기는 제약**

- `apps/ai-engine`에서 `backend_core`/`api`를 import하면 안 됩니다(역도 동일). 이 한 줄이
  결정의 전제를 조용히 무너뜨립니다.
- Docker 빌드 컨텍스트를 레포 루트로 넓히면 안 됩니다 — 넓히는 순간 상대 앱 소스를 참조할 수
  있게 됩니다.
- 앱을 추가하면 함께 고쳐야 하는 곳이 있습니다: 루트 `pyproject.toml`의 ruff `src`,
  `ci.yml`의 matrix, `scripts/setup-github.sh`의 `contexts`, `CODEOWNERS`.

**쉬워지는 것**: 계층을 가로지르는 변경이 PR 하나로 원자적으로 들어갑니다. 문서·인프라·env가
한 곳에 있어 드리프트가 없습니다.

**재검토 신호**: 앱별 배포 주기가 확연히 달라지거나, 팀이 커져 폴더 소유권만으로 충돌이
정리되지 않을 때. 그때는 이 ADR을 고치지 말고 새 ADR로 대체하세요.
