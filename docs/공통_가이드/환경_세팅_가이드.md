# 개발 환경 세팅 가이드

새로 합류한 팀원이 **한 줄 명령으로 개발 환경을 맞추고**, 어긋난 부분을 스스로 진단·복구하기 위한 문서입니다.
저장소 설정(브랜치 보호·라벨·머지 전략)은 admin이 1회만 하는 별도 작업이며 [저장소_운영.md](저장소_운영.md)가 담당합니다.

> **왜 스크립트가 필요한가.** 이 저장소의 품질 게이트는 "명령을 실행했는가"가 아니라 "설정이 실제로 등록됐는가"에 달려 있습니다.
> 예를 들어 `.gitattributes`의 `filter=nbstripout`은 로컬 git config에 필터 드라이버가 없으면 **git이 조용히 무시**합니다 —
> 오류 없이 노트북 출력 셀이 그대로 커밋되고, 그 파일은 이후 영원히 `modified`로 남습니다.
> 같은 이유로 `pre-commit install`만 하고 `--hook-type pre-push`를 빠뜨리면 pytest 게이트가 로컬에서 아예 돌지 않습니다.
> 이런 항목들은 **성공했다고 착각하기 쉬운 실패**라서, 사람이 아니라 스크립트가 확인해야 합니다.

## 1. 5분 퀵스타트

```bash
git clone https://github.com/Codeit-AI10-Part4-3Team/AI10-Part4-3Team-Advanced-Project.git
cd AI10-Part4-3Team-Advanced-Project
```

| OS | 명령 |
|---|---|
| macOS · Linux · WSL · Git Bash | `bash scripts/setup-dev.sh` |
| Windows PowerShell | `powershell -ExecutionPolicy Bypass -File scripts\setup-dev.ps1` |

스크립트는 **진단 → 항목별 확인 프롬프트 → 복구 → 재점검 → 로컬 CI 실행** 순으로 진행하며,
동의하지 않은 항목은 건드리지 않습니다. 검사 로직은 [`scripts/dev_env.py`](../../scripts/dev_env.py) 한 곳에만 있고
두 진입점은 인터프리터를 찾아 넘기는 래퍼입니다(셸/PowerShell 두 벌로 나누면 반드시 드리프트가 나기 때문).

### 옵션

| 옵션 | 용도 |
|---|---|
| `--check` | 진단만. 파일·설정을 일절 바꾸지 않습니다 (CI·타인 PC 점검용) |
| `--yes` | 확인 프롬프트 없이 전부 복구 (자동화·재설치용) |
| `--skip-tests` | 마지막 `run-tests.sh` 실행 생략 |
| `--mode host\|docker\|container` | 환경 유형 지정. 미지정 시 자동 감지 (§4) |

### 종료 코드

| 코드 | 의미 |
|---|---|
| `0` | 정상 |
| `1` | 자동 복구 실패 또는 로컬 CI 실패 |
| `2` | 수동 개입 필요 (전제 조건 미충족, 셸 재시작 필요) |

## 2. 무엇을 검사하는가

`FIX`는 스크립트가 복구할 수 있는 필수 항목, `WARN`은 담당 역할에서만 필요한 선택 항목입니다.

| 코드 | 검사 | 등급 | 수동으로 하려면 |
|---|---|---|---|
| E01 | git 사용 가능 + 저장소 인식 | BLOCK | git 설치 후 clone한 위치에서 실행 |
| E02 | Python 3.12 이상 | BLOCK | `apps/*/pyproject.toml`의 `requires-python`과 동일 |
| E03 | 격리된 파이썬 환경 | FIX | `python3 -m venv .venv` 또는 `conda create -n adgen python=3.12` |
| E04 | 앱 editable 설치 **+ 그 설치가 이 체크아웃을 가리키는지 + 다른 체크아웃이 같이 깔려 있지 않은지** | FIX | `pip install -e "./apps/backend[dev]" -e "./apps/ai-engine[dev]"` |
| E05 | `core.hooksPath` 충돌 없음 | FIX | `git config --unset core.hooksPath` |
| E06 | pre-commit 설치 | FIX | `pip install pre-commit` |
| E07 | pre-commit 훅 등록 **+ 훅이 가리키는 인터프리터가 살아 있는지** | FIX | `pre-commit install` |
| E08 | **pre-push 훅 등록** (같은 인터프리터 확인 포함) | FIX | `pre-commit install --hook-type pre-push` |
| E09 | **nbstripout git filter 등록** | FIX | `pip install nbstripout && python -m nbstripout --install` |
| E10 | pre-commit 훅 환경 캐시 | FIX | `pre-commit install-hooks` |
| E11 | `infra/.env` 존재 + git 무시 | FIX | `cp infra/.env.example infra/.env` |
| E12 | 셸 스크립트 개행(LF) | FIX | `.sh` 삭제 후 재취득, 또는 `setup-dev.ps1` 1회 실행 |
| W01 | gh CLI 인증 | WARN | `gh auth login` (admin만) |
| W02 | docker + compose v2 | WARN | Docker Desktop / docker-ce (인프라) |
| W03 | Node.js | WARN | LTS 설치 (프론트엔드) |
| W04 | e2e 의존성 (`playwright` 모듈까지) | WARN | `pip install -r e2e/requirements.txt` **+ `playwright install`** (QA) |
| W05 | bash 사용 가능 | WARN | Git for Windows 또는 WSL |

> **W04는 모듈만 봅니다.** 브라우저 바이너리(`playwright install`)는 검사하지 않으므로, 모듈이
> 있는데도 `cd e2e && pytest`가 브라우저 없음으로 실패할 수 있습니다. QA는 두 명령을 모두 실행하세요.

**커밋이 막히는데 위 항목이 전부 OK라면 내 PC 문제가 아닐 수 있습니다.** `ruff-sync` 훅은 ruff 핀
네 곳(`.pre-commit-config.yaml`, 두 앱의 `ruff==`, `reviewdog.yml`의 `RUFF_VERSION`)이 어긋나면
저장소 상태 때문에 실패합니다 — 고칠 곳은 환경이 아니라 그 네 파일입니다
([저장소_운영.md](저장소_운영.md) 4-1절).

마지막 단계에서 [`scripts/run-tests.sh`](../../scripts/run-tests.sh)를 실행해 **로컬 게이트와 CI가 같은 결과를 내는지**까지 확인합니다.
여기서 실패하면 환경이 아니라 코드/테스트 문제이므로, 그대로 고치고 커밋하면 됩니다.

이 단계는 CI의 required 잡 셋을 모두 재현합니다 — `ruff` · `mypy` · `pytest`(앱 두 곳)와
`pre-commit run --all-files`(훅 전량)입니다. 뒤쪽은 `training/` · `packages/` · `scripts/` · `e2e/`의
파이썬과 문서 위생, ruff 핀 동기화를 검사하는 **유일한 로컬 지점**입니다.
`ruff-check`가 `--fix`로 도는 훅이라 이 단계에서 파일이 수정될 수 있고, 그때 pre-commit은 실패로
보고합니다 — 수정된 내용을 확인하고 함께 커밋하세요.

> 재현되지 않는 CI 검사는 **gitleaks 전체 트리 스캔** 하나입니다. 훅의 gitleaks는 staged 변경만
> 보도록 고정돼 있어 `--all-files`에서는 아무것도 검사하지 않고, 대신 `ci.yml`이 별도 스텝으로
> 트리 전체를 훑습니다. 로컬 훅은 "새로 넣는 키"를, CI는 "이미 들어가 있는 키"를 막습니다.

## 3. 파이썬 환경 정책 — venv를 강제하지 않습니다

판정 기준은 "`.venv` 폴더가 있는가"가 아니라 **"격리돼 있는가"** 입니다. 아래 셋 모두 통과합니다.

| 환경 | 판정 | 비고 |
|---|---|---|
| `python3 -m venv .venv` | OK | 프로젝트 폴더 안에만 생기고 `.gitignore`에 이미 등록돼 있습니다 |
| conda 전용 env (`conda activate adgen`) | OK | conda 사용자는 venv를 만들 필요가 없습니다 |
| 컨테이너 내부 | OK | 이미지가 격리를 담당 |
| conda **base** | 실패 | 다른 프로젝트와 의존성이 섞입니다 → `conda create -n adgen python=3.12` |
| 시스템 파이썬 | 실패 | 스크립트가 `.venv` 생성을 제안합니다 |

conda 사용자가 conda base 상태로 실행하면 스크립트는 **venv를 자동 생성하지 않고** conda 명령을 안내만 합니다.
conda 위에 venv를 얹으면 인터프리터 상속 관계가 헷갈려 문제 추적이 오히려 어려워지기 때문입니다.

> ⚠️ **"전용"이 조건입니다 - 다른 프로젝트와 같이 쓰는 env는 격리된 것이 아닙니다.**
> 이 저장소는 템플릿에서 파생됐고, 같은 템플릿에서 나온 다른 프로젝트는 `api`, `backend_core`,
> `ai_engine`이라는 **똑같은 최상위 모듈명**을 씁니다. 한 인터프리터에 둘을 editable로 설치하면
> 한쪽이 이름을 가져가고, 진 쪽 저장소의 테스트는 **남의 소스를 import한 채** 돕니다.
> 실패는 `ModuleNotFoundError`가 아니라 `ImportError` · `ValidationError`로 나타나기 때문에
> 환경 문제가 아니라 코드 결함으로 오진하기 쉽습니다. E04가 이 경우를 잡습니다.

> ⚠️ 격리 환경을 새로 만든 직후에는 **셸을 다시 활성화한 뒤 스크립트를 재실행**해야 합니다.
> 자식 프로세스는 부모 셸의 PATH를 바꿀 수 없으므로, 스크립트가 대신 activate 해줄 방법이 없습니다.

## 4. 도커로 개발할 때 — git 훅과 충돌하지 않습니다

혼동하기 쉬운 지점이라 명시합니다. **git 훅은 `git commit`을 실행하는 쪽에서 돕니다.**
컨테이너로 앱을 돌려도 커밋을 호스트에서 한다면, pre-commit·gitleaks·nbstripout은 **호스트에 설치돼 있어야 합니다.**
컨테이너는 파이썬 의존성만 담당합니다. 그래서 검사 항목마다 적용 범위를 나눠 두었습니다.

| 모드 | 감지 방법 | host 항목 (E05~E12: 훅·시크릿) | python 항목 (E03·E04) |
|---|---|---|---|
| `host` (기본) | 기본값 | 필수 | 필수 |
| `docker` | `--mode docker` 또는 `PROJECT_ENV_MODE=docker` | 필수 | **경고로 강등** — 컨테이너가 담당 |
| `container` | `/.dockerenv` 자동 감지 | **생략** — 여기서 커밋하지 않음 | 필수 |

호스트에서 컨테이너로 개발하는 사람은 `--mode docker`를 쓰면 됩니다. editable 설치는 실패로 잡히지 않지만,
IDE 자동완성·mypy를 호스트에서 쓰려면 여전히 설치해 두는 편이 낫습니다(그래서 경고로 남깁니다).
컨테이너 이미지 안에서 `--mode container`로 돌리면 훅 항목이 조용히 생략됩니다.

## 5. 오류 카탈로그

스크립트가 실패하면 `[E09] ... -> docs/공통_가이드/환경_세팅_가이드.md#e09` 형태로 이 절의 항목을 가리킵니다.

<a id="e01"></a>
### E01 — git 없음 / 저장소 아님

`fatal: not a git repository`. 압축 파일로 내려받았거나 clone 위치 밖에서 실행한 경우입니다.
반드시 `git clone`으로 받으세요 — `.git`이 없으면 훅도 gitleaks도 동작하지 않습니다.

<a id="e02"></a>
### E02 — Python 3.12 미만

`apps/*/pyproject.toml`이 `requires-python = ">=3.12"`이고 CI도 3.12로 돕니다.
3.11 이하에서는 editable 설치 자체가 거부됩니다.
conda: `conda create -n adgen python=3.12` / 그 외: python.org 또는 pyenv로 3.12 설치.

<a id="e03"></a>
### E03 — 격리 환경 없음 (시스템 파이썬 / conda base)

전역에 설치하면 다른 프로젝트와 의존성이 충돌하고, 나중에 원인 분리가 불가능해집니다.
§3의 표를 참고해 venv 또는 conda 전용 env를 만든 뒤 **활성화하고 재실행**하세요.

<a id="e04"></a>
### E04 — `ModuleNotFoundError: api` / `backend_core` / `ai_engine`

원인은 셋 중 하나입니다.

1. 환경을 활성화하지 않음 (다른 인터프리터로 실행 중)
2. editable 설치를 안 함 → `pip install -e "./apps/backend[dev]" -e "./apps/ai-engine[dev]"`
3. **`from src.api import ...` 처럼 `src.` 접두어로 import** — src 레이아웃에서는 설치 환경에서 깨집니다.
   `from api import ...` / `import backend_core` / `from ai_engine import ...` 가 정답이며, lint가 잡지 못하는 사각지대입니다.

> ⚠️ 저장소 루트에서 `pip install .` 은 **하면 안 됩니다.** 루트 `pyproject.toml`은 ruff 설정 전용이고 `[project]`가 없습니다.

#### E04 변종 — import는 되는데 남의 저장소가 import되는 경우

E04는 import 가능 여부만이 아니라 **그 모듈이 이 체크아웃에서 왔는지**까지 봅니다.
아래처럼 나오면 인터프리터가 다른 프로젝트와 섞인 것입니다.

```
[ !! ] E04  앱 editable 설치  이 체크아웃 밖을 import 중:
       ai_engine -> /path/to/other-project/apps/ai-engine/src/ai_engine/__init__.py
```

같은 템플릿에서 파생된 프로젝트끼리는 최상위 모듈명(`api` · `backend_core` · `ai_engine`)이
겹칩니다. 한 인터프리터에 둘을 editable로 설치하면 **한쪽이 이름을 통째로 가져갑니다.**
증상이 `ModuleNotFoundError`가 아니라 아래처럼 나오는 것이 이 변종의 특징입니다.

```
ImportError: cannot import name 'Answer' from 'backend_core.models'
  (/path/to/other-project/apps/backend/src/backend_core/models.py)
```

`from`에 찍힌 경로가 이 저장소가 아니라는 점이 유일한 단서이고, 그걸 놓치면 코드 결함으로
오진하게 됩니다. pre-push 훅의 pytest가 이것 때문에 막히는 경우도 같은 원인입니다.

**해결은 이 저장소 전용 환경입니다.**

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e "./apps/backend[dev]" -e "./apps/ai-engine[dev]"
python3 -c "import ai_engine; print(ai_engine.__file__)"   # 이 저장소 경로여야 정상
```

> ⚠️ 공용 env에서 `--fix`로 재설치하면 **이번엔 반대쪽 프로젝트가 깨집니다.** 두 프로젝트가
> 한 인터프리터를 두고 이름을 뺏고 뺏기기 때문입니다. 근본 해결은 env를 나누는 것이지
> 재설치가 아닙니다.

#### E04 변종 2 — 지금은 이기고 있어서 조용한 경우

위 변종은 **진 쪽에서 실행할 때만** 보입니다. 이긴 쪽에서 보면 경로가 자기 체크아웃이라
아무 이상이 없고, 그래서 "해결됐다"고 판단하기 쉽습니다. 실제로는 두 체크아웃이 여전히
같은 `sys.path`에 올라와 있고 승패만 갈린 상태입니다.

승패를 정하는 것은 **설치 순서가 아니라 `.pth` 파일명의 사전순**입니다. editable 설치는
site-packages에 `__editable__.<배포판>-<버전>.pth` 를 만들고, `site.py`가 그 파일들을
정렬된 이름 순으로 읽어 `sys.path`에 붙입니다. 그래서 배포판 이름 첫 글자 하나로 승자가
바뀝니다.

2026-08-22에 conda `ai` 환경에서 실측한 상태입니다.

```
__editable__.adgen_ai_engine-0.1.0.pth        -> .../part4-adcraft-ai/apps/ai-engine/src
__editable__.savers_ai_engine-0.1.0.pth       -> .../savers-project/apps/ai-engine/src
```

`adgen` < `savers` 라서 이 저장소가 이기고 있었고, 반대로 `savers-project` 쪽에서 이
인터프리터를 쓰면 **이 저장소의 소스를 import한 채** 돌고 있었습니다. 어느 한쪽을
`pip uninstall` 하는 순간 남은 쪽이 승자가 되므로, 조용한 상태는 언제든 뒤집힙니다.

E04는 승자 경로만이 아니라 **`sys.path` 위에 우리 모듈명을 제공할 수 있는 모든 디렉토리**를
훑어 이 상태를 잡습니다.

```
[ !! ] E04  앱 editable 설치  다른 체크아웃이 같은 인터프리터에 함께 설치됨:
       /path/to/other-project/apps/ai-engine/src (ai_engine)
```

이 판정에서는 `--fix`가 **의도적으로 아무것도 하지 않고 실패**합니다. 재설치해도 두 항목이
그대로 `sys.path`에 남아 사전순 추첨을 다시 돌릴 뿐이고, 남의 저장소 배포판을 지울지는
도구가 아니라 사람이 정할 일이기 때문입니다. 대신 확인·제거 명령을 출력합니다.

```bash
python3 -m pip list                        # 겹치는 배포판 이름 확인
python3 -m pip uninstall <배포판_이름>      # 이 인터프리터에서 남의 체크아웃 제거
```

> ⚠️ 다른 저장소를 `.venv`로 옮겼다면 그 저장소의 **git 훅도 다시 걸어야 합니다.**
> `pre-commit install`은 훅 스크립트에 인터프리터 절대경로(`INSTALL_PYTHON`)를 박아 두므로,
> `.venv`를 만들기만 하고 재설치하지 않으면 훅은 계속 예전 공용 env에서 돕니다.
> 진단은 [E07](#e07) · [E08](#e08)입니다.

컨테이너 안(`--mode container`)에서는 이 판정을 건너뜁니다. 이미지는 `pip install .`로
**비-editable** 설치하므로 site-packages에 들어가는 것이 정상이고, 애초에 다른 프로젝트가
같이 설치돼 있을 수 없습니다.

<a id="e05"></a>
### E05 — `core.hooksPath`가 설정돼 있음

전역 git 설정에 `core.hooksPath`가 있으면 `.git/hooks/`가 통째로 무시되어 **pre-commit 설치가 무력화**됩니다.
`pre-commit install`은 이 경우 오류를 내며 거부합니다. `git config --unset core.hooksPath`로 해제하세요
(전역이라면 `git config --global --unset core.hooksPath`).

<a id="e06"></a>
### E06 — pre-commit 미설치

`pip install pre-commit`. 다른 환경(conda base 등)의 pre-commit이 PATH에 잡혀 있어도
훅 스크립트에 그 인터프리터 경로가 박히므로, **현재 프로젝트 환경에 설치**하는 편이 안전합니다.

<a id="e07"></a>
### E07 — pre-commit 훅 미등록

`pre-commit install`. 이걸 빠뜨리면 로컬에서는 아무 검사도 돌지 않고 **CI에서만 실패**합니다
(`Pre-commit hooks` 잡은 required check라 머지가 막힙니다).

<a id="e08"></a>
### E08 — pre-push 훅 미등록

`pre-commit install --hook-type pre-push` — **별도 명령입니다.**
`.pre-commit-config.yaml`의 pytest 훅은 `stages: [pre-push]`라서 commit 훅만 등록하면 테스트 게이트가 전혀 동작하지 않습니다.
증상이 없다는 게 증상이므로 가장 놓치기 쉬운 항목입니다.

#### E07 / E08 변종 — 훅은 있는데 인터프리터가 사라진 경우

`pre-commit install`은 훅 스크립트 안에 **절대 인터프리터 경로**를 박습니다(`INSTALL_PYTHON=...`).
그래서 환경을 지웠다 다시 만들면 훅 파일은 그대로 남지만 그 경로는 없어집니다.

```
[ !! ] E07  pre-commit 훅 등록  훅이 사라진 인터프리터를 가리킴: /path/to/old-env/bin/python
```

훅에는 PATH 폴백(`exec pre-commit`)이 있어서 **PATH에 `pre-commit`이 있으면 계속 동작합니다.**
그래서 이 판정은 폴백까지 없을 때만 실패로 잡습니다. 그 상태에서의 증상은 이렇습니다.

```
pre-commit: command not found
```

커밋 자체가 막히는데 원인이 훅 파일에 적힌 옛 경로여서, 검사 규칙이나 코드를 들여다보면 아무것도
나오지 않습니다. 복구는 재등록입니다 — `pre-commit install` 과 `pre-commit install --hook-type pre-push`
를 **현재 환경에서** 다시 실행하면 경로가 새로 박힙니다. E09(nbstripout 필터)가 같은 형태의 함정을
막고 있어, 두 항목을 같은 기준으로 맞춰 두었습니다.

<a id="e09"></a>
### E09 — nbstripout git filter 미등록

`.gitattributes`는 `*.ipynb filter=nbstripout`을 선언하지만, **필터 드라이버가 git config에 없으면 git은 그 선언을 조용히 무시합니다.**
경고도 오류도 없이 출력 셀이 그대로 커밋되고, 해당 노트북은 이후 계속 `modified`로 표시됩니다.

```bash
pip install nbstripout && python -m nbstripout --install   # .git/info/attributes 에 기록
git config --get filter.nbstripout.clean                   # 등록 확인
```

또 하나의 함정: 필터에는 **절대 인터프리터 경로가 박힙니다.** 그 환경을 지우면 노트북을 만질 때마다 필터가 실패합니다.
스크립트는 이 경우도 `필터가 사라진 인터프리터를 가리킴`으로 잡아내며, 항상 현재 프로젝트 환경으로 다시 설치합니다.

<a id="e10"></a>
### E10 — 훅 환경 캐시 없음

첫 커밋에서 pre-commit이 ruff·gitleaks·nbstripout 환경을 내려받느라 수 분간 멈춘 것처럼 보입니다(정상 동작).
`pre-commit install-hooks`로 미리 받아두면 됩니다. 사내망/프록시로 다운로드가 막히면 여기서 실패하므로 네트워크를 먼저 확인하세요.

<a id="e11"></a>
### E11 — `infra/.env` 없음 / git에 추적될 수 있음

`cp infra/.env.example infra/.env` 후 발급받은 키를 채웁니다.
**이 저장소는 public이라 키가 커밋되면 되돌릴 수 없습니다** — revert가 아니라 폐기·재발급만이 해결책입니다.
스크립트는 `git check-ignore`로 `.env`가 실제로 무시되는지까지 확인합니다.
`.env.example`(키 이름만, 값 없음)만 커밋 대상입니다.

<a id="e11-renamed"></a>
#### E11 변종 — `.env`에 옛 이름이 남아 조용히 무시되는 경우

`infra/.env`는 커밋되지 않으므로 **이름이 바뀐 항목은 각자의 로컬에서만 낡습니다.**
`.env.example`을 고쳐도 이미 만들어 둔 `.env`는 따라오지 않고, `docker compose`는 자기가 아는
이름만 읽고 모르는 줄은 오류 없이 지나갑니다. 그래서 값을 넣은 사람은 적용됐다고 믿고
실제로는 기본값이 돕니다 — 진단이 어려운 쪽은 틀린 값이 아니라 **읽히지 않은 값**입니다.

지금까지 이름이 바뀐 항목:

| 옛 이름 | 새 이름 | 시점 |
|---|---|---|
| `ADGEN_IMAGE_QUALITY` | `ADGEN_IMAGE_QUALITY_OVERRIDE` | 2026-08-20 ([ADR-0017](../adr/0017-만화형은_칸을_따로_생성해_합성한다.md)) |

품질 티어는 이제 요청이 계약으로 실어 보내고(`ImageRenderRequest.quality`), 설정으로 남은 것은
**개발용 강제 override 하나**입니다. `ADGEN_IMAGE_QUALITY=low`를 넣어 둔 `.env`가 있으면
개발 회차가 `low`가 아니라 계약이 실어 보낸 티어로 돌고, 유료 키가 붙은 뒤에는 그 차이가
요금으로 나타납니다. 발동했을 때만 나오는 경고 한 줄이 유일한 표시라, **안 나오는 것이
정상인지 아닌지를 로그로는 구별할 수 없습니다.**

확인 — `.env.example`에 없는 이름만 출력됩니다:

```bash
keys() { sed -n 's/^\([A-Z_][A-Z0-9_]*\)=.*/\1/p' "$1" | sort -u; }
comm -13 <(keys infra/.env.example) <(keys infra/.env)
```

나오는 것이 있으면 오타이거나 이름이 바뀐 항목입니다.
`.env.example`에 일부러 적지 않은 개인 값을 쓰고 있다면 그것도 함께 나옵니다.

PowerShell(`comm`과 프로세스 치환이 없습니다):

```powershell
$keys = { param($f) Select-String $f -Pattern '^[A-Z_][A-Z0-9_]*(?==)' | ForEach-Object { $_.Matches[0].Value } }
Compare-Object (& $keys infra/.env.example) (& $keys infra/.env) |
  Where-Object SideIndicator -eq '=>' | ForEach-Object InputObject
```

주의: 반대 방향(새로 생긴 항목을 `.env`가 아직 안 가진 경우)은 이 명령으로 안 보이고,
보일 필요도 없습니다. 그쪽은 `docker-compose.yml`의 `${X:-기본값}`이 받아 줍니다.

<a id="e12"></a>
### E12 — 셸 스크립트가 CRLF

Windows에서 `core.autocrlf=true`로 체크아웃하면 `.sh` 파일에 CRLF가 들어가고,
WSL·Git Bash에서 `$'\r': command not found` 또는 `bad interpreter`로 실패합니다.

**신규 클론은 `.gitattributes`의 `*.sh text eol=lf`가 막아 줍니다.
E12는 그 줄이 생기기 전에 만들어진 기존 클론의 복구 경로입니다.**

주의: `git checkout`이나 `git add --renormalize`로는 고쳐지지 않습니다(실험으로 확인).
저장소 blob이 원래 LF라 git이 차이를 감지하지 못해 작업트리 파일을 다시 쓰지 않기 때문입니다.
유효한 복구는 파일을 실제로 없앴다가 받아오는 것뿐입니다.

```bash
rm scripts/*.sh && git checkout -- scripts/   # 삭제 후 재취득
```

주의: 저장소 원본으로 되돌리는 명령이라 `scripts/*.sh`에 커밋하지 않은 수정이 있으면 사라집니다.
있다면 `setup-dev.ps1` 쪽을 쓰세요. 파일 안의 CRLF만 바꾸므로 수정이 보존됩니다.

<a id="w05"></a>
### W05 — Windows에서 `run-tests.sh`가 실패 (WSL bash 오검출)

Windows에는 기본으로 `C:\Windows\System32\bash.exe`가 있습니다. 이건 bash가 아니라 **WSL 실행기**라서,
스크립트가 이걸 잡으면 두 단계로 깨집니다.

1. Windows 경로(`C:\...\scripts\run-tests.sh`)가 리눅스 쪽에 그대로 넘어가 **파일을 못 찾습니다.**
2. `wsl bash scripts/run-tests.sh`로 경로를 우회해도 이번엔 **`ruff: command not found`** — 개발 환경(venv)은
   Windows 쪽에 있고 WSL 배포판에는 아무것도 설치돼 있지 않기 때문입니다.

`dev_env.py`는 이제 System32 아래의 bash를 **사용 가능한 bash로 치지 않고**, Git for Windows의
`bash.exe`(`…\Git\bin\bash.exe`, `git.exe` 위치에서 역산)를 찾습니다. 둘 다 없으면 로컬 CI 단계를
건너뛰고 안내만 출력합니다(WARN이므로 세팅 실패는 아닙니다).

해결은 둘 중 하나 — **섞지 마세요.** venv가 있는 쪽에서 전부 실행해야 합니다.

```powershell
winget install --id Git.Git       # (A) Windows에서 계속 작업: Git Bash 설치 후 setup-dev.ps1 재실행
```

```bash
# (B) WSL로 이주: WSL 안에서 clone → venv → 설치까지 전부 리눅스 쪽에서
git clone <repo> && cd AI10-Part4-3Team-Advanced-Project && bash scripts/setup-dev.sh
```

(B)를 고를 때 Windows 드라이브(`/mnt/c/...`)에 clone된 저장소를 WSL에서 쓰는 구성은 피하세요 —
파일 I/O가 느리고 git 훅 권한 문제가 따라옵니다.

<a id="w06"></a>
### W06 — PowerShell 실행 정책 차단 (Windows)

`... cannot be loaded because running scripts is disabled on this system` 이 나오면 실행 정책 때문입니다.

```powershell
powershell -ExecutionPolicy Bypass -File scripts\setup-dev.ps1   # 이번 실행만 우회 (권장)

```
