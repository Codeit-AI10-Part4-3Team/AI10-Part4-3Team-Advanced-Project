# 배포, 관통, 실패 모드 실측 보고서

| 항목 | 내용 |
|---|---|
| 대상 | 배포 VM 스택 (main `afa3e01`) |
| 기준 시점 | 2026-08-28 |
| 수행 | 05 백엔드/인프라 (임동규) |
| 방법 | 재배포 1회, `e2e/` 6건, `scripts/check_failure_modes.py` 4종 |
| 생성 모드 | `stub` |

이 보고서는 세 가지를 한 자리에 적습니다. **26커밋을 올린 재배포 1회**, **배포본을 상대로 한
관통 테스트(F17)**, 그리고 **`e2e/`가 자동화하지 않은 실패 경로 4종**입니다.

셋을 묶은 이유는 순서가 하나이기 때문입니다. 재배포가 세 이슈의 수정을 처음 실물에 올렸고,
그 배포본이 있어야 관통 판정이 성립하며, 실패 모드는 그 배포본 위에서만 잴 수 있습니다.

**주의: 이 회차는 `stub` 모드입니다.** 여기 숫자는 배선이 서는지에 대한 것이지 생성 품질에
대한 것이 아닙니다. 답하지 않는 것은 D-b절에 적었습니다.

근거가 되는 결정은 [2026-08-28 회의록](../회의록/2026-08-28_잔여_6건_확정.md) 안건 03과
04입니다. 그 회의록이 "이 저장소만으로는 08-28 재배포가 실제로 실행됐는지 알 수 없습니다"로
열어 둔 자리를 이 보고서가 채웁니다.

## A. 재배포

### A-a. 무엇을 올렸는가

`a42e78c` 에서 `afa3e01` 로 26커밋입니다. 이 배포가 처음 실물에 올린 수정이 셋입니다.

| 이슈 | 무엇 | PR |
|---|---|---|
| #292 | 배포가 `.env.example` 안 바뀐 범위에서 스스로 중단 | #295 |
| #293 | Caddy 설정이 배포 후에도 갱신되지 않음 | #300 |
| #294 | `.webp` 의 `content-type` 이 컨테이너에서만 틀림 | #299 |

셋 다 그전까지 "고쳤다고 적혀 있지만 배포에서 돈 적은 없는" 상태였습니다.

### A-b. 첫 시도는 실패했고, 그것이 예상된 동작입니다

첫 실행이 `show_changes` 에서 멈췄습니다. **#295 가 고친 바로 그 자리입니다.**

원인은 자기 참조입니다. `bash scripts/deploy-vm.sh` 는 실행 시작 시점의 파일을 붙들고 끝까지
돌므로, **자기를 고치는 배포는 옛 판으로 돕니다.** 옛 판(`a42e78c`)의 `show_changes` 마지막
줄이 이렇습니다.

```bash
grep -q '^infra/\.env\.example$' <<<"$touched" && warn ".env.example 이 바뀌었습니다 ..."
}
```

이번 범위는 `infra/.env.example` 을 건드리지 않았습니다(확인함). 따라서 `grep` 이 실패하고,
그 AND 리스트가 함수의 마지막 문이라 **함수 반환값이 1** 이 되며, `set -e` 가 배포를 죽입니다.

멈춘 지점은 `bring_up` 직전입니다. 체크아웃은 `afa3e01` 로 갔고 이미지는 옛것인 상태로
남았습니다. 이것이 이 스크립트가 `--no-build` 와 `--ref` 조합을 거부하면서까지 막으려던
상태이므로, 그대로 두면 안 됩니다.

**복구는 재실행입니다.** 두 번째 실행은 `prev == now` 라 `show_changes` 가 조기 반환하고,
그때는 새 판을 읽습니다. 실제로 그렇게 지나갔습니다.

**주의: 이 성질은 다음에도 재발합니다.** `scripts/deploy-vm.sh` 를 고치는 배포는 항상 한 번
실패하고, 두 번째 실행이 필요합니다. 배포 담당이 아닌 사람이 이 실패를 보면 원인을 찾는 데
시간을 씁니다.

### A-c. 두 번째 실행에서 확인된 것

| 확인 | 증거 |
|---|---|
| #295 배포가 스스로 죽지 않음 | `show_changes` 를 지나 `bring_up` 도달 |
| #300 `caddy reload` 가 돎 | `==> Caddy 설정 다시 읽기`, `using config from file` |
| #300 하드닝 헤더가 **다시 벗겨지지 않음** | `OK 하드닝 헤더 (nosniff)` |
| 스택 4개 healthy | `compose ps` 가 ai-engine, backend, caddy, frontend 를 `Up 6 seconds (healthy)` 로 |
| 상태 보존 | `OK 상태 파일 /data/adgen.sqlite 보존`, `OK 계정 2건 시드됨` |
| 생성 모드 | `INFO 생성 모드: stub` |

**셋째 행의 "다시 벗겨지지 않음" 이 낱말 하나가 아닙니다.** `nosniff` 를 붙인 것은 이번
배포가 아니라 2026-08-27 의 `--force-recreate` 입니다(#293 본문). #300 이 한 것은 마운트를
파일에서 디렉토리로 바꿔 **다음 배포가 그것을 다시 벗기지 못하게** 만든 것입니다. A-d 절의
순서 서술과 갈리지 않게 여기 적어 둡니다.

**넷째 행은 배포 출력의 표를 읽은 것입니다.** `scripts/deploy-vm.sh` 의 `verify()` 는
`compose ps` 를 찍기만 하고 그것을 성공 조건으로 세지 않습니다 - 판정하는 것은 `/health` 200,
화면 진입 200, `/v1/sessions` 401, `nosniff` 넷입니다. 그래서 "배포가 통과했으니 healthy 도
포함" 으로 읽을 수 없고, 표를 따로 봐야 합니다.

**caddy 컨테이너가 재생성됐습니다.** #300 이 마운트를 파일에서 디렉토리로 바꿔 compose 의
config 해시가 달라졌기 때문입니다. 이제 `git merge` 가 inode 를 갈아치워도 컨테이너가 옛
내용을 붙들지 않습니다.

### A-d. `.webp` 의 content-type 과 화풍 격자 8칸 (#294, #274)

PR #299 가 `Closes` 대신 `Refs` 를 쓴 이유가 여기 있습니다. 결함의 정의 자체가 "로컬에서는
맞고 배포에서만 틀리다" 이므로, 머지가 아니라 배포 실측이 닫는 조건입니다. 08-28 회의록
안건 03 도 같은 근거로 그렇게 적었습니다.

#### 잰 방법

VM 에서 이렇게 잽니다. 공개 호스트를 셸에 노출하지 않으려고 `.env` 에서 읽습니다.

```bash
cd /srv/adcraft/app
export $(grep '^ADGEN_PUBLIC_HOST=' infra/.env | xargs)
curl -sS -D - -o /dev/null "https://$ADGEN_PUBLIC_HOST/static/art-styles/style-02.webp" \
  | grep -iE '^content-type|^x-content-type-options'
```

**주의: `ADGEN_PUBLIC_HOST` 가 셸에 없으면 URL 이 `https:///static/...` 이 되고 curl 이
`static` 을 호스트로 읽습니다** (`Could not resolve host: static`). 값을 못 읽은 것이지
경로가 없는 것이 아니므로, 그 오류를 404 로 오해하지 마십시오. `echo ${#ADGEN_PUBLIC_HOST}`
로 길이만 찍어 보면 값 노출 없이 확인됩니다.

#### 결과

| | 이전 (2026-08-27) | 이번 (2026-08-28) |
|---|---|---|
| `content-type` | `application/octet-stream` | **`image/webp`** |
| `x-content-type-options` | `nosniff` | `nosniff` |

이전 값의 출처는 이슈 #294 본문입니다. 그 이슈가 "같은 응답에 `nosniff` 와
`application/octet-stream` 이 함께 나간다"를 기록해 두었고, 그 어긋남이 이번에 해소됐습니다.

원인은 환경 차이였습니다. `python:3.12-slim` 에 `/etc/mime.types` 가 없고 파이썬 3.12 의
내장 표에도 `.webp` 가 없어, `StaticFiles` 의 추측이 컨테이너에서만 빗나갔습니다. PR #299 가
`Content-Type` 을 `images.MEDIA_TYPE` 으로 직접 정해 그 추측을 걷어냈습니다.

#### 화풍 격자 8칸

**화풍 선택 화면을 브라우저로 열어 8칸이 모두 그려지는 것을 확인했습니다**(육안).

이슈 #274 가 "다음 재기동에 화풍 격자가 깨집니다"로 예고했지만 깨지지 않았습니다. #294 가
`높은 신뢰` 로 적어 둔 판단, 즉 "Fetch 명세상 `nosniff` 가 차단하는 것은 script 계열과
style 뿐이고 `<img>` 는 그 목록에 없다"가 실측으로 확인된 셈입니다.

**순서가 뒤집힌 채로도 깨지지 않았다는 점을 함께 적습니다.** #274 는 "content-type 을 먼저
고쳐야 nosniff 가 안전하다"를 본문에 못박았는데, 실제로는 2026-08-27 재기동으로 `nosniff` 가
먼저 붙고 content-type 은 이번 배포에서야 고쳐졌습니다. 그 사이 하루 동안 배포본은 #274 가
위험하다고 적은 상태였고, 그때도 격자는 그려졌습니다.

**다만 브라우저 한 종류에서만 봤습니다.**

이슈 #274 의 완료 조건 넷째인 회귀 시험은 배포 실측이 아니라 코드에 있습니다 -
`apps/backend/tests/api/test_art_style_static.py` 의
`test_the_type_does_not_depend_on_the_operating_system_mime_table` 이 `image/webp` 를
단언하고, PR #306 이 그 시험의 운영체제 mime 표 의존까지 걷어냈습니다. **이 보고서만 읽으면
넷째가 미충족으로 보이므로 여기 적어 둡니다.**

#### 예시 전달 2단계가 이미 끝나 있었습니다

격자가 그려진다는 것은 `exampleImageUrl` 이 채워져 있다는 뜻입니다. 화면은 그 값이 비면
"예시 준비 중" 자리를 잡지 그림을 그리지 않기 때문입니다(#179). 되짚어 네 축을 확인했습니다.

| 축 | 값 |
|---|---|
| 볼륨 `/data/art-styles/` | 파일 8장 |
| `settings().art_styles` | 항목 8, `exampleImageUrl` 채워진 것 8, 빈 것 없음 |
| `/static/art-styles/style-02.webp` | `200 image/webp` |
| 화면 | 격자 8칸 (육안) |

값은 `.env` 를 화면에 띄우지 않고 일회용 컨테이너로 파싱해 셌습니다. 그 파일에는 유료 키가
있습니다.

```bash
docker compose -f infra/docker-compose.yml --env-file infra/.env \
  run --rm --no-deps -T backend python -c "
from api import deps
s = deps.settings().art_styles
print(len(s), sum(1 for a in s if a.example_image_url))
"
```

**주의: 누가 언제 2단계를 실행했는지는 저장소에 기록이 없습니다.** 05 진행 기록이 2026-08-22
에 "그 절차는 아직 실행해 본 적이 없습니다" 로 끝나 있고 그 뒤로 이어진 기록이 없습니다.
이 보고서가 확인하는 것은 **2026-08-28 시점에 들어와 있다**는 사실이지 실행 시점이 아닙니다.

작업 표는 그동안 실제보다 덜 된 것처럼 보이고 있었습니다.

## C. 실패 모드 4종

`e2e/README.md` 가 "아직 자동화하지 않은 것"으로 적어 둔 열화 경로를 포함해 넷을 잽니다.
하네스가 docker 를 직접 다루는 결합은 아직 정해지지 않은 항목이므로, 별도 스크립트
(`scripts/check_failure_modes.py`)가 그것을 맡습니다.

### C-a. 결과

`scripts/check_failure_modes.py`. 대상은 배포 VM, 생성 모드 `stub`.

| 검사 | 기대 | 실제 | 판정 |
|---|---|---|---|
| A 열화 (stop) | `201 brief_filling degraded` | `201 brief_filling degraded` | OK |
| B 시안 타임아웃 (pause) | `504 GENERATION_TIMEOUT` | `504 GENERATION_TIMEOUT` | OK |
| B 브리프 잠금 해제 (ADR-0012) | `brief_ready` | `brief_ready` | OK |
| C 렌더 실패 (stop) | `200 failed UPSTREAM_UNAVAILABLE` | `200 failed UPSTREAM_UNAVAILABLE` | OK |
| D 복구 (전 구간) | `done image/webp` | `done image/webp` | OK |

복구 확인됐고(`ai-engine running healthy`), 세션 4건이 남았습니다. 보존 정리 배치가 치웁니다.

### C-b. stop 과 pause 를 가르는 이유

`backend_core/ai_client.py` 가 `httpx.TimeoutException` 을 `GenerationTimeoutError` 로,
나머지 `HTTPError` 를 `AiEngineUnavailableError` 로 나누고, 라우트와 렌더 워커가 **둘을 다른
응답으로 매핑**합니다. 컨테이너를 `stop` 하면 커널이 연결을 거부해 앞쪽만 지나고 **뒤쪽은 한
줄도 안 지나갑니다.**

`pause` 는 cgroup freezer 로 프로세스만 얼립니다. 리스닝 소켓은 커널에 남아 연결은 되는데
응답이 오지 않으므로, 그것이 타임아웃 갈래를 태우는 무해한 방법입니다.

**이 전제가 이번 회차에서 처음 실물로 확인됐습니다.** 그전까지는 블랙홀 소켓으로만 재
`추정` 이었습니다. B 가 `504` 라는 것이 그 확인입니다.

### C-c. 세 번째 확인이 본체입니다

B 의 두 줄 중 잠금 해제 쪽이 더 중요합니다. ADR-0012 는 시안 생성이 실패하면 세션을
`brief_ready` 로 되돌리라고 정하는데, 그러지 않으면 사용자가 **브리프는 잠겼고 보여 줄 시안은
없는** 세션에 갇힙니다. 상태 코드만 보면 그 일이 안 났는지 알 수 없습니다.

### C-d. 출력에 섞이는 소음

`Error response from daemon: Container ... is not paused` 가 세 번 나옵니다. 스크립트의
`up()` 이 `unpause` 를 조건 없이 부르기 때문이고, 판정에는 영향이 없습니다. 다만 기록에
붙으면 오류처럼 보이므로 그 stderr 를 삼키는 것이 후속입니다.

## D. 남은 한계

### D-a. 재시도 정책이 미확정입니다

[2026-08-28 회의록](../회의록/2026-08-28_잔여_6건_확정.md) 안건 04 가 확정한 것을 그대로
적습니다.

**재시도 정책은 정하지 않고 현행(재시도 0)으로 제출하며, 429 가 실패로 집계되는 것을 알려진
한계로 남깁니다.** 08-24 회의가 정한 순서(실측 먼저)를 따르려 했으나 08-28 중에도 07 의
이음매별 시간값 표가 나오지 않아, 표를 계속 기다리는 것 자체가 위험하다고 판단한 결과입니다.

미결정 대장 N19-a 는 계속 잠정 진행으로 남고 제출 후 과제로 넘어갑니다.

**이 보고서의 어떤 숫자도 재시도가 있는 상태를 재지 않았습니다.**

### D-b. 이 회차가 답하지 않는 것

- **가드레일 거절(`CONTENT_POLICY_REJECTED`)** 은 스텁이 거절하지 않아 재현 조건이 없습니다.
  실물 이음매가 붙은 뒤에 들어갈 자리입니다 (`e2e/README.md`).
- **만화형은 관통 대상이 아닙니다** (구현_범위 1절). B 와 C 에서 지나간 것은 단일 광고형
  하나입니다. 만화형에 통과를 요구하면 스텁의 현재 동작이 계약으로 굳습니다.
- **지연 값은 지표가 아닙니다.** `stub` 구간의 숫자는 자기 자신과의 일치율입니다
  (`AGENTS.md` 현재 상태). 이 보고서에 지연 값을 싣지 않은 이유입니다.
- **브라우저는 한 종류만 봤습니다.** A-d 의 격자 확인이 그렇습니다.
- **`docker pause` 이외의 지연은 재지 않았습니다.** 느린 응답, 부분 응답, 연결 후 절단은
  각각 다른 갈래일 수 있습니다.

### D-c. 이 보고서가 결정이 아닌 것

`AGENTS.md` 근거 자료 규칙대로, 여기 실린 것은 실측값이고 결론이 아닙니다. "그래서 이렇게
하자"에 해당하는 판단은 회의록이 합니다.
