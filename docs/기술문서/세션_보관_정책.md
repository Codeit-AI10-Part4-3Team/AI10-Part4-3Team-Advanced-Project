# 세션 보관 정책

기획서 17.1이 "기술문서에서 정할 것"으로 넘긴 6개 항목의 답입니다. 각 항목은 **결정 + 이유 +
대안 + 뒤집힐 조건** 형태로 적혀 있습니다.

여섯 항목 모두 **확정**입니다 (2026-08-09, TL). 근거는 각 절과
[ADR-0010](../adr/0010-상태_저장소와_파일_보관_위치.md)이며, 남은 미결정은 7절에 따로 모았습니다.

전제: 1차 범위는 워킹 스켈레톤이고 사용자는 팀 내부입니다 (기획서 11.2, 14.4). 아래 결정은
그 전제 위에서만 타당하며, 외부 공개 시점에 전부 다시 봅니다 (기획서 17.2).

## 1. 로그인 및 사용자 구분

| 구분 | 내용 |
|---|---|
| 결정 | **아이디와 비밀번호** 방식. 서버가 계정을 발급하고 로그인 세션으로 사용자를 구분합니다 |
| 근거 | 기획서 17.1이 "어떤 방식으로 로그인을 받는지"를 정하라고 했습니다. 로그인 여부가 아니라 **수단**을 묻는 항목입니다 |
| 대안 | OAuth (구글, 카카오) / 익명 쿠키 / 매직 링크 |
| 뒤집힐 조건 | 외부 공개 시 계정 관리 부담이 문제가 되는 경우. 그때는 OAuth로 옮깁니다 |
| 소관 | 05 백엔드 |

OAuth를 택하지 않은 이유는 **외부 의존이 늘기 때문**입니다. 제공자 등록, 리다이렉트 URI, 키
관리가 붙는데 22일 일정에서 그 비용은 회수되지 않습니다. 아이디와 비밀번호는 전부 우리 안에서
끝납니다.

### 1.1 두 식별자를 혼동하지 마세요

| 식별자 | 가리키는 것 | 수명 |
|---|---|---|
| `userId` | **사람 한 명** | 계정이 사는 동안 |
| `sessionId` | **제작 1건** | 그 세션이 보존되는 동안 (2절) |

`sessionId`는 사용자 구분이 아니라 작업물의 식별자입니다. 한 사용자가 세션 여러 개를 가집니다.
세션을 버리는 것은 계정을 버리는 것이 아니라 **작업물 한 건을 버리는 일**입니다.

**`sessionId`를 접근 제어로 쓰지 마세요.** 접근 제어는 로그인 세션이 합니다 --
`GET /v1/sessions/{id}`는 그 세션의 `userId`가 요청자와 같을 때만 200이고, 아니면 404입니다
(403이 아닙니다. 존재 여부 자체를 알리지 않습니다).

### 1.2 비밀번호

이 저장소는 **public**입니다. 아래는 취향이 아니라 최소선입니다.

- 비밀번호는 **해시로만** 저장합니다 (`argon2` 또는 `bcrypt`). 평문과 가역 암호화는 둘 다
  금지입니다.
- 해시 파라미터와 솔트 정책은 라이브러리 기본값을 씁니다. 직접 조정하면 잘못 조정합니다.
- 로그인 실패 응답은 아이디 오류와 비밀번호 오류를 구분하지 않습니다. 구분하면 아이디 존재
  여부가 새어 나갑니다.
- 비밀번호를 로그에 남기지 않습니다. 요청 본문 전체를 찍는 디버그 로그가 가장 흔한 사고입니다.
- 비밀번호 재설정은 1차 범위 밖입니다. 메일 발송 경로가 없기 때문이며, 잊으면 계정을 다시
  만듭니다. 외부 공개 시 다시 봅니다 (기획서 17.2).

### 1.3 로그인이 캐릭터 재사용을 1차로 끌어오지는 않습니다

기획서 7.4는 "로그인 기반 캐릭터와 마스코트 재사용"을 **2차 고도화**로 두었습니다. 로그인이
1차에 있다고 그 기능이 따라오지 않습니다 -- 로그인은 재사용의 **선행 조건**이지 재사용 자체가
아닙니다. 1차에서 계정이 하는 일은 내 세션 목록을 되찾는 것까지입니다.

### 1.4 로그인 세션의 수명

| 구분 | 내용 |
|---|---|
| 결정 | 토큰 **24시간 만료, 갱신 없음**. `HttpOnly` 쿠키 |
| 이유 | refresh 토큰을 두면 회전, 재사용 탐지, 폐기 목록이 따라옵니다. 22일 일정에서 그 비용은 회수되지 않고, 만료돼도 잃는 것이 없습니다 |
| 대안 | 7일 단일 토큰 / access 30분 + refresh 14일 / 슬라이딩 만료 |
| 뒤집힐 조건 | 외부 공개로 사용자가 팀 밖으로 나갈 때. OAuth 전환과 함께 다시 엽니다 |
| 소관 | 05 백엔드 |

**세 수명을 혼동하지 마세요.** 셋은 서로 독립입니다.

| 수명 | 길이 | 만료되면 |
|---|---|---|
| 로그인 토큰 | 24시간 | 다시 로그인. 데이터는 그대로입니다 |
| 업로드 사진 | 24시간 (2절) | 사진을 다시 올려야 합니다 |
| 브리프 / 시안 / 결과 | 7일 (2절) | 세션이 사라집니다 |

토큰과 사진이 우연히 같은 24시간인 것은 근거가 다릅니다. 토큰은 탈취 창을, 사진은 개인정보
보관 기간을 기준으로 잡았습니다. **한쪽을 바꿀 때 다른 쪽을 따라 바꾸지 마세요.**

계약 표면(쿠키 속성, 만료 응답)은 [API_계약.md](API_계약.md) 6절이 정본입니다.

## 2. 정보 보존 범위

입력 이미지와 생성 결과는 개인정보이거나 저작물일 수 있습니다. 보존 기간을 정하지 않은 채 디스크에
쌓는 것은 [AGENTS.md](../../AGENTS.md)의 설계 제약 위반입니다.

| 데이터 | 보존 기간 | 이유 |
|---|---|---|
| 계정 (아이디, 비밀번호 해시) | 계정 삭제 시까지 | 세션 목록을 되찾는 근거입니다 |
| 업로드 제품 사진 | **업로드 후 24시간** | 렌더 도달 여부와 무관합니다. 아래 참고 |
| 브리프 / 시안 (텍스트) | 7일 | 세션 복원과 실험 자료 |
| 결과 이미지 | 7일 | 사용자가 받아 갈 시간 |
| 프롬프트 / 호출 로그 | 30일 | 지표 실측과 원인 분석에 필요합니다 |

사진의 기준을 "렌더 완료 후"가 아니라 **업로드 후**로 잡았습니다. 렌더에 도달하지 않고 버려지는
세션이 있는데, 완료를 기준으로 삼으면 그 세션의 사진에는 만료가 영영 오지 않습니다. 기간 없이
개인정보를 쌓지 말라는 [AGENTS.md](../../AGENTS.md) 하드 제약을 정책이 스스로 어기게 됩니다.

24시간 안에 확정하지 못하면 사진을 다시 올려야 합니다. 그 비용은 감수합니다 -- 무기한 보관보다
낫습니다.

- 만료된 데이터는 **삭제하는 코드가 있어야 합니다.** 기간을 문서에만 적어 두면 아무것도 지워지지
  않습니다. **일 1회 정리 배치**로 지웁니다. 기간 값과 배치 주기는 설정값입니다.
- 로그에 제품 사진과 개인 식별 정보를 남기지 않습니다. 남기는 것은 `sessionId`와 크기, 형식입니다.
- 팀 시연과 발표에 쓸 산출물은 보존 기간과 무관하게 **별도로 내려받아** 보관하세요. 만료 후
  복구 경로는 없습니다.
- 뒤집힐 조건: 브랜드 데이터를 학습에 쓰기로 결정하는 경우. 그때는 권리 근거 대장이 먼저입니다
  (`training/data/README.md`).

## 3. 작업 상태 보관

| 구분 | 내용 |
|---|---|
| 결정 | 서버 보관. 상태 저장소는 **SQLite 파일**, 이미지 파일은 **VM 로컬 디스크** |
| 이유 | VM 1대에 프로세스가 몇 개뿐입니다. Postgres와 Redis를 세우면 운영 대상이 셋으로 늘고, 22일 안에 그 비용을 회수하지 못합니다 |
| 대안 | Postgres + 오브젝트 스토리지 / 인메모리 (재시작 시 유실) |
| 뒤집힐 조건 | 워커를 여러 개로 늘려야 하거나, 쓰기 경합으로 잠금 오류가 실제로 관측되는 경우 |
| 근거 | [ADR-0010](../adr/0010-상태_저장소와_파일_보관_위치.md) |
| 소관 | 05 백엔드 |

- **인메모리 보관은 채택하지 않습니다.** 프로세스가 재시작되면 진행 중이던 세션이 사라지고,
  그것은 사용자에게 "확정을 눌렀는데 결과가 없다"로 보입니다.
- 새로고침하면 `sessionId`로 상태가 복원됩니다. 화면은 `GET /v1/sessions/{id}` 하나로 어느
  단계에서든 다시 그릴 수 있어야 합니다 ([API_계약.md](API_계약.md) 1절).
- `ai-engine`은 상태를 갖지 않습니다. 상태를 가지면 재시작마다 진행 중인 잡이 사라지고, 엔진을
  독립 배포 단위로 두는 의미가 없어집니다 ([아키텍처.md](../공통_가이드/아키텍처.md)).

## 4. 생성 중 처리 방식

| 구분 | 내용 |
|---|---|
| 결정 | 잡 접수 + 폴링. 브라우저를 닫아도 `jobId`로 결과를 회수합니다 |
| 이유 | 수 분짜리 작업을 HTTP로 붙들면 프록시와 브라우저 타임아웃에 먼저 걸립니다 |
| 대안 | SSE / WebSocket / 이메일 알림 |
| 뒤집힐 조건 | 진행률을 실시간으로 보여 줘야 한다는 UX 요구가 확정되는 경우 |
| 소관 | 05 백엔드 + 06 프론트 |

- 규약은 [API_계약.md](API_계약.md) 2.1절에 있습니다.
- 잡은 재시작을 견뎌야 합니다. 상태 저장소에 남기고, 프로세스가 죽으면 `failed`로 회수합니다 --
  `running`인 채로 영원히 남는 잡이 가장 나쁜 상태입니다.
- 대기 화면 구성은 미정입니다 (기획서 18.2 #14). 이 문서는 **서버가 무엇을 보장하는지**까지만
  정합니다: `jobId`가 살아 있는 동안 결과는 회수 가능합니다.

## 5. 오류 전달 형식

[API_계약.md](API_계약.md) 5절이 정본입니다. 이 문서에서 중복해 정의하지 않습니다.

여기서 정할 것은 하나입니다: **실패한 잡의 결과도 보존 기간을 따릅니다.** 실패 원인은 30일간
남는 호출 로그에서 확인하며, 사용자에게는 코드와 메시지만 전달합니다.

## 6. 동시 요청

| 구분 | 내용 |
|---|---|
| 결정 | 렌더는 **직렬 처리**(동시 1건). 대기 중인 요청에는 `queuePosition`을 돌려줍니다 |
| 이유 | GPU가 1대뿐이고, 로컬 모델을 채택하면 동시 실행은 곧 OOM입니다. GPT API만 쓰더라도 큐를 먼저 두면 나중에 모델을 바꿔도 인터페이스가 유지됩니다 |
| 대안 | 무제한 동시 실행 (API 전용 구성에서만 가능) / 동시 N건 설정값 |
| 뒤집힐 조건 | 로컬 모델 미채택이 확정되고, 실측 지연이 대기 시간보다 문제가 되는 경우 |
| 소관 | 05 백엔드 |

- 텍스트 단계(브리프 채우기, 시안 생성)는 직렬화하지 않습니다. 외부 API 호출이라 서로를 막지
  않습니다.
- 동시 실행 수는 **설정값**으로 두되 기본값 1로 시작합니다. 코드에 상수로 박으면 실험할 때마다
  배포가 필요합니다.
- 대기 시간이 길어질 때의 사용자 안내 문구는 배포 단계 소관입니다 (기획서 17.2).
