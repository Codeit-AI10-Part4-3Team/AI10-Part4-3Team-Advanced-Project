# 구현 범위

**무엇을 만들지**보다 **무엇을 만들지 않을지**가 더 중요한 문서입니다. 짧은 프로젝트에서
범위가 조용히 늘어나는 것이 가장 흔한 실패 원인입니다.

> **상태: 확정입니다** (2026-08-21). 기획서 18.1 #6("워킹 스켈레톤 범위 정의 - 1차 범위의
> 경계", 미결정_대장 A-6)이 닫혔습니다 -- PM이 PR #54 에서 답한 네 건을 회의가 추인했습니다
> ([회의록](../회의록/2026-08-21_미결정_5건_확정.md) 06번 안건). 네 건은 기획서 문안을 고칠
> 것, 관통은 단일 광고형으로 갈 것, VM 배포는 1차에 포함할 것, 관통 테스트는 백엔드가 맡을
> 것입니다.
>
> **기획서 14.4절의 문안 수정은 아직 남아 있습니다** (01 소관). 그 문장이 고쳐지기 전까지
> 기획서와 이 문서가 같은 범위를 다르게 적고 있으므로, 어긋나면 이 문서와 회의록이 맞습니다.

## 0. 세 개의 축을 혼동하지 않기

문서 곳곳에 "1차", "단계", "개발 단계"라는 말이 나오는데 **서로 다른 세 개의 축**입니다.
섞어 쓰면 "1차에 배포가 들어가나요" 같은 질문에 아무도 답할 수 없게 됩니다.

| 축 | 값 | 정의 위치 |
|---|---|---|
| **진행 절차** | 1 기획 확정 -> 2 기술문서 -> **3 워킹 스켈레톤** | 기획서 14.2 |
| **기능 차수** | 1차 (기능 완성) / 2차 (고도화) | 이 문서 |
| **운영 성숙도** | 개발 단계 / 배포 단계 | 기획서 12.5, 17.2 |

- **워킹 스켈레톤은 기능 차수가 아니라 진행 절차의 한 단계**입니다. 기능을 담는 그릇이 아니라
  그릇이 새지 않는지 확인하는 일입니다.
- 운영 성숙도는 같은 기능의 다른 완성도입니다. 오류 표시는 1차에 들어가지만, 개발 단계에서는
  원인을 그대로 보여 주고 배포 단계에서 사용자용 문구로 바뀝니다.

### 0.1 기획서 해석 (PM 확인됨, 기획서 반영 대기)

기획서 14.4는 "워킹 스켈레톤에 포함된 것이 1차 범위"라고 적혀 있고, 7.1은 9개 기능을 "1차 필수"로
나열합니다. 두 문장이 같은 것을 가리키지 않습니다 -- 7.1의 9개를 전부 만들면 그것은 스켈레톤이
아니라 완성된 제품입니다.

**TL 해석: 둘을 분리합니다.**

| | 워킹 스켈레톤 (진행 절차 3단계) | 1차 (기능 차수) |
|---|---|---|
| 목적 | 전 구간이 연결되는지 확인 | 기능이 실제로 동작 |
| 품질 | 관통만 되면 됨. 결과물의 품질은 보지 않음 | 기획서 7.1, 7.2 충족 |
| 외부 의존 | 스텁 허용 | 실물 |
| 근거 | 기획서 14.2 단계 3 | 기획서 7.1, 7.2 |

**PM이 고치기로 했습니다** (PR #54 리뷰). 들어갈 문안도 함께 제시되었습니다.

> 진행 절차 3단계는 워킹 스켈레톤이며, 1차 기능 범위는 7.1을 따른다.

기획서를 실제로 고치는 것은 PM 소관이며, 반영되면 이 절의 "PM 확인 필요" 표시를 지웁니다.

## 1. 워킹 스켈레톤 (진행 절차 3단계)

**수직 관통 한 줄만 만듭니다.** 요청 하나가 화면부터 결과 파일까지 전 구간을 지나가고, 각 외부
의존이 **이름 붙은 이음매** 뒤에 스텁으로 들어가 있으면 끝입니다.

- 관통 경로는 **단일 광고형 하나**입니다. 만화형 가지는 분기 지점만 만들고 스텁으로 둡니다 --
  분기 자체가 구조이므로 없애지 않되(기획서 5.3), 6컷 격자와 캐릭터 일관성은 스켈레톤이 답할
  문제가 아닙니다.
  - **이 절은 스켈레톤 시점의 기록입니다.** 스켈레톤이 관통한 뒤(2026-08-19) 만화형 실물
    분기가 들어왔고(2026-08-20), **스텁도 2026-08-27 부터 6컷을 채웁니다**
    ([ADR-0020](../adr/0020-스텁도_만화형_여섯_칸을_채운다.md), 미결정_대장 N22). "스텁은
    만화형을 채우지 않는다"를 **지금의 규칙으로 인용하지 마십시오** -- 코드 주석 셋이 이 절을
    그 근거로 인용하고 있었고, 그 인용을 함께 걷었습니다.
- **결과물의 품질은 판정 대상이 아닙니다.** 자리표시자 이미지가 내려와도 통과입니다.
- **로그인은 플로우만 만듭니다.** 가입, 탈퇴, 비밀번호 변경은 계약만 잡고 501로 응답합니다
  ([ADR-0008](../adr/0008-로그인_수단과_스켈레톤_범위.md)). 스켈레톤이 답할 질문은 "인증이 관통
  경로에 실제로 걸리는가"이고, 계정을 만드는 일은 그 질문에 답하지 않습니다.

| # | 항목 | 완료 조건 (DoD) | 소관 |
|---|---|---|---|
| S0 | 로그인 | **고정 계정 둘**로 아이디 조회 + 비밀번호 대조 + 세션 쿠키 발급. 미인증 요청은 401, 남의 세션 조회는 404 (INV-9) | 임동규 |
| S1 | 계약 골격 | 세션, 시안, 확정, 잡 경로가 `openapi.yaml`에 존재하고 `contracts-check` 통과 | 신호정 |
| S2 | 세션 상태 전이 | `created`부터 `completed`까지 전이가 저장소에 남고, 프로세스 재시작 후 복원됨 | 임동규 |
| S3 | 브리프 채우기 이음매 | backend가 ai-engine을 호출하고, 더미 구현이 고정값을 반환함 | 임동규 (호출) + 신호정 (더미) |
| S4 | 시안 생성 이음매 | 유형 분기가 존재하고, 단일 광고형 더미 구현이 고정 시안을 반환함 | 임동규 + 신호정 (더미) |
| S5 | 부분 교체 | `revision` 기반 patch에서 지정한 필드만 바뀌고 나머지는 원문 유지 | 임동규 |
| S6 | 확정과 잡 | `finalize` -> `jobId` -> 폴링 -> 잡이 `done`. 렌더러 더미가 자리표시자 이미지를 반환 | 임동규 + 신호정 (더미) |
| S7 | 최소 화면 | 입력, 시안, 확정, 결과 다운로드가 브라우저에서 한 번에 통과 | 송기하 |
| S8 | 오류 경로 1종 | ai-engine을 꺼도 화면이 죽지 않고 우측 상단에 오류가 표시됨 | 임동규 + 송기하 |

**전체 DoD**: 브라우저에서 입력부터 파일 다운로드까지 한 번에 지나가고,
[아키텍처.md](아키텍처.md) 5절의 이음매 표에 **모든 스텁이 이름과 소관과 함께** 올라가 있을 것.

**S0의 "고정 계정 둘"은 최소값입니다** ([ADR-0008](../adr/0008-로그인_수단과_스켈레톤_범위.md)).
하나면 "남의 세션"이 존재하지 않아 404 경로를 한 번도 지나지 않기 때문에 둘이며, 셋 이상을
금지하는 규칙이 아닙니다. 개발 중에 각자 계정을 더 두어도 로그인은 아이디 조회와 비밀번호
대조뿐이라 **계약도 코드도 바뀌지 않습니다.** 다만 가입 경로가 501이므로 늘리는 방법은 시드
데이터 추가뿐이고, 자격 증명은 `infra/.env`에만 두므로 **팀원마다 계정 목록이 달라집니다.**
S0의 완료 판정은 공용 고정 계정 둘로 하고, 개인 계정은 각자 로컬에만 두십시오.

### 1.1 더미 구현은 실물과 같은 자리에서 갈립니다

2026-08-11 회의에서 **더미 구현 3곳(S3, S4, S6)을 신호정이 맡기로** 확정했습니다
([회의 결정](../회의록/2026-08-11_차단7건_회의결정.md)). AI 담당이 배관 작업에 묶이지 않게 하기
위해서입니다.

만드는 방식은 이렇습니다.

- **함수는 실물과 같은 것을 만듭니다.** 더미 전용 경로를 따로 파지 않고, 같은 함수 안에서
  더미 루틴과 실제 구현이 **분기**되도록 구현합니다.
- 그래서 03(생성·서빙)이 실제 기능을 붙일 때 **호출부와 계약을 건드리지 않습니다.** 분기의 한쪽을
  채우는 일이 됩니다.
- 이것이 `AGENTS.md`가 말하는 "옆에 새로 만들지 말고 같은 이음매에서 갈아끼운다"를 코드 수준으로
  옮긴 것입니다. 우회 경로를 만들면 스켈레톤이 검증하던 성질(폴백, 가드레일, 계약)이 조용히
  사라집니다.
- 분기 조건은 **설정으로 드러냅니다.** 어느 쪽이 돌고 있는지 코드를 읽지 않고 알 수 있어야
  합니다. 스텁 응답을 실측값으로 착각하는 사고가 여기서 나옵니다.

되어 **배관과 검증 실험이 한 사람에게 겹칩니다.** 다섯 명을 셋 + 둘로 갈라 두 트랙을 동시에

**신호정이 두 트랙을 모두 진행합니다.** 검증 실험을 다른 사람에게 재배분하지 않고 **일정 지연을
감수하기로 확정했습니다.** 새 마일스톤 날짜는 진행 보고를 받은 뒤 재조정하며, 그때
[00-overall.md](../역할_일정/00-overall.md)와 역할별 일정 문서를 함께 고칩니다.

### 1.4 두 트랙은 동시에 굴러갑니다

스켈레톤과 검증 실험은 **서로를 기다리지 않습니다.** 이것이 성립하는 이유는 하나입니다:
스켈레톤에 필요한 것은 모델 호출이 아니라 **응답의 모양**뿐이고, 그 모양은
[도메인_모델.md](../기술문서/도메인_모델.md)가 이미 고정했기 때문입니다.

2026-08-11 회의로 **검증 트랙에 선행 조건이 없어졌습니다.** 더미 구현을 신호정이 맡으면서
(1.1절) AI 담당은 첫날부터 검증 실험을 시작합니다.

**문서 의존은 여전히 없지만, 사람이 겹칩니다.** 08-14 재배정으로 두 트랙의 담당이 모두
신호정이 되었습니다 (아래 다이어그램에서 같은 이름이 양쪽에 나오는 이유). 트랙이 서로를
기다리지 않는다는 성질은 문서 의존 관계의 이야기이고, **한 사람이 두 트랙을 동시에 진행할 수는
없으므로 일정상으로는 직렬화됩니다.** 이 상태를 감수하기로 확정했습니다 (1.2절).

```mermaid
flowchart LR
    subgraph T1["스켈레톤 트랙 - 임동규, 송기하, 신호정"]
        D["더미 구현 3종<br/>신호정"] --> S["S1 ~ S8 배관 관통"]
    end
    subgraph T2["검증 트랙 - 신호정"]
        V1["1순위 한국어 렌더링"]
        V2["2순위 컷 경계"]
        V3["3순위 일관성"]
        V4["4순위 로컬 모델 비교"]
    end

    V1 --> V2 --> V3 --> V4
    S --> JOIN(["합류: 이음매 교체 시작"])
    V2 --> JOIN
```

- **더미 응답 3종**은 `brief:fill` 고정 응답, `draft:generate` 단일 광고형 고정 시안,
  `image:render` 자리표시자 이미지입니다. 규격에 맞는 값이면 되고 품질은 보지 않습니다.
  실제 구현은 나중에 **같은 함수의 다른 분기로** 들어옵니다 (1.1절).
- **합류 지점은 검증 2순위까지**입니다. 1순위(대사 처리)와 2순위(컷 경계)가 닫혀야 `image:render`
  이음매를 무엇으로 채울지 정해집니다. 3순위와 4순위는 이음매 교체와 병행할 수 있습니다.
- 검증 트랙이 스켈레톤보다 먼저 끝나면 AI는 이음매 교체로 합류합니다. 반대로 검증이 늦어지면
  **밀리는 것은 스켈레톤이 아니라 F7과 F9**입니다. 스켈레톤은 스텁으로 완주합니다.

## 2. 1차 기능 범위 (스켈레톤 이후)

스켈레톤의 스텁을 **이음매에서** 실물로 바꾸는 일입니다. 스텁을 우회해 옆에 새 경로를 만들면
스켈레톤이 검증하던 성질(관통, 계약, 오류 경로)이 조용히 사라집니다.

소관은 기획서 14.1의 실명, 근거는 기획서 절 번호입니다.

**F9a를 F9에서 떼어 놓은 이유**는 완료 판정이 갈리기 때문입니다. F9는 "규격에 맞는 이미지가
나오는가"이고 F9a는 "몰릴 때와 실패할 때 어떻게 되는가"입니다. 한 줄로 묶으면 앞의 것만 되어도
완료로 보고되는데, 컷별 생성에서는 **뒤의 것이 새로 생긴 위험 전부**입니다 -- 잡 하나가 외부
호출 5건을 동시에 내고, 그중 하나가 죽으면 세트가 불완전해집니다. 잠정안과 남은 물음:
[미결정_대장.md](../기술문서/미결정_대장.md) N19-a, N20-a.

**F9a의 소관이 2026-08-19에 배정되었고, 한 사람이 아니라 둘로 갈렸습니다**
([회의록](../회의록/2026-08-19_소관배정_화풍확정_카피경로확인.md) 1번).

| 무엇 | 어디 | 소관 |
|---|---|---|
| 잡 하나 안에서 칸 5장을 동시에 부르고 실패를 처리하는 것 | `apps/ai-engine` | 신호정 (03) |
| 잡끼리 몰리지 않게 막는 것 (`render_timeout_s`, 잡 워커) | `backend_core` | 임동규 (05) |

**갈린 기준은 소유 경로**이고, 그 결과 **동시성이 두 곳에 생깁니다.** 두 담당이 인터페이스를
먼저 맞춰야 합니다 -- 두 앱의 허용된 결합은 `packages/contracts`의 HTTP 계약뿐인데
([AGENTS.md](../../AGENTS.md) 아키텍처 경계), 구현이 앞서면 그 선을 넘는 쪽이 쉬워집니다.

**F16(배포)은 1차에 포함합니다.** 기획서 14.4는 이번 범위를 워킹 스켈레톤까지로 정의하고 배포를
명시하지 않지만, 과제 요구사항과 기획서 13.1은 배포를 전제합니다. PM이 "서빙부터 배포 운영까지가
프로젝트 범위"라며 포함을 확인했습니다 (PR #54 리뷰).

**F17은 BE(임동규)가 맡습니다** (PR #54 리뷰). 테스트 작성과 통과 판정 모두입니다. 소수가 여러
역할을 맡는 구조에서 QA가 따로 배정되지 않아 비어 있던 자리입니다.

작성자와 판정자가 같아도 되는 이유는 **관통 테스트가 자동 테스트**이기 때문입니다. 통과 여부를
사람이 보는 것이 아니라 코드가 판정하므로, 기획서 15절이 막으려던 것("결과를 만든 사람이 눈으로
보고 좋다고 하는 것")이 성립하지 않습니다. 같은 이유로 **무엇을 통과로 보는지는 코드에 남아야
합니다** -- 판정 근거가 사람 머릿속에 있으면 그때부터는 자기 채점입니다.

## 4. 검증 트랙 (스켈레톤과 병행)

기획서 15절의 검증 과제 중 **구현 방식을 결정하는 것**들입니다. 결과가 나오기 전에 그 부분을
구현하면 버리는 코드가 됩니다. 스켈레톤은 이 결과를 기다리지 않아도 됩니다 -- 스텁이기 때문입니다
(1.4절).

### 4.1 과제와 합류 시점

| 순위 | 검증 | 뒤집히면 바뀌는 것 | 합류 | 상태 |
|---|---|---|---|---|
| 1 | 6칸 조건 한국어 렌더링 | 대사 처리 방식 전체 (기획서 10.3). 합성 단계와 폰트 자산이 새로 필요 | 이음매 교체 전 | **닫힘 (08-18). 본안 유지** |
| 2 | 컷 경계 제어 | 3x2 격자 생성 방식. 후처리 합성으로 전환 가능성 | 이음매 교체 전 | **닫힘 (08-18). 컷별 생성 후 합성** |
| 3 | 캐릭터와 화풍 일관성 | 프롬프트 설계. IP-Adapter 도입 여부 | 교체와 병행 가능 | 대기 |
| 4 | 로컬 모델과 GPT 비교 | 단일 광고형의 생성 경로 | 교체와 병행 가능 | **닫힘 (08-20). 미채택** |

순위는 기획서 15절 그대로입니다. **1순위를 건너뛰고 2순위부터 하지 마세요** -- 대사를 함께
그리지 않기로 뒤집히면 2순위의 격자 조건 자체가 달라집니다.

**합류 지점이 열렸습니다** (2026-08-18,
[회의록](../회의록/2026-08-18_이미지_생성_경로_결정.md)). 1.4절이 "합류 지점은 검증 2순위까지"라고
적어 둔 조건이 충족되어, `image:render` 이음매를 무엇으로 채울지가 정해졌습니다. 3순위와 4순위는
원래대로 교체와 병행합니다.

**4순위도 닫혔습니다** (2026-08-20,
[회의록](../회의록/2026-08-20_검증4순위_로컬모델_미채택.md)). 로컬 모델 미채택이며, 판정자
두 사람(임동규, 송기하)이 모두 동의해 B-15의 통과 기준을 충족했습니다. **남은 검증은 3순위와
5순위이고, 3순위는 판정 시트 수정이 끝나 착수 가능합니다** (2026-08-20, PR #152).

**닫힌 것은 두 항목이고, 그 대가로 셋이 열렸습니다** (N18 대사 길이 상한, N19 동시 실행 상한,
N20 컷 부분 실패). 셋 다 잠정안이 있어 구현을 시작할 수 있지만, 비운 채로 F9를 완료로 보고할 수는
없습니다 (2.1절 F9a).

2026-08-11 회의에서 확정된 검증 과제는 **모두 8건**이며 담당도 함께 정해졌습니다
([회의 결정](../회의록/2026-08-11_차단7건_회의결정.md)). 위 4건은 그중 **구현 방식을 바꾸는
것**만 추린 것입니다. 나머지 4건(비용 실측, 화풍 반영, 기획 근거 조사, VM 스펙 확인)은 결과가
어느 쪽이든 코드 구조를 바꾸지 않아 여기 합류표에 없습니다. 전체 표의 정본은 기획서 15절입니다.

| 무엇 | 값 |
|---|---|
| 잔여 예산 | **19 USD** (디스코드 `!usage` 실측) |
| QA 이후 단계 몫 | **10 USD.** 이번 라운드에서 쓰지 않고 남깁니다 |
| **이번 라운드 작업 상한** | **9 USD.** 만화형과 단일 광고형 공통입니다 |

근거는 [2026-08-22 회의록](../회의록/2026-08-22_이월_6건_확정.md) 01 이며, 실측치의 정본은
[API생성_시험_보고서.md](../보고서/API생성_시험_보고서.md) 입니다.

**주의: 위 표는 2026-08-22 값이고 그 뒤에 두 번 움직였습니다.** 인용하기 전에 바로 아래
소절을 함께 보십시오.

#### 잔여는 2026-08-29 에 다시 쟀습니다 (5.58 USD)

| 시점 | 잔여 | 무엇이 바뀌었나 |
|---|---|---|
| 2026-08-22 (회의 확정) | 19 USD | QA 이후 단계 몫 10 을 떼고 이번 라운드 작업 상한 9 USD |
| 2026-08-27 (회의 확정) | 약 12.5 USD | **QA 몫 10 USD 를 제출까지의 작업 예산에 합쳤습니다** (= 그 시점 잔여 2.5 + 10). 근거는 [08-27 회의록](../회의록/2026-08-27_안건_12건_확정.md) 01 |
| 2026-08-28 (`!usage` 실측) | 11.94 USD | 총 30.00 USD 중 **18.06 USD 집행(60.2%)**. 01(정승호)이 디스코드 `!usage` 로 재확인 |
| **2026-08-29 (`!usage` 실측)** | **5.58 USD** | 총 30.00 USD 중 **24.42 USD 집행(81.4%)**. 하루 만에 6.36 USD 가 나갔습니다 - 아래 |

**바뀐 것은 08-27 의 결정이 아니라 그 결정이 만든 잔여의 실측값입니다.** 12.5 는 08-27
시점의 근사치였고 집행이 그 뒤에도 이어져 실측이 그보다 조금 낮습니다. 08-27 회의가 이미
"12.5 냐 12.2 냐가 이번 결정을 뒤집지는 않는다" 로 적어 둔 범위 안이며, 확인 시점을 함께
남기는 것이 그 회의의 후속 지시였습니다. 실측값의 근거는
[2026-08-28 회의록](../회의록/2026-08-28_잔여_6건_확정.md) "확인과 공유만" 절입니다.

**08-29 의 6.36 USD 는 둘로 갈립니다.** 실물 모드 시나리오 회차 19세션이 **6.07 USD**
([기록 시트](../보고서/실물모드_시나리오_기록_시트.md) 집행액 절, 그 시점 실측 24.13)이고,
그 뒤에 돈 제품 사진 레퍼런스 탐색 14회가 **0.29 USD** 입니다
([탐색 보고서](../보고서/제품사진_레퍼런스_탐색_보고서.md)). 뒤의 값은 두 `!usage` 실측의
차(24.42 - 24.13)이며 그 사이의 집행이 이 회차뿐이라 그대로 회차 집행액입니다 - 모델별로도
`gpt-5` 출력이 6.98 에서 움직이지 않았고(탐색은 시안을 손으로 써서 텍스트 호출이 0회)
이미지 출력만 14.15 -> 14.2835 로 올랐습니다.

**회차 계획의 예상을 넘긴 것은 회차 쪽입니다.** 시나리오 계획서의 예상 3.886 과 상한 4.755 를
6.07 이 넘었고, 원인은 만화형 8건을 두 번 렌더한 것입니다(기록 시트 집행액 절). 탐색 0.29 는
보고서가 추정한 0.22 보다 0.07 높은 정도입니다.

**"작업 상한 9 USD" 를 지금의 상한으로 읽지 마십시오.** 08-27 결정으로 QA 몫이 합쳐졌으므로
제출까지 쓸 수 있는 것은 **잔여 5.58 USD 전부**입니다. 위 표의 9 USD 는 08-22 ~ 08-27
구간에만 해당하는 값입니다. **집행 누계 자체는 이 조정으로 줄지 않습니다.**

주의: **만화형 실물 렌더 한 세트가 약 0.43 USD 입니다.** 잔여 5.58 은 그 기준으로 약 13세트이고,
08-29 회차가 예상의 1.6배를 쓴 전례가 있으므로 남은 실물 집행은 **회차 전에 상한을 다시 계산한
뒤에** 하십시오. 이 절은 실측을 기록할 뿐이고 **예산 재배분은 회의가 정합니다.**

주의: **유형별로 쪼개지 않는다는 08-22 결정은 그대로입니다.** 잔여가 늘었다고 "만화형 몫"
같은 칸이 생기지 않습니다.

**유형별로 숫자를 미리 쪼개지 않습니다.** 세션 단가가 유형마다 12.6 ~ 58.6배 차이나는데도
그렇습니다 -- 총액으로 관리하면 그 차이를 상한에서 나눠 반영할 필요가 없기 때문입니다.
**보고서 F절의 "유형별로 나눠 잡아야 한다"는 권고는 이 이유로 채택하지 않았습니다.** 집행은
그때그때 사용량을 확인하며 합니다.

**숫자가 갈리는 지점을 알고 정한 값입니다.**

| 유형 | 티어 | 이미지 | 텍스트 | 세션 합 |
|---|---|---|---|---|
| 만화형 (6칸) | `medium` | 0.4041 | 0.0305 | **0.4346 USD** |
| 단일 광고형 | `low` | 0.0069 | 0.0277 | **0.0346 USD** |

단일 광고형은 **텍스트가 이미지보다 4배 비싸** 세션 비용의 80퍼센트가 텍스트입니다. 이미지
기준으로만 상한을 잡으면 이 유형에서 어긋납니다.

주의: **보고서 F절의 "17배"를 이 자리에 옮기지 마십시오.** 그것은
[ADR-0017](../adr/0017-만화형은_칸을_따로_생성해_합성한다.md)이 폐기한 한 장 6칸 조건
(호출 1회 0.1171 USD)의 수치입니다. 같은 보고서 E절이 컷별 생성의 실측값을 따로 싣고 있고,
위 표가 그것입니다.

**환산값은 배정이 아닙니다.** 9 USD 를 만화형 `medium` 세션으로만 쓰면 약 20세션이고 개발용
`low` 만화형이면 약 92세트이지만, 이것은 크기 감각을 위한 나눗셈이지 유형별로 떼어 둔 몫이
아닙니다. 위 결정이 쪼개지 않기로 한 것을 환산표로 되살리지 마십시오.

**이 값에 직접 걸리는 것**은 검증 5순위의 회차 수와 시연 산출물입니다. 개발과 실험을
`low`(또는 스텁)로 돌리고 최종 확인만 `medium` 으로 하는 운용은
[생성_파이프라인.md](../기술문서/생성_파이프라인.md) 6.2절이 정본입니다.

키는 `infra/.env`에 두고 **절대 커밋하지 않습니다.** 이 저장소는 public이라 푸시되는 순간
공개된 것이며, 해결은 revert가 아니라 폐기와 재발급입니다.

### 4.3 실험 코드와 결과를 두는 곳

| 무엇 | 어디 | 왜 |
|---|---|---|
| 실험 코드 | `notebooks/` | 스켈레톤 코드에 의존하지 않아야 병행이 성립합니다 |
| 확정된 로직 | `apps/ai-engine/src/ai_engine/` | 실험이 끝난 뒤 승격. 노트북을 import하지 않습니다 |
| 생성 이미지 원본 | 커밋하지 않음. 팀 공유 드라이브 | 저장소가 public이고 용량이 큽니다 |
| 판정 결과 수치 | 회의록 + [미결정_대장.md](../기술문서/미결정_대장.md) | 문서에 반영되지 않은 실험은 없었던 실험입니다 |

노트북은 nbstripout이 출력을 지웁니다. **판정 근거를 노트북 출력에만 남기지 마세요** -- 커밋하는
순간 사라집니다. 수치는 회의록에, 이미지는 드라이브에 남깁니다.

### 4.4 실험 하나가 끝났다는 것

아래 네 가지가 있어야 결과로 인정합니다. 기획서 15절의 "결과물을 만든 사람이 자기 결과물을
채점하지 않는다"를 절차로 옮긴 것입니다.

1. **조건**: 프롬프트, 해상도, 시도 횟수. 6칸 검증은 반드시 3456 x 2304로 합니다.
2. **수치**: 성공 비율. 판정 기준은 [미결정_대장.md](../기술문서/미결정_대장.md) A-1 참고.
3. **판정자**: 결과를 만든 사람이 아닌 사람. 과제별 명단은 아래 표.
4. **결론**: 본안 유지인지 예비안으로 전환인지. "더 해봐야 안다"는 결론이 아닙니다.

**판정자와 방식은 2026-08-11 회의에서 확정되었습니다**
([회의 결정](../회의록/2026-08-11_차단7건_회의결정.md)).

- **판정은 AI 담당을 제외한 전원**이 합니다. 눈으로 세는 항목과 주관이 섞이는 항목을
  가르지 않고 하나로 통일했습니다.
- 방식은 **메신저에 결과 이미지를 올리고 팀원이 감상을 남기는 것**입니다. 결과가 나올 때마다
  올리므로 판정이 실험 끝에 몰리지 않습니다.
- 이 방식이 성립하려면 **이미지가 판정자에게 실제로 보여야 합니다.** 노트북 출력이나 개인
  드라이브에만 있는 결과는 판정되지 않은 것으로 취급합니다 (4.3절).

**판정자와 통과 기준은 2026-08-14에 확정되었습니다**
([회의록](../회의록/2026-08-14_역할_재배정_임유빈_하차.md)). "AI 담당"은 **03(생성·서빙)만**
가리키며, 04는 판정자에서 빠지지 않습니다.

| 과제 | 판정자 | 통과 기준 |
|---|---|---|
| 1, 3, 5순위 (주관이 섞임) | 정승호, 임동규, 송기하 **3명** | **3명 중 2명 이상** 동의 |
| **4순위** (로컬 모델 비교) | 임동규, 송기하 **2명** | **2명 모두** 동의 |

**4순위만 판정자가 다른 이유**는 그 과제의 수행자가 04(정승호)이기 때문입니다. 판정에 넣으면
자기 결과물을 자기가 채점하게 됩니다. 통과와 별개로 **비교 결과 수치를 함께 남기세요** —
두 사람의 동의만으로는 [ADR-0003](../adr/0003-이미지_생성_경로.md) 재검토 근거가 되지 않습니다.
수치의 정본: [미결정_대장.md](../기술문서/미결정_대장.md) B-15, B-16.

### 4.5 결과가 문서로 돌아오는 경로

기획서 14.3의 문서 관리 원칙을 이 트랙에 적용한 것입니다.

```
실험 -> 회의록 -> 미결정_대장 항목 닫기 -> 기술문서 잠정 표시 제거 -> (구조가 바뀌면) ADR
```

반영은 TL이 합니다. 대장만 닫고 기술문서를 고치지 않으면, 다음 사람이 잠정안을 확정으로 읽습니다.
